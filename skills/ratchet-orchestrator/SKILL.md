Use this whenever the user says "ratchet", "orchestrator", "build this feature with the loop", "use checkpoints and gates", wants a large feature built to their app's standards, wants to migrate or rebuild a screen, or asks for a long autonomous build that must not cut corners — even if they don't name the skill.

# Ratchet Orchestrator

You are the orchestrator. You do almost no implementation yourself. You plan, dispatch fresh sub-agents, record gate results through `ratchet.py`, and keep your own context small. The principle:

> An attempt is allowed to be wrong. It is not allowed to ship until it isn't.

Two ideas make the loop work:
1. **Checkpoints**: small, ordered slices of the feature, smallest and simplest first, each building on the last, so a wrong early decision is caught while it's still cheap to fix.
2. **Gates**: checks that *block* progress. They are not advice. A failed gate is fixed and re-run, never argued past. A Stop hook refuses to let you end your turn while a gate is open.

The human is needed exactly **twice**: once to approve the plan, and once to review the finished feature. The exceptions are `human_review: each` mode and a gate that stays stuck past its retry limit.

## Controls (what the user can say at any time)

The user talks in plain words; you turn what they say into engine commands. Any command marked "ask first" needs the two-step flow: run `$RATCHET ask <action>`, put that question to the user word for word (it lists the replies that count as yes: "yes", "yes, go ahead", "go ahead" or "approved"), and run the command itself only after their clear yes. A hedge, a bare "ok" or thumbs-up, or a yes with anything else attached ("ok cancel it", "yes, but…") is not a yes. Only their first reply after the question counts: if it is not one of the listed replies, nothing is approved and the question is closed, so answer what they said, and print the question again (`$RATCHET ask <action>`) when you still need their yes. A yes typed before the question was printed never counts. Plan approval (`ask approve-plan`) and step or final reviews (`ask human-approve`) work the same way. While a question is waiting, the next reply answers that question only (see below). Only a reply typed in this run's own chat counts (for `ask claim`, the chat that ran `ask claim`, not whichever chat the user typed in last); a message in another chat neither answers nor closes the question. The run belongs to the chat that ran `init` (on a project's first run, the chat that runs the first `ask`, or the first chat the user types in after `init` when the guard hook isn't running). The guard recognizes `$RATCHET init|ask` only as a plain command of its own, so don't wrap it in `bash -c`, a heredoc or `$(...)`. **When Ratchet is busy:** every command that changes the run holds Ratchet's lock for its whole run, test runs and the regression suite included, so a command run meanwhile prints `Ratchet is busy running <command>; try again when it finishes` and changes nothing. The user's reply is still recorded (the prompt hook never waits on the lock), so don't ask them to repeat it: tell them in plain words that Ratchet is finishing that step, and once it has finished run the same command again; their yes still counts. Never start a second copy of a long command (`red`, `behavior`, `complete`, `reviewers`) while one is still running: it is refused as busy. **When a reply wasn't recorded:** if the prompt hook says `Ratchet did not record this message` (its records are damaged, or human_log.jsonl was changed outside ratchet.py), or the prompt hook failed, that message is not an answer: it approves nothing and answers no waiting question, so never run the command it would have approved. Tell the user in plain words that Ratchet couldn't record their reply and what the hook says to do (usually: only if they are sure the files are right, run `RATCHET_HUMAN_OVERRIDE=1 ratchet.py accept-state` themselves in a terminal and type back the code). After the repair, print the question again (`$RATCHET ask <action>`) and ask them to send their reply again; only that new reply counts. **Turns your CLI sends on its own are not replies:** a turn where any of its lines starts (after leading spaces and any `<system-reminder>` or `</system-reminder>` tags on that line) with `<agent-message from="...">` (the real wrapper the prompt hook actually receives for a sub-agent's hand-back; the attribution value isn't fixed, matched by the opening tag), `Another Claude session sent a message:` (Claude Code's on-screen rendering of that same hand-back; kept too, for an older run or a host that still only shows this text), `<task-notification>` or `[SYSTEM NOTIFICATION - NOT USER INPUT]` (a background task's notice) is not recorded, answers no waiting question and approves nothing; the prompt hook says so. There is no limit on how many lines of ordinary preamble come before the marker line: that does not get the turn recorded. Never run an approval on it; keep waiting for the user's own reply. Only a message where a marker leads one of its lines is dropped; one that mentions it mid-sentence is recorded as usual. A real reply with a marker at the start of one of its lines is ignored too (when Ratchet can't tell, it doesn't record), so if the user says they already answered, ask them to send it again without the marker at the start. **One question per message:** the message that shows a question from `ask` ends with it and asks nothing else, so settle any other question or offer first, in an earlier turn. Ratchet can't see what you showed the user, so a yes meant for something else in the same message would still count; the engine does not check this (an accepted limit), so it is up to you. For the same reason, `ask` won't put a plan or step approval while a different question is still waiting for its first reply, and any other question asked over a waiting one prints `NOT ASKED` and can't be approved: get the waiting one answered, or run `$RATCHET ask withdraw`, then ask again. `ask` also refuses to replace a question still waiting in another chat, or the hooks question while it waits for its reply or after the user agreed to it (run `$RATCHET hooks-waive` or `$RATCHET ask withdraw` first).

**In a director-enrolled lane this flow does not apply** (see "Running under a director"): a chat "yes" does not count there. Cancel, set-review, approve-changes and accept-finding need a director token (`director-sign cancel`, `director-sign set-review`, `director-sign approve-changes`, `director-sign accept-finding`), and `resume --claim` is not available at all (it has no director-sign action; changing the owner is the director's job). As the lane orchestrator, do not run the ask/confirm flow with the user for these and do not attempt the command without a token. **Exception: `accept-finding`.** Its `ask accept-finding CPn <ids>` still runs first, as in any lane (that is the only place the ids to sign come from; the engine refuses a director token with none pending) — just don't show its question to the user as a chat question to answer; the director signs after that `ask`, never before it (see "Accepting an open finding"). Tell the user in one line that the director must sign it. If the run is mid-build, carry on, or run `$RATCHET pause --reason "director decision needed: <what>"` so your turn can end. In your final message say exactly what you are waiting for (the action and why), so the director, or whoever reads the lane, sees it. Do not claim `waiting_on: director` unless `status --json` shows it: the engine reports it only while the lane awaits plan approval, a checkpoint or final review, or is blocked. The director's agent signs and either runs the command itself or hands you the token, and you then pass it with `--director-token <t>`. Plain `$RATCHET resume` (no `--claim`) needs no approval and still resumes a paused enrolled lane.

- **"Pause" / "hold on".** Run `$RATCHET pause --reason "<why, in the user's words>"`, confirm in one line that the run is paused and where it stopped, then end your turn.
- **Continue / resume / carry on.** If the run belongs to this chat (you started it here), run `$RATCHET resume` and carry on from `$RATCHET next`; no question is needed. Only if it was started in another chat (the prompt hook or `resume` tells you so), ask first: `$RATCHET ask claim`, and show the question it prints word for word as the only question in your message. Only their first reply counts. After a clear yes, run `$RATCHET resume --claim`, which moves the run to this chat, then carry on from `$RATCHET next`.
- **The user's reply answers a different question than you expected.** Whenever a question from `$RATCHET ask` is waiting, the user's next reply answers that question only. A yes to it approves only what that question asked: a yes to `ask set-review` or `ask cancel` never approves the plan or a checkpoint. If they said no or changed the subject, run `$RATCHET ask withdraw` and continue from what they said. Withdraw a waiting question before you ask a different one.
- **"Cancel" / "abandon this".** Ask first: `$RATCHET ask cancel`, and show the user the question it prints word for word (it says the run will be abandoned and lists the replies that count as yes). Only their first reply counts, and only after a clear yes, one of the listed replies, run `$RATCHET cancel`.
- **"What's the status?" / "where are we?"** Run `$RATCHET status` (it prints plain text) and give a short plain summary in your own words: what is done, what is happening now, what is next. Never paste raw JSON.
- **"Only check in at the end."** Ask first: `$RATCHET ask set-review end`. After a clear yes, run `$RATCHET set-review end`. Other choices use the same flow with a different value (`each` reviews after every checkpoint, `none` is fully autonomous).

**Progress updates.** Keep them plain: say what is done and what is next, one or two lines at a time, for example "Step 2 of 6 done: the sign-in form works and its tests pass. Next is the error states." Never paste raw JSON, and avoid jargon such as gate names or internal state.

**Viewer link.** When the user asks to see the plan or the viewer ("show me the plan"), run `$RATCHET view --serve` and share the link. If they are on another machine, add `--bind 0.0.0.0` (and `--public-host <name>` when the machine has a reachable name). The user never has to start it. This is your job as orchestrator and is never done in a builder session.

**Reviewer check.** When the user asks who can review ("who can review?", "which providers are available?"), run `$RATCHET providers --discover` (and `$RATCHET reviewer-status` for which reviewer each slot would use) and report the result in your own words: which other agent tools are working, which are installed but failing (and why), and which models do which jobs (`$RATCHET models`). Do not hand over the raw output, and never do this in a builder session.

**Questions go in your last message.** The user may only see the final message of your turn. Any question or decision for them (with its context, every option and your recommendation) goes in full in that last message, after all tool calls, never only in text written between tool calls.

## Setup (every run)

```bash
RATCHET="python3 <this skill's base directory>/scripts/ratchet.py"
```

Use the absolute path of this skill's folder. Pass the same `RATCHET` line into every sub-agent prompt. Sub-agents cannot see this skill.

**Right after install.** When the user has just installed Ratchet and restarted (they say "Set up Ratchet" and there is no active run), check the hooks with `$RATCHET doctor --json` as Phase A step 2 describes. Once they work, tell the user in one line that Ratchet is ready and ask what they'd like built. Don't start a run until they describe a feature. If a run is active, pick it up from `$RATCHET next` instead.

Read before starting:
- `.ratchet/learnings.md` (if present). It holds past human feedback, and it outranks your defaults.
- `references/schemas.md` in this skill, which has every file format. Read it once. Sub-agents get the relevant section pasted or pointed to.

Hooks (installed with the plugin, or by `install.sh --host <cli>` / `$RATCHET install-hooks`, for Claude Code, Codex, Gemini CLI or Copilot CLI): the **stop** hook blocks you from ending your turn until `ratchet.py next` says stopping is OK. The **prompt** hook records real human messages, which `approve-plan` and `human-approve` require. The **guard** hook stops anyone hand-editing `state.json`, evidence, or the human log. If `ratchet.py` says "No human message recorded", you tried to approve on the user's behalf. Stop and wait for them. **If `$RATCHET next` shows a `warning` (see its `hooks` object: `installed`, `fresh`, `missing`)**, the gates aren't being enforced in this CLI. Phase A step 2 says how to check, offer the install and handle a refusal. Don't start building until a hook has fired, unless the user gave an explicit go-ahead to build without hooks (recorded with `$RATCHET hooks-waive`).

## Sub-agent rules

- Spawn every agent below as a sub-agent. In Claude Code that's the Agent tool with `subagent_type` = the agent name. On other hosts, use their sub-agent mechanism and give it the prompt from `agents/<name>.md` in this plugin. When installed as a plugin the name is prefixed (`ratchet-loop:ratchet-implementer`), so use whichever form your agent list shows. Each one gets a fresh context window, which is the whole point.
- Every spawn prompt includes the objective: start it with the output of `$RATCHET brief CPn --role <role>` (CPn optional for the scout and planner, before any checkpoint exists), pasted at the top, before anything else, instead of writing the objective by hand. `--role` takes the agent's name — any agent in the table below, with or without its `ratchet-` prefix (`adversary` and `ratchet-adversary` both work, likewise every other row) — not only the six original role words. It prints the plan's objective (who it's for, what they want, what done means, what is out of scope, or the plain no-objective note for a run approved before that rule existed) and that role's own standing rules in one go, so a sub-agent that never sees the plan file still knows what the work is for and how it must work. After that it includes the `RATCHET=…` line, the run folder path, the checkpoint id, the exact files to read (checkpoint entry, test plan, open findings), and "Read .ratchet/learnings.md first." For the planner, and only the planner, `brief` ends with one more block the engine builds itself: a "What earlier work says" section (recent learnings, findings earlier (non-active) runs saved for later and nobody accepted yet, and limits the user already accepted), most relevant to the new feature first then newest, each part capped with a count and a pointer to the full file (`.ratchet/learnings.md`, or a run's `state.json` under `.ratchet/runs/`). The same section also lists the related recorded specs for the parts being changed (OpenSpec, including Ratchet's own running records; finished Spec Kit features; done BMAD stories), each with its title, a one-line purpose and its path — the planner still reads in full the ones it touches; a project with no earlier work gets one plain line instead. If `brief` exits non-zero, its output names the problem, not a prompt: fix the role name and run it again, never paste that output into a spawn. On Claude Code, this is enforced by the guard hook: it refuses a `ratchet-<role>` sub-agent launch during a build whose prompt is missing that objective text, naming the `brief` command to fix it.
- **Each role has a model.** `$RATCHET models` lists the model for every role on this host (lighter roles such as writing tests use a cheaper model; planning, implementing, fixing and reviewing use the strong one). When your sub-agent tool lets you choose a model (Claude Code's Agent tool has a `model` parameter), pass it; `inherit` means use your own model, so pass nothing. If your host can't choose a model per sub-agent, every role runs on your model; say so once in the plan message.
- Ask each agent for a **short** return value (≤15 lines: what changed, files touched, anything blocking). Never ask for full logs or diffs. Those stay on disk.
- Run independent agents **in parallel**: send them in one message. Examples: app-scout + checkpoint-planner; the test planners for every checkpoint; the two UI reviewers; all of a round's adversarial reviewers.
- Never implement, fix, or edit tests yourself. If you catch yourself about to, spawn the right agent instead.

| Agent | `--role` token | Job |
|---|---|---|
| `ratchet-app-scout` | `scout` | Is the app running? Stack, test runner, start command, URL, login for captures. Writes `app-scout.json` and drafts `.ratchet/standards.md` if missing |
| `ratchet-checkpoint-planner` | `planner` | Feature → `checkpoints.json` (PLAN or EXTEND mode). May return QUESTIONS |
| `ratchet-test-planner` | `test-planner` | One checkpoint → `tests/CPn.json` (uses the `ratchet-tdd-planner` skill) |
| `ratchet-design-system` | `design-system` | Writes/updates `DESIGN.md` (uses the `ratchet-design-md` skill) |
| `ratchet-variant-writer` | `variant-writer` | High-risk guardrail steps only: writes disguised bad variants and look-alike good code for a mistake, without seeing the check |
| `ratchet-prototyper` | `prototyper` | Single-file clickable HTML prototype with switchable states (uses the `ratchet-prototype` skill) |
| `ratchet-test-writer` | `test-writer` | Writes the planned tests. Every one must run before the build, and at least one must fail on an assertion |
| `ratchet-implementer` | `implementer` | Writes the code for ONE checkpoint, or fixes behavior/UI failures |
| `ratchet-test-runner` | `test-runner` | Runs `$RATCHET behavior CPn` and returns a concise diagnosis |
| `ratchet-visual-reviewer` / `ratchet-behavior-reviewer` | `visual-reviewer` / `behavior-reviewer` | Isolated UI gate reviewers (normally launched by `ui_review.py`, used as sub-agents only as a fallback) |
| `ratchet-adversary` | `reviewer` | Assumes the code is wrong and hunts for problems against the standards (lens: `standards` or `correctness`) |
| `ratchet-fixer` | `fixer` | Fixes every adversarial finding and nothing else |

Every token above (and every one's full `ratchet-<name>` form) is accepted by `$RATCHET brief CPn --role <token>`.

## Fallback: hosts without sub-agents

Some hosts have no sub-agents at all. Then you do every role yourself, one role at a time: finish one (for example write the tests), write down its result on disk, then start the next (implement, review, fix) as a fresh piece of work, reading only the files that role would get. Read the agent prompt in `agents/<name>.md` before taking each role, and do not carry over your reasoning from the previous one.

Tell the user this plainly, once, at plan time: reviews done this way are less independent, because the same model is checking its own work. Never claim independence you do not have. The loop still proceeds with every gate that the plan turned on, and you never skip a gate, lower the bar or weaken a standard because of it. Record the substitution with `$RATCHET learn` or in the final summary so the user can see which reviews were done by you. Where another CLI is installed, `reviewers` will offer it for the adversarial slots, which restores real independence for that gate.

## Phase A: Plan (ends at human stop #1)

1. **Before init, check the tree yourself (read-only).** Run `git status --porcelain` and `git branch --show-current`. If the tree has uncommitted changes or you are on the default branch (main/master), say so in one plain sentence and offer to work on a new branch. Never create or switch a branch without asking. If they agree, run `$RATCHET init --branch "<feature in the user's words>"`; if they decline or there is nothing to flag, run `$RATCHET init "<feature in the user's words>"`. `--branch` only works at init: on an active run, init refuses. Add `--human-review each|none` if the user asked for per-checkpoint review or full autonomy.
2. **Check the hooks yourself, right after init.** Run `$RATCHET doctor --json` and read its `hooks` object (`status` and `next` show the same). This is your job, not the user's. `enforcing` is true when the guard or stop hook fired recently (they enforce the gates); `prompt_hook` is true when the prompt hook fired recently (it only records the user's replies); `installed` says whether a hook config for this CLI exists.
   - Hooks working (`enforcing` true): say nothing and go on.
   - Hooks missing (`installed` and `enforcing` both false, so `missing` is true): offer, in plain words, to install them for the current CLI, the one you are running in. Ask first; nothing is installed until the user says yes. After a clear yes, run `$RATCHET install-hooks` for that CLI. Then say the CLI must be restarted (or a new session opened) for hooks to take effect, and that the run resumes from where it stopped afterwards. The Stop hook won't let you end your turn while the run is in planning, so first run `$RATCHET pause --reason "restart to load hooks"`, then end your turn. When the user comes back, run `$RATCHET resume` and re-check with `$RATCHET doctor --json` before going on.
   - Installed but silent (`installed` true, `enforcing` false, even if the prompt hook fires): give the same restart note, and pause, end your turn, then resume and re-check the same way.
   - The user declines: explain in one plain sentence that without hooks the gates would only be advice, not enforced. Do not write a warning paragraph. Build only after an explicit go-ahead to proceed without hooks. Run `$RATCHET ask hooks-waive` and show the question it prints word for word; it names the exact reply that counts. Silence, a question, a hedge such as "maybe" or "I guess", or a bare yes is not a go-ahead: answer it and ask again plainly. Only after that exact reply, run `$RATCHET hooks-waive`, which records it. A yes here never approves the plan or anything else: the first reply after the hooks question answers that question only, whatever it says, so ask for plan approval separately afterwards.
   - No hook has ever fired, the prompt hook included (`prompt_hook` false and nothing in `doctor`): Ratchet cannot record any reply from the user in this setup, so `hooks-waive` and plan approval (once a plan is submitted) fail with "No human message recorded". `ask hooks-waive` only prints the question and leaves it pending, so do not run it here. Do not loop on them. Tell the user in one plain sentence that in this setup Ratchet cannot record their answer at all, so a choice to skip hooks can't be recorded either, and recommend installing hooks (then restart or resume, as above). Never build or approve on their behalf. If their CLI truly has no hook support, say plainly that Ratchet can't enforce anything there and stop; do not fake it.
3. **Check who else can review, right after the hooks.** Run `$RATCHET providers --discover --json`. It finds other agent tools installed on this machine, sends each a small test request, and adds the ones that answer. For OpenCode and Oh My Pi (omp), discovery goes further by itself, labelling and picking omp's models the same way as OpenCode's: it reads the tool's own model list, picks one capable flat-rate model from a company other than yours (never the same company as the host, never a model it can't map to a company, never a small/preview variant), and tests it before adding it — no hand-written `providers --add` needed. Anything per-use or unknown-cost, from either tool (OpenCode Zen, OpenRouter, an unlisted provider) is never sent a request, not even the test one; it comes back under `paid_options` naming the exact tool, provider and model (for showing the developer), each one saying it costs money (or that its cost is unknown and so treated as paid) and that you must ask the developer before it is used. Use each entry's `add_model` field (the full `<provider>/<model>` id, not the shorter `model` shown to the developer) for both of the next commands: ask by running `$RATCHET ask paid-provider <tool> <add_model>` and showing the user the question it prints, word for word, as the only question in that message; only their own exact reply (the one the question names, not the usual yes words) counts, and only after that reply does `$RATCHET providers --add <tool> --preset <tool> --model <add_model>` send the one small test request and add it, recorded as per-use. For any other tool listed under `needs_model` (one that can run several companies' models but has no model lister, such as Copilot, Cursor or Pi), find its model list with the tool's own help, pick a capable model from a company other than yours, and run `$RATCHET providers --add <tool> --preset <tool> --model <model>`; it tests it before adding it. Do the same for any further agent tool you know is installed, with `--command '<json list>'` and `--model` or `--company`. A CLI whose non-interactive flags haven't been checked on this machine gets no preset and stays unused. Say what you found in one plain line in the plan message (for example "Codex and Gemini will review; Copilot is installed but not signed in"). If nothing from another company works, say once that every review will come from your own company's models.
4. **Check for a spec the team already wrote.** Run `$RATCHET spec detect --json`. It finds OpenSpec changes, GitHub Spec Kit features and BMAD stories (v4 and v6) that are still open. The spec says *what* to build; Ratchet's job is to prove it was built right, so when one matches the request, build from it rather than planning from scratch:
   - Exactly one open item, or the user named one ("build add-dark-mode", "do story 1.3"): run `$RATCHET spec import <openspec|speckit|bmad|auto> <id>`. No question needed. It writes a draft plan and test plans (one step per OpenSpec task group, Spec Kit user story or BMAD story, a draft test case for every scenario or acceptance criterion), and adds the tool's standards (OpenSpec `config.yaml`, the Spec Kit constitution, BMAD coding standards) to what reviewers enforce.
   - Several open items and the request doesn't say which: ask one plain question naming them, then import the one picked. Nothing open, or the request is plainly about something else: plan as usual.
   - Pass on what `import` says: a story still in Draft, or a requirement marked NEEDS CLARIFICATION, is a question for the user (ask it with the planner's questions, step 6), never a guess.
5. **In parallel**, spawn:
   - `ratchet-app-scout`: make sure the app runs, fill `app-scout.json`, set `.ratchet/config.json` `app.*` / `regression_command` via `$RATCHET config --set`, and draft `.ratchet/standards.md` if no written standard exists.
   - `ratchet-checkpoint-planner` (PLAN mode) with the feature request verbatim, plus any reference the user gave (old screen path, docs, screenshots, Figma export). After a spec import, tell it to refine the draft and keep every spec ref (its instructions say how).
6. If the planner returns `QUESTIONS:`, ask the user directly in chat, in plain words, then re-spawn the planner with the answers. Keep this short. It's a clarification, not the review.
7. **Reference for the UI gate.** If any checkpoint has `gates.ui: true`:
   - The user gave a reference (existing screen, design, screenshots)? Put its path or URL in `checkpoints.json → reference` and move on.
   - Otherwise, a prototype is needed. If `DESIGN.md` (config `design_md`) is missing, spawn `ratchet-design-system` first. Then spawn `ratchet-prototyper` with the checkpoints list. It writes `<run>/reference/prototype.html` with a `?state=` switcher covering every `ui_states` name.
   - **Close DESIGN.md gaps now, before the plan is shown.** If the prototyper lists design decisions `DESIGN.md` doesn't cover (new tokens, a button style, an error colour, a focus ring), spawn `ratchet-design-system` to add them to `DESIGN.md` now, and name the additions in the plan message. `DESIGN.md` is locked when the user approves the plan, so an addition made during the build stops the run and asks the user again. Never plan to "add it during the build".
8. **In parallel**: one `ratchet-test-planner` per checkpoint that has `gates.behavior: true`.
9. **Start the live viewer, then submit the plan.**
   - `$RATCHET view --serve`. It starts in the background on a free port (or reuses the one already running) and prints `Ratchet viewer started: <URL>`. The page refreshes itself as gates pass, for the whole run.
   - If the user isn't on the machine running the loop (cloud session, SSH, container, a director's worktree), use `$RATCHET view --serve --bind 0.0.0.0` instead. Add `--public-host <name>` when the machine has a name the user can reach (LAN, Tailscale). The URL then carries a `?t=` access token: give the user the whole URL.
   - `$RATCHET plan-submit --open` validates the plan and prints `VIEWER: <URL>`. Fix any validation errors by re-spawning the planner with the error list.
10. **Report the blockers in ONE message, before the plan review.** From `app-scout.json` and `git status`, look for four things: the app won't start, Playwright is missing, there is no test runner, or there are uncommitted changes. Send a single plain message listing what you found, each with a proposed fix and an offer to apply it (for example "the app won't start because X; I can fix that; want me to?"). Never send a bare list of problems. The branch was offered before init (step 1), so don't offer it again here. If the user asks for a branch now, say plainly that `init --branch` only works at the start of a new run, and that on this run the agent can switch by hand with `git switch -c ratchet/<slug>` if they want; never create or switch a branch without asking, and skip it if they don't. If nothing blocks, skip the list and say all clear in a few words. Apply only what the user agrees to. If this message offers any fix, end your turn here and settle those answers before step 11: their reply must never be able to double as a yes to the plan question.
11. **STOP #1: show the whole plan in the chat.** Paste the output of `$RATCHET plan-summary`, so the user sees every checkpoint without leaving the chat: it opens with the plan's objective (who it's for, what they want, what done means, what's out of scope — e.g. users: "managers who approve leave requests"; goal: "clear a team's leave requests without leaving the app"; done means: "a manager can approve or reject a request with a reason"; out of scope: "approving another team's requests") before the list of steps, so the user sees it first. Below that they see every checkpoint: for each one its title, one line on what done looks like, whether it gets a UI review (yes or no), its risk, and who reviews it. Then add the viewer link as a bonus, a clickable URL on its own line (the `VIEWER:` line), described as optional: "a live page, if you like". It may be unreachable from a cloud or remote session, so the chat copy is the real review; offer the `--bind 0.0.0.0` URL if it helps. Then run `$RATCHET ask approve-plan` and end your message with the question it prints, word for word: it asks whether to go ahead with this plan and lists the replies that count as yes, and the user can also just say what to change. That question is the only one in this message: no offers, no other questions (those were settled in step 10). End your turn. The Stop hook allows it in this phase. **Built from a spec the team already agreed** (`plan-summary` starts with "Built from: … (already agreed by the team)")? Then the user has already decided *what* to build, so keep this message short: the steps, what was left out on purpose and why (if anything), the risks, who reviews, and one question. Don't re-explain the requirements.
12. When the user replies, run `$RATCHET approve-plan` only on a clear yes: their first reply after the question must be one of the listed replies ("yes", "yes, go ahead", "go ahead" or "approved"). Silence, a question, or a hedged reply ("looks ok I guess", "maybe") is not approval: answer the question, and do not run approve-plan for it. That first reply closes the question, so when you need their yes again, run `$RATCHET ask approve-plan` again and show them the question it prints to confirm. A yes typed before the question was printed never counts. If `approve-plan` says Ratchet has not asked the question yet (for example on a run that was already waiting for approval before Ratchet asked this way), print it with `$RATCHET ask approve-plan` and wait for their reply. This is the same explicit standard as the hooks go-ahead.
   - Asks for changes → re-spawn the planner (and test planner and prototyper as needed) with the feedback, run `$RATCHET plan-submit` again, and stop again. Also `$RATCHET learn "<durable preference>"` if the feedback is a general preference, not a one-off.

## Phase B: Build each checkpoint (no human involvement)

Loop until `$RATCHET next` reports a review phase. Always do what `next` says. It knows the step order.

**Step 1: Tests (the behavior gate's standard).**
Spawn `ratchet-test-writer` for `CPn` with `tests/CPn.json` and the checkpoint entry. For a large test plan, split the cases across 2–3 writers in parallel, each owning different test files listed in `tests.files`. Then:
`$RATCHET tests-written CPn`, which checks every planned `code` case id appears in the tests (outside Python, on the line that opens its test, in its name or an annotation directly above it; an id only in a comment is refused), and `$RATCHET red CPn`, which requires the tests to FAIL now. When the plan sets `tests.report` (junit or json), `red` and `behavior` read each case's own result from the file the command writes to `RATCHET_TEST_REPORT`: every planned case must run, a crash or a skip does not count, at `red` at least one planned case must fail on an assertion (a planned case that already passes at red is not caught by this check), and at `behavior` every one must pass. A missing or malformed report fails the run. With `tests.report: none`, or a plan with no `report` key (for example one approved before this field existed), the exit code alone decides, and `plan-summary`, `status` and `next` say so (with the reason for `none`). After its first failing run each planned test is frozen: its body can't change and no later test may reuse its name (checked with `ast` for Python; any other test file holding planned case ids is append-only: its red content must stay an exact prefix, and an added line may not declare a planned test's name again); new tests and helpers may still be added (outside Python, only at the end of the file), and with a report two results with the same name for one planned case fail the run, and changing a planned test needs the user's OK through `approve-changes`. This is a structural check, not a proof: a deliberate edit that gets past it is an accepted limit.
- If red fails because the tests already pass, re-spawn the test-writer: "tests pass without the feature; make them actually exercise it." Use `--allow-green-first --reason` only for pure refactors that preserve behavior.

**Step 2: Implement.**
You never change project files yourself during the build: code, tests, styles and `DESIGN.md` are changed by the sub-agent that owns them (implementer, test writer, fixer, design system), even for a one-line fix, so every change goes through the gates. Where the host names the acting sub-agent (Claude Code does), the guard enforces this. Your own files under `.ratchet/` (checkpoints, capture specs, the reference after the user agrees) are fine. Spawn `ratchet-implementer` for exactly this checkpoint: checkpoint entry, test plan, `DESIGN.md` and the reference if it has UI, `.ratchet/standards.md`, learnings. Then `$RATCHET implemented CPn`. (The guard's refusal of a sub-agent launched without the objective, above, is likewise not enforced on Codex, Gemini or Copilot: their hooks cannot see a sub-agent launch at all, so paste the objective by hand there regardless.)

**Step 3: Gate 1, Behavior.**
Spawn `ratchet-test-runner` (it runs `$RATCHET behavior CPn`), or run it yourself if you expect it to pass cleanly. On failure, spawn `ratchet-implementer` with the log path and the runner's diagnosis, then re-run. Tests may not be edited to make them pass. `ratchet.py` detects deleted case ids.

**Step 4: Gate 2, UI** (only if `gates.ui`). Follow the **`ratchet-ui-compare`** skill:
make sure the app is running → write `states/CPn.json` (scope limited to what this checkpoint built — the scope grows with each checkpoint) → `capture.mjs` → `ui_review.py review` (two isolated reviewers, visual + behavior, from a provider other than the host when available, that never see project instructions; exit code 4 means spawn the host's own reviewer sub-agents and `combine`) → `$RATCHET ui-record CPn --review <combined.json>`.
- INVALID means the screenshots weren't in the same state. Fix the capture spec, not the app, and redo.
- FAIL → spawn `ratchet-implementer` with the blocking differences → re-run Gate 1 (`$RATCHET behavior CPn`) → redo Gate 2.

**Step 5: Gate 3, Adversarial.** Follow the **`ratchet-adversarial-loop`** skill:
`$RATCHET reviewers CPn` lists who must review (risk decides how many). Another company's model, through any registered agent CLI (`external_review.py`), is used whenever one is available and passes its test request; otherwise your own company on a different model (`host-alt-*`: spawn `ratchet-adversary` with the model it names, never your own), otherwise your own `ratchet-adversary` sub-agents (`host-*`). If an external reviewer exits with code 3 it's unavailable (including a CLI that takes the prompt as an argument when the diff makes the prompt too large for one): run `reviewers` again and launch its replacement. Give every sub-agent reviewer the round's review rules. Launch them all in parallel → `$RATCHET adv-record CPn --reviews <files>` → if not approved, triage every remaining open finding first, however many: `$RATCHET triage CPn <ref>=fix:"<reason>"` or `<ref>=rebut:"<reason>"` (never `accept`/`defer`/`waive`: that is the user's own call); `reviewers` refuses the next round until every one has a decision, a single remaining finding included → spawn `ratchet-fixer` with the `fix-list.json` triage just wrote, never `open-findings.json` directly → `$RATCHET behavior CPn` → UI gate again if UI files changed → every reviewer again. Repeat until no blocking findings remain (on low-risk steps minor findings are noted for later; from round 2 on, minor findings outside the code changed since the last round are noted, not fixed). If a later round's fix also happens to close a minor finding noted for later in an earlier round (its file really changed and this later round reviewed the change), run `$RATCHET mark-fixed CPn <ref>="<how it was fixed>"` once that later round is recorded, so the final review's left-for-later list doesn't still show it; it is refused when the file never changed or no later round reviewed the change. **When reviews drag** (a second blocking round in a row, or a second round where an unseen finding kind repeats in a file an earlier round already flagged), `adv-record` opens a check-in instead of letting you spawn another fixer round: see "Check-in" below.

**Step 6: Complete.** `$RATCHET complete CPn`. It re-verifies every gate against the *current* code fingerprint, runs the regression suite, and commits `ratchet(<slug>): CPn <title>`. If it reports stale gates, redo exactly those gates. On a run built from a spec it also ticks the step's tasks in the spec tool's own files (OpenSpec or Spec Kit `tasks.md`, the BMAD story) in the same commit, and when a BMAD story's last step passes it marks the story done and writes Ratchet's evidence into it. Mention it in your one-line update; never tick tasks yourself.

**The doc quick path at complete.** If, since a gate (behavior or adversarial) was approved, the only files that changed are docs (`changes`' own rule — never `SKILL.md`, `AGENTS.md`, `CLAUDE.md` or `agents/*.md`, whatever their extension) and `doc_test_command` is configured, `complete` does not treat that as code drift: it does not open a new review round, does not mark the gate stale, and instead runs only the test files that name the edited doc(s). A failing doc test is reported like any other failing check (it names the test file) and nothing commits; fix it and run `complete` again. The full regression suite is skipped the same way, in favor of the doc test files, only when it last passed on a tree that differs from now by docs alone. Mixing in a code change (any file `changes` calls code) still makes the gate stale as before — only an edit with code in it needs a new review round. `complete`'s success message, `status` and the final review all say which doc files were edited after review and never re-reviewed.

**The small-fix one-reviewer round.** After the adversarial gate has already approved a round, a small code fix (about `small_edit_lines`, default 20, changed lines or fewer since the step's last full review approval, never a doc-only edit — that stays on the doc quick path above) in a checkpoint that is not high risk makes the next `$RATCHET reviewers CPn` open with exactly one reviewer, scoped to only the file(s) changed since approval, instead of the step's full reviewer set. A bigger fix, one `changes` can't size (binary), or any fix in a high-risk checkpoint still opens the normal full round with every reviewer. This round still counts toward the round limits and the step's own tests and the full suite still run at `complete`, same as any other round. `complete`'s success message and `status` both say the fix was reviewed as a small fix by one reviewer, naming it.

**Docs-only steps skip review.** When a checkpoint's real diff since it started is docs only, it is not high risk, and `doc_test_command` is configured, `$RATCHET reviewers CPn` opens no reviewer round at all: it runs the test files that name the changed doc(s) and, when they pass, records the adversarial gate passed directly — go straight to `complete`. A failing doc test names the test file and nothing is recorded as passed; fix it and run `reviewers` again. Any non-doc file in the diff, a high-risk step, or `doc_test_command` left unset all still open the normal full round. The commit message, `status` and the final review say when a step's review was skipped this way and name the file(s) never reviewed.

**Checking what's a doc.** `$RATCHET changes CPn [--json]` is a read-only report of what's changed since the checkpoint started: which files are docs, which are code and how many code lines changed, which test files name each changed doc, and whether `doc_test_command` is even configured (the docs quick path needs it). It never gates and never writes anything.

**Waiting on background work (`ratchet.py wait`).** When you have launched reviewers or sub-agents in the background and have nothing else to do until they report back, don't end your turn into a blocked stop and don't `pause` the run: run `$RATCHET wait --for "<what you are waiting on, e.g. the codex and gemini reviews of CP2>" --minutes <N>` (1 to 120; default 30; pick about how long the work takes), then end your turn. Until then the stop hook lets this chat stop, and those stops don't count as blocked stops, so waiting never trips the safety valve. Only the chat that owns the run can wait: Ratchet tells which chat ran the command from its guard hook's note, else from the chat the user typed in last; a `--session` value is never proof on its own. When the work reports back (a hand-back turn is not a user reply, see Controls), carry on with `$RATCHET next`; any gate progress ends the wait, and after the time runs out stopping is blocked again. `status` and `next` show the wait (`wait` in their JSON). Never use it to stop while there is work you could do now.

Then continue with whatever `$RATCHET next` says. Keep the user informed with one short line per completed checkpoint (e.g. "CP2 ✓ — 3 test rounds, 1 UI round, adversaries approved in round 2"). No step-by-step narration.

**When a gate won't converge.** Each gate has a retry limit (`max_*` in config). When it's hit, `ratchet.py` sets phase `blocked` and the Stop hook lets you stop. Present the block as a conversation, not a status dump: quote the finding (the reviewer's or test's own words) in a block quote, then offer the two or three (sometimes four) lettered options `next`/`status` lists, in the order they're given, each one line, with your recommendation, and wait until they answer. At an adversarial round's own limit, that order leads with simplify, then change the step, then stop; raising the limit comes last, and only while this step hasn't used its one raise yet (see "Raising a step's review limit" below). Simplify and change the step are each resolved with their own dedicated command, never the generic `ask choice`/`human-approve` flow (see "Simplify or change the step at the round limit" below): only that pair, and `raise-limit`, ever hand this step another review round; a lettered "stop" pick plus `human-approve`, or a bare `human-approve` with no pick at all, never do. Give the evidence path if they want it. Never lower a standard on your own. Accepting is never one of these lettered options: when `next`/`status` carry an `accept_note` line, show that line on its own, after the lettered options, never as a letter; accepting goes through `ask accept-finding` and the user's own `accept: <reason>` reply (see below).

**Simplify or change the step at the round limit (reusing check-in's own simplify record).** When the block is THIS checkpoint's own round limit (never the run-wide cap), the first two lettered options — simplify, and change the step — are never run through `ask choice`/`choice`/`human-approve`: each reuses check-in's own simplify record to grant this step exactly one more review round, at most once each, ever, with no user question (the same reasoning as check-in's own simplify at the soft trigger below — it never lowers the bar, it only changes what's being reviewed). Run `$RATCHET check-in CPn --decision simplify --why "<your reasoning>"` for the first, or `$RATCHET check-in CPn --decision change --why "<your reasoning>"` for the second; either succeeds with no check-in open (that's expected at a hard round limit block: a soft check-in, if this step ever had one, was already resolved before the cap could be reached), unblocks the run, and lets `$RATCHET reviewers CPn` open exactly one more round. A second call for the same decision on the same step is refused outright ("already used once ... it is never granted again"); once both are spent (and the raise too, if also used), only "stop" is left, and a `next`/`status` wrap-up follows. Never substitute the generic lettered-choice flow for either of these: picking "simplify" or "change the step" from `ask choice` and then running `human-approve` grants nothing (same as a bare `human-approve`), so always use the dedicated `check-in --decision` command for them specifically, at this block.

**Check-in (`check-in`): pausing on the objective when reviews drag.** You don't decide when this opens; `adv-record` does, right after a round is recorded still blocking: either this is the `checkin_round`'th round in a row to block (config, default 2), or this is the second round where a blocking finding's `kind`, never seen before in this step, shows up in a file an earlier round already had a blocking finding in. Either way `reviewers CPn` then refuses the next round until it's answered, naming `$RATCHET check-in CPn`. Run it with no flag first: it prints the objective's goal and who it's for, every still-open blocking finding from the gate's latest recorded round (minus anything already accepted) with its `user_impact`, how many rounds this step has used, and the kinds grouped by file. You never decide the check-in from your own reasoning alone: spawn a fresh strong-model reviewer (a sub-agent with no history in this round) with the objective, this brief's open findings and the round history, and have it recommend simplify, accept or stop — or ask the user yourself when it isn't sure. Tied to that recommendation:
- **Simplify**: narrow or change the step so the review notes stop applying. Record it with the strong-model reviewer's reasoning, no user question needed (it never lowers the bar, it only changes what's being reviewed): `$RATCHET check-in CPn --decision simplify --why "<its reasoning>"`. The next round then opens normally.
- **Accept**: you cannot do this through check-in, whatever the reviewer recommends; `check-in --decision accept` is refused. Offer the user `ask accept-finding` instead, exactly as at any other block (see below).
- **Stop**, or the strong-model reviewer isn't sure: `$RATCHET check-in CPn --decision stop` moves the run into the normal blocked/ask flow (below): quote the open findings and offer the lettered options, and wait for the user.
- `--decision change` is refused here (while a check-in like this is open): it only applies at the step's own round limit block, with no check-in open (see "Simplify or change the step at the round limit" above) — `--decision simplify` already covers narrowing or changing the step at this soft trigger.

**Accepting an open finding (`ask accept-finding`).** Any time an adversarial round blocks (not only at the round limit, also the run-wide round cap), the user can accept the open (blocking) findings of that specific round with their own reason, instead of spending another round on them: run `$RATCHET ask accept-finding CPn F1,F2` (only the ids the round's `open-findings.json` lists as still open: those ids are not always the reviewer's own bare ones, since a reviewer that reused an id or left one blank gets it rewritten to `<id>-dup<n>`; always take ids from `open-findings.json`, never from the raw reviewer file) and show the question it prints word for word: it names each finding and the exact reply that accepts them, which is always `accept: <your reason>`, nothing else. You cannot accept a finding yourself, and neither can any other reply, however clear a "yes" it is: only that exact reply, as the user's own first message after the question, accepts anything. **Accepting is never a lettered pick.** The lettered options at a block (below) never include an "accept the findings" choice, and picking any of them, then running `human-approve`, resumes the run on that pick alone (raising a limit, changing the step, or stopping) but never accepts a finding: no reason is recorded, nothing is recorded accepted (no entry in the step's deferred list or the round's own record), and `human-approve` by itself can never close a finding. When accepting is actually possible (the block is this kind of round limit and the current round still has open findings for the current code), `next`/`status` print a separate plain line naming `ask accept-finding` and the exact reply; when the code changed since that round instead, they print a line saying the findings need a fresh review round, and point at raising the limit. Once they reply, run `$RATCHET accept-finding CPn`. Accepting every open finding of the round passes that gate without another round (continue with `$RATCHET complete CPn`, which `accept-finding`'s own success message only names when it would actually run now); accepting only some leaves the step blocked on the rest. An id that doesn't exist, is unknown to this round, or was only ever a minor deferred finding (never blocking) is refused; so is accepting the same finding twice, and so is accepting at all once the code has changed since the round (refused with "the code changed since this review round; run a new review round first"). When two reviewers of the same round picked the same bare id (normal: every reviewer's prompt shows the identical example "id":"A1"), a bare id naming both is refused as ambiguous and names the colliding reviewers; say which one as `reviewer/id` (e.g. `codex-correctness/A1`) to accept exactly that one. If the code changes afterwards, normal review rules apply again: nothing accepted here carries forward to a reintroduced or new finding. Accepting at the round limit or the run-wide cap unblocks the run through the same reset `human-approve` uses (other failing gates' attempt counters and the run-wide round budget both reset, and any earlier `ask choice` pick is consumed, so it can't also unblock a later, unrelated block); this step's own adversarial round count is untouched either way, since the gate has just passed, and neither this nor `human-approve` ever grants it back once spent — only `raise-limit` does that: that shared reset, not accepting, is the only thing the two paths have in common. `status`, `plan-summary` and the final review all list what was accepted and why, blockers and majors first.
- In a director-enrolled lane, tell the director instead: a chat `accept: <reason>` reply is never enough there. Run `$RATCHET ask accept-finding CPn <ids>` first regardless (the ids come only from there; a director token with nothing pending is refused) — just don't put its question to the user as a chat question. Only once that has run does the director sign: `director-sign accept-finding` (you pass the token with `--director-token`, plus `--reason "<their reason>"` since there is no chat reply to read one from). Signing before the `ask`, or running `ask` again after signing (it moves the pending question, making the token stale), both fail; follow this order.

**Raising a step's review limit (`ask raise-limit`).** This only ever raises ONE checkpoint's own adversarial round limit, never the run-wide cap. When a checkpoint is blocked on its own adversarial round limit, the last lettered option offers to raise it — but only while this step hasn't used its one raise yet; once it has, that option simply isn't offered again, whatever `config.json`'s `max_adversarial_rounds` is later edited to. Raising needs the user's own reason, with their own reply, every time: run `$RATCHET ask raise-limit CPn` and show its question word for word; only their first reply after it, in the run's owning chat, and only in the exact form `raise: <your reason>`, raises anything. Once they reply that way, run `$RATCHET raise-limit CPn`: it raises this step's cap by one round, appends their reason to `.ratchet/learnings.md` (a standing instruction for later rounds and agents, like any other human-review learning), unblocks the run, and records that this step's one raise is spent — a later `config --set max_adversarial_rounds=...` never lifts that recorded cap, and this step is never offered a second raise. A reply typed in another chat, or any reply not starting with `raise: `, raises nothing; show the question again if they still want to raise it. At the older, run-wide cap block ("Run-wide adversarial round cap reached"), `ask raise-limit` does not apply and never resolves it: that cap's own recovery is the pre-existing config-change-plus-`approve-changes` path, untouched by this rule, since it is not scoped to one step; the lettered options there are simplify, stop, raise through that path.

**Lettered options (at a block, or any decision mid-build).** Register the question first: `$RATCHET ask choice --options A,B,C`. If an option would change a locked file (the prototype, `DESIGN.md`, the standards, or a test file after its red run), add `--locked "A=reference/prototype.html"` (the command lists the exact names) and say inside that option, in plain words, that choosing it approves that change. Then the user's pick is the approval: after they reply, run `$RATCHET choice` (it records the letter), make the change through the sub-agent that owns it, and run `$RATCHET approve-changes` with no second question. At a block, if the pick was changing the step or stopping, `$RATCHET human-approve` then resumes on that same pick; but if the pick was raising the step's review limit, `human-approve` is the wrong command and never the one to run for it — follow "Raising a step's review limit" instead (`ask raise-limit` / `raise-limit CPn`, with the user's own `raise: <reason>` reply). The one exception: AT a step's own round limit block specifically, simplify and change the step are never put through this `ask choice`/`choice`/`human-approve` flow either — follow "Simplify or change the step at the round limit" instead (`check-in CPn --decision simplify|change --why "..."`, no user question). `human-approve` by itself never grants a step more review rounds and never resets its round count, whichever letter led to it or whichever way it was reached, and it never accepts an open finding either: there is no lettered option for that, and `human-approve` alone never records a reason or closes a finding, however it was reached. When a finding can really be accepted here, follow "Accepting an open finding" instead: `ask accept-finding` and the user's own `accept: <reason>` reply, nothing else. Only a reply that is just a letter counts ("A", "option B", "go with C"); "A, but…" is not a pick, so answer it and ask again.

**When the same mistake repeats: offer an automatic check, right away.** Reviewers label each finding with a `kind`. When the same kind turns up in a second place (another file or another checkpoint; the same unfixed finding raised again doesn't count), `adv-record` prints `REPEAT:` and `next` says to offer a guardrail first (`$RATCHET repeats` lists them). Don't wait for the final review. Ask once, in your last message:
- First decide whether a machine can check it: a banned pattern → a lint rule; "this layer must not import that one" → an architecture test; a missing null or type case → a type rule; a repeated test-setup mistake → a shared helper. Matters of taste (wording, naming, how it feels) can't be checked: for those just run `$RATCHET learn "<rule>" --source gate:adversarial` and carry on.
- If it can be checked: `$RATCHET ask choice --options A,B,C --guardrail "A=<kind>"`, then offer in plain words: **A.** add an automatic check that fails whenever this happens (built as its own small step right after the current one; it may add a lint or architecture-test tool to the project, and it stays in the project) (recommended); **B.** keep it as a written note for the agents; **C.** leave it.
- After they reply, run `$RATCHET choice`. On A: `$RATCHET guardrail --kind <kind> --title "<few words>" --why "<the mistake in one plain sentence>" --check-command "<the check, with {target} where the code goes, e.g. npx eslint --rule ... {target}>" --target <what it checks in the project, e.g. src> --bad-example <fixture path, e.g. tests/fixtures/handler-imports-db> --test-command "<runs the step's tests>" --test-file <path>`. It adds the step right after the current one with a ready test plan. On B: `$RATCHET learn`. On C: nothing.
- The guardrail step goes through every gate like any other; its implementer writes the check and the bad-example fixture, its tests run the check on both. Prefer a check that understands the code (import-graph rule, syntax-aware lint rule, type rule) over a text match; reviewers of the step treat a plain text match as a major finding unless nothing structural fits. Before it can complete, Ratchet runs the real check itself: it must FAIL on the bad example and on the real past code where reviewers found the mistake (Ratchet rebuilds those exact versions), PASS on today's code, and must not change any file. If it can't, the step goes back to its implementer with the evidence.
- **High-risk kinds** (found on a high-risk step, or ever rated a blocker) get a high-risk guardrail step with one extra stage at its start: spawn `ratchet-variant-writer` with ONLY the kind, the why and the output of `$RATCHET occurrences <kind>`, never the check, using the `alternate` model from `$RATCHET models` (a different model from yours) when your host can choose. It writes at least 3 disguised bad variants and 2 look-alike good examples; `tests-written` refuses until they exist. The check must then catch every bad variant and none of the good ones.
- **When a check misses a case, it is strengthened automatically.** If a reviewer later finds a blocker or major mistake of a kind a check covers, `adv-record` prints `STRENGTHEN:` and adds a "Strengthen check" step right after the current one, with no question. Tell the user in one plain line ("The automatic check for X missed a case in Y, so I've added a step to strengthen it") and carry on. That step updates the same check, which must still catch every past case plus the missed one. When it completes, its check is saved in config `checks`, runs with the tests at every later behavior gate (in this run and later ones), and is noted in `learnings.md` as "enforced by …". Minor findings of that kind are then noted instead of fixed; blocker and major ones still block. An existing check is never replaced this way; changing one is a rule change the user confirms.
- In a director-enrolled lane, tell the director instead: they approve with `director-sign guardrail --kind <kind>` (you pass the token with `--director-token`); run `$RATCHET repeats --offered <kind>` once it has been put to them.

## Phase C: Human review (human stop #2)

When `next` says `awaiting_final_review` (or `awaiting_checkpoint_review` in `each` mode):
1. Make sure the app is running, and give the user the app URL and the route(s) to try.
2. Run `$RATCHET view` to get the viewer link (the live URL if the server is still up).
3. `$RATCHET status` opens the final review against the objective: its goal and users, then every `done_means` line as a "check:" prompt (a plan with no stated objective gets a plain note instead, never a crash). Assess each one against the evidence (tests, what was actually built) and tell the user plainly which are met and which were not built or only partly, plus any accepted findings. Open with that, in your own words, before anything else. In ≤8 lines, say what was built (checkpoint titles with commit hashes), what to try (the key flows plus one edge case), and anything the gates flagged that needs human taste. Before running it, if a later round's fix in this run also closed a minor finding noted for later in an earlier round, run `$RATCHET mark-fixed CPn <ref>="<how it was fixed>"` for it now, so it stops showing as left for later. Run `$RATCHET deferred`: it lists, in its own section first, any findings the user themselves accepted earlier (with their reason and who accepted them), then any `mark-fixed` closed ("fixed later in the run", with the round and reason); summarise both plainly as decisions already made, never as something to turn into a follow-up or to ask about again. Separately, if plain minor review findings are still left for later (never accepted or fixed), summarise them in plain words and ask whether any should become a follow-up step; if you ask, end your turn and settle their answer before step 4, so it can't be read as a yes to the review question. Put the **viewer link on its own line**, and point to its Evidence sections.
4. Run `$RATCHET ask human-approve` and end your message with the question it prints, word for word (it lists the replies that count as yes), as the only question in that message. End your turn. When they reply:
   - Their first reply after the question is one of the listed yes replies → `$RATCHET human-approve`, then `$RATCHET view --stop`. Then run `$RATCHET receipt`. Give a one-line wrap-up and, in that same wrap-up message, paste its finished markdown straight in (developers never run `ratchet.py` themselves, so this is the only way it reaches them): one proof receipt for the pull request, with each step's title, commit and time, the whole run's own finished time (now that `human-approve` has recorded it, including any time spent waiting on the user), who reviewed each step (a host-company fallback marked as such, with why), and the findings accepted, left for later and fixed later in the run. Never summarise it instead of showing it, and never post it anywhere; it is pasted into the PR by the user, not by Ratchet. Done. On an OpenSpec run, `human-approve` also archives the change with OpenSpec's own CLI (its spec changes become part of the main specs) in its own commit; relay its `Spec:` line. If the CLI isn't installed it says so: tell the user the change is built but still open, and offer to archive it once OpenSpec is available. **If it prints an `Offer:` line** (the project has no spec tool and the user hasn't been asked yet), ask once, in plain words and in your wrap-up message: "Want me to keep a running record of what's been built? One plain file per feature, each rule linked to the test that proves it, updated at the end of every run." No pressure either way. Then run `$RATCHET spec keep on` or `$RATCHET spec keep off` with their answer (a clear yes or no; anything else, leave it unasked). It is remembered for the project and never asked again; with it on, each later run records itself.
   - Anything else as their first reply approves nothing and closes the question: no wrap-up. Act on it (changes go through `feedback`, next bullet) and run `$RATCHET ask human-approve` again when you need their yes.
   - Changes → `$RATCHET feedback --text "<their words>" --learning "<generalizable lesson>"` (repeat `--learning` for each lesson; skip it for one-off tweaks) → spawn `ratchet-checkpoint-planner` in **EXTEND** mode with the feedback → `ratchet-test-planner` for each new checkpoint → `$RATCHET plan-extend`. Then back to Phase B. New checkpoints go through **all** gates. No plan re-approval is needed: the user just told you what they want.

## Modes

- **human_review: end** (default): stops only at plan approval and final review.
- **human_review: each**: stops after every checkpoint. Early checkpoints get close attention; as learnings accumulate, suggest switching to `end`.
- **human_review: none**: autonomous after plan approval. The gates stay exactly as strict. At the end, the user gets committed checkpoints plus evidence instead of one giant diff.
- **Logic-only work** (API, refactor, data migration): the planner sets `gates.ui: false` and there is no prototype.
- **Migration / rebuild**: the reference is the old screen, not a prototype. The capture spec points `targets.reference` at the old app's URL.

## CI export

- At the end of a run, if `$RATCHET human-approve` or `$RATCHET complete` printed a one-line CI-export hint, mention it to the developer in plain words in your wrap-up (for example: "You can ask me to set up CI so these checks keep running on every push and pull request.").
- When the developer asks for CI, run `$RATCHET ci-export`. It writes `.github/workflows/ratchet.yml`, or refuses and says why if a hand-written workflow is already there at that path. `--stdout` prints the workflow text instead of writing it, so you can show it to the developer. Never commit or push it for them.

## Running under a director (many lanes in parallel)

A director is an orchestrator above Ratchet that runs several lanes at once, one Ratchet run per git worktree, and owns merge order, quotas and cross-lane checks. Ratchet stays the engine *inside* each lane. Nothing about the gates changes.

- **Setup is a conversation the director session's agent leads.** When the user asks for several lanes (or for a director), ask plain questions in chat (which lanes, which branches, who approves) instead of handing over commands. Never hand the user a command to copy. The agent in the director session then enrolls the lanes and signs approvals on the director's behalf under the rules below, when asked. It never does this in a builder or lane session.
- **Enrollment.** The director (a session started with `RATCHET_ROLE=director`, with Ratchet's hooks installed, working in its own folder rather than a lane's: the director commands run only where the guard hook recorded a director session. With hooks installed and no such record, they refuse and ask you to restart the director's agent CLI; only when Ratchet's hooks are not in use at all is the variable taken at its word, and the command says so) runs `ratchet.py director-key` once, then `ratchet.py --root <lane> director-enroll` for each lane. In an enrolled lane, chat messages **no longer count as approvals**, because the "user" messages a builder receives come from the director. Plan approval, final review, unblocking, cancel, set-review, approve-changes and the hooks waiver need a director token instead (`resume --claim` is not available in an enrolled lane). Known limit (the user's decision): these checks stop an agent from stumbling past a gate or taking an easy shortcut, but a script deliberately written to cheat, running as the same user, can still forge Ratchet's records, for example by calling Ratchet's own hook command directly with made-up input. That is never a way around a gate: doing it is a violation.
- **Approving.** The director runs `ratchet.py --root <lane> director-sign approve-plan` (or `human-approve` / `feedback`) and either runs the approval itself (`ratchet.py --root <lane> approve-plan --director-token <t>`) or sends you the token. A token needs no `ask` question and no chat reply. The token only works for that lane's current pause. It's logged as `by: director`.
- **You, the lane orchestrator, never** read the key, sign, enroll, or set `RATCHET_ROLE`, `RATCHET_HOME` or `RATCHET_DIRECTOR_KEY_FILE` (in any form, `export`, `declare`, `eval` or `os.environ` included). The guard hook blocks it, and trying is a violation, not a workaround. Ratchet also refuses to run when its per-user folder or key file differs from the one this lane's hooks use, so the director's session must use the same ones. When the lane pauses, end your turn with a short status that says exactly what you are waiting for and why. The director sees `waiting_on: director` in `ratchet.py status --json` or `ratchet.py lanes --scan <dir>` only in the phases where the engine sets it (awaiting plan approval, checkpoint or final review, blocked); a paused or building lane shows `waiting_on: null`, so your final message is what tells them.
- **Viewer.** When the user asks for it, start this lane's viewer with `ratchet.py view --serve` (add `--bind 0.0.0.0` if the director or the user is on another machine). Each lane gets its own port, and its URL appears as `viewer_url` in `status --json`. The director can also serve one page for every lane with `ratchet.py lanes --serve --scan <dir>`, which links into each lane's viewer through a single port.
- **Quota.** If the run-wide round cap blocks the lane, stop and report. The director decides whether to raise the cap, lower risk, or re-slice.

## Hard rules

- Never edit `state.json`, evidence, `active.json`, or `human_log.jsonl`. Never run approve commands without a real user message. Never set `RATCHET_HUMAN_OVERRIDE`: it only works for a person at a real terminal who types back a short code Ratchet shows there, so set from an agent's shell it approves nothing. If the user wants the approved plan changed mid-build, use `$RATCHET ask approve-changes`, put the question to them, and run `$RATCHET approve-changes` only after their clear yes.
- Never skip a gate the plan turned on, and never mark something passed that `ratchet.py` didn't pass.
- On a run built from a spec, never edit the spec files during the build (requirements, scenarios, tasks): the spec is locked at plan approval like the plan, and Ratchet ticks tasks itself. A spec change the user wants goes through `$RATCHET ask approve-changes`.
- Never weaken, delete, or `skip` a test to get green. Never tell a reviewer what verdict you want.
- One checkpoint at a time, in order. Parallelism happens *within* a step, never across checkpoints.
- If you truly must stop mid-build (tool outage, missing credentials), run `$RATCHET pause --reason "…"` and tell the user why. To end your turn only while background reviewers or sub-agents finish, use `$RATCHET wait --for "…" --minutes N` instead (see "Waiting on background work").

## Recovering / resuming

Any time you're unsure where things stand, run `$RATCHET status` then `$RATCHET next`. Relay `status` to the user in your own plain words and show `$RATCHET plan-summary` at the plan approval stop; when the run is blocked, put the quoted reason and the lettered options (`options` in `next`) to the user as a question, and when it also carries an `accept_note` line, show that too, as its own plain line after the options, never as a letter. Never show the user raw JSON or ask them to type a command. A new session picks up from `state.json`, because nothing lives only in your context.
