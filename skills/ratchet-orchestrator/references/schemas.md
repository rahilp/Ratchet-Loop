# Ratchet file schemas

All paths are relative to the project root. `<run>` = `.ratchet/runs/<slug>`.

Contents
1. Project layout
2. `<run>/app-scout.json` — written by ratchet-app-scout
3. `<run>/checkpoints.json` — written by ratchet-checkpoint-planner
4. `<run>/tests/CPn.json` — written by ratchet-test-planner
5. `<run>/states/CPn.json` — capture spec for the UI gate
6. UI review JSON — written by the visual / behaviour reviewers
7. Adversarial review JSON — written by ratchet-adversary
8. `.ratchet/config.json`
9. `ratchet.py status --json` / `lanes --json` — director interfaces
10. Hooks
11. Building from a spec tool (OpenSpec, Spec Kit, BMAD)
12. `ratchet.py receipt`
13. CI export

---

## 1. Project layout

```
.ratchet/
  config.json          # loop settings (human_review, adversaries, app url, …)
  learnings.md         # EVERY agent reads this before working
  standards.md         # the written standard the adversaries enforce
  human_log.jsonl      # written by the UserPromptSubmit hook, plus ratchet.py's override audit lines (log_override, section 10) (protected)
  active.json          # which run is active (protected)
  hook-heartbeat.json  # last time each hook fired and via which host (liveness only, never crash state; written by the hooks; see section 10)
  hook-env.json        # the per-user folder and director key file the hooks use, and the role of the session that last ran a command here (written by the hooks only; see section 10)
  hook-env/            # one record per hook run (its start time, and a guard's session role, in the file name) that hook-env.json combines (written by the hooks only; see section 10)
  hook-errors.log      # internal hook errors (hooks fail open)
  hook-crashes/        # per host and hook: empty marker files for its last crash and last clean run since (written by the hooks; see section 10)
  hook-crashes-unsaved.log  # fallback: crashes whose hook-crashes/ marker could not be saved (written by the hooks; see section 10)
  unavailable-reviewers.json  # providers that just failed (quota, auth, timeout) and until when; skipped for the TTL
  viewer.json          # live viewer server: url, port, bind, pid, token (written by `view --serve`)
  runs/<slug>/
    state.json         # gate state — written ONLY by ratchet.py (protected). Optional field `hooks_waived`:
                       #   {at, by, prompt} = the user chose to build without hooks (see section 10)
                       #   Optional `hooks_waive_n` (int): incremented whenever a hooks-waive director token is used
                       #   and whenever `hooks_waived` is auto-cleared; folded into the hooks-waive director-token
                       #   payload, so that token is single use and a spent one is dead
                       #   Optional `wait`: {reason, set_at, until, session, minutes}, written only by
                       #   `ratchet.py wait` (section 10, "Waiting on background work")
    prompt-chats.jsonl # appended by the prompt hook while no chat owns the run: {at, session}; the next command
                       #   that changes the run makes the first matching chat the owner (section 8)
    stop-blocks.jsonl  # appended by the stop hook: {at, phase} per refused stop, {at, reset} when one is allowed
                       #   (its count of stops without progress; the hooks never write state.json, section 8);
                       #   a stop allowed by a live `wait` adds no line
    app-scout.json
    checkpoints.json
    tests/CP1.json …
    states/CP1.json …  # UI capture specs
    reference/         # prototype.html or reference screenshots; spec-source.json when built from a spec (section 11)
    reviews/           # scratch area where reviewers write JSON
    evidence/CP1/…     # logs, screenshots, reviews archived by ratchet.py (protected)
    viewer.html
    viewer-data.json   # what the viewer shows; its `hooks` key is the hooks object of section 10 (incl. `waived`)
DESIGN.md              # design system (path configurable)
```

## 3. checkpoints.json

Every plan carries a top-level `objective`: who the result is for, what they want, what done means to them, and
what is deliberately out of scope. `plan-submit` refuses a plan with no `objective`, or with any of its four
parts empty, naming the missing part. `plan-summary` prints it first, before the list of steps, so the human
sees it at the moment they approve the plan. `plan-extend` (feedback) keeps the approved plan's objective; a
feedback plan that drops or empties it is refused. A plan drafted from a spec (section 11) gets a draft objective
built from the spec's own words (an OpenSpec proposal's "Why" paragraph, a Spec Kit user story, a BMAD
"As a … I want … so that …" line); the planner refines it like the rest of the draft. `users` is always taken
from an "As a … I want …" narrative the spec itself states (OpenSpec, Spec Kit or BMAD alike), never from a
story's title; when no item in the spec states its audience, the draft leaves `users` as a literal
`FILL IN: ...` placeholder instead of inventing one, and `plan-submit` refuses any objective part that still
starts with `FILL IN:`, naming the part, so the planner or user must fill it in before the plan is approved.
A run whose plan was approved before this field existed keeps working with no objective at all — nothing about
it is required retroactively. `ratchet.py brief CPn --role <role>` prints this same objective text, then that
role's own standing rules; every sub-agent's spawn prompt starts with its output instead of the orchestrator
writing the objective by hand. This is enforced only on Claude Code: the guard hook refuses (exit 2) a
`ratchet-<role>` sub-agent (`Task`/`Agent`, `subagent_type` matching `ratchet-<role>` with or without a plugin
prefix) launched during a build (`building` or `blocked`) whose prompt is missing this objective text, naming the
`brief` command to fix it; a prompt carrying it, however re-wrapped, always passes, and an unreadable plan fails
the check open. Codex, Gemini and Copilot give hooks no way to see a sub-agent launch at all, so this check is not
enforced on those three; it is documented here, not built there. For the planner, `brief` also ends with a
"What earlier work says" section, built by the engine itself from records already on disk: recent
`.ratchet/learnings.md` bullets, the findings earlier (non-active) runs saved for later that nobody accepted yet,
and the limits the user already accepted, most relevant to the new feature first then newest, each part capped
with a count and a pointer to the full file (`.ratchet/learnings.md`, or a run's `state.json` under
`.ratchet/runs/`). The same section also lists the related recorded specs for the parts being changed — OpenSpec
specs under `openspec/specs/` (including Ratchet's own running records), finished Spec Kit features and done
BMAD stories — each with its title, a one-line purpose and its path, ranked and capped together with the rest;
a project with no specs at all gets no such list, and the planner still reads in full the specs it actually
touches. A project with no earlier work of any kind gets one plain line instead.

```json
    "done_means": [

    ],
    "out_of_scope": [

      "Changing a decision after it was made"
    ]
  },

  "assumptions": ["Only direct managers can approve"],
  "checkpoints": [

      "summary": "An empty Approvals page that managers can open from the sidebar.",

        "Employees who are not managers do not see the link"

      ],

        "command": "pnpm vitest run src/server/leave/__tests__/approvals.cp1.test.ts --reporter=junit --outputFile=$RATCHET_TEST_REPORT",
        "report": "junit"

      "notes": "Reuse the PageHeader component."
    }

```

Rules enforced by `ratchet.py plan-submit`:
- top-level `objective`: `users`, `goal`, `done_means` (non-empty list) and `out_of_scope` (non-empty list) must
  all be present and non-empty; a plan missing any part is refused, naming the missing part
- no objective part may still start with `FILL IN:` (the draft's placeholder for an audience or part it could
  not fill in from the spec); a plan with one is refused, naming the part
- ids are `CP1…CPn`, in build order; `depends_on` may only point backwards
- `title` ≤ 8 words; `summary` one plain-language sentence
- `done_when` non-empty, written so a non-engineer can check it
- `gates.adversarial` is always `true`
- `gates.behavior:false` requires `behavior_skip_reason`
- `gates.ui:true` requires `ui_scope` and ≥1 `ui_states`
- `gates.behavior:true` requires `tests.command` (and `tests.files`)
- `tests.report`, if set: `junit` | `json` | `none`; `none` requires `tests.report_reason`. Locked at approval with the rest of the plan. With `junit` or `json`, `red` and `behavior` delete any old file at the path they pass in `RATCHET_TEST_REPORT`, run the command, then read each case's result from the file the command wrote there: JUnit XML (`<testcase>` with `<failure>` = failed, `<error>` = crashed, `<skipped>`), or `{"cases": [{"id": "CP1-T01", "status": "passed|failed|error|skipped", "message": "..."}]}` (the format is told apart by content). A case's result is found by its id in the JUnit `name`, `classname` or a `<property>` value, or the JSON `id`, in any of the spellings CP1-T01, CP1_T01, cp1_t01 or CP1T01 (case-insensitive, no digit run on either side). A leading UTF-8 byte-order mark is ignored. A missing or malformed report fails the run. At `red` every planned `code` case must have a result, no two of its results may have the same name, none may crash (`error`) or be skipped, and at least one must fail a check. At `behavior` every planned case must pass, and any planned case skipped now that was not skipped at the red run fails the gate (other entries in the report are ignored). Config `checks` keep the exit-code rule. With `none`, or on a plan with no `report` key (for example one approved before this field existed), the exit code alone decides, and `plan-summary` (a `Tests:` line), `status` and `next` (`test_check`) say so, with the reason for `none`.
- After the red run a test file may only grow (every non-blank line kept, in order), and each planned test is frozen: it can't change after its first run. In a Python file each planned case id belongs to the innermost `def` or `class` around it (or the one right after its comment line); that definition, with its decorators and its enclosing classes' decorators, must be unchanged (compared with `ast`), and no later definition (a `def`, `class` or assignment in the same scope) may reuse its name. Only an id found in no definition at all (for example only in a header comment) makes the file's existing top-level code the test: each old top-level statement must stay unchanged and in order, and no old `def` or `class` name may be defined again; an id that names a test function and also appears in a header comment freezes just that function. New tests and helpers may be added to a Python file anywhere outside the planned tests. Any other test file that holds a planned case id (in any usual spelling) is append-only after the red run: the file as it was at the red run must be an exact prefix of the file now, so new tests and helpers may only be added at its end (after the file's last line, including any closing `}` or `end` of a surrounding class or `describe`, so a new test goes in a new block there), and no line added there may declare a planned test's name again (its quoted name, in any quotes, or the identifier holding the id, such as Go's `TestCP1T01`), since in some languages a later definition with the same name replaces the earlier one. No language syntax is parsed, so brace style, attributes, multi-line strings and comments make no difference. Outside Python a planned case id must still sit on the line that opens its test, outside any comment: in the test's name (`it("[CP1-T01] ...", () => {`, `func TestCP1_T01(t *testing.T) {`, any usual spelling) or on an annotation directly above it (`@DisplayName("[CP1-T01] ...")`). `tests-written` and `red` refuse, with a plain message, an id that outside Python files appears only in a comment, because the per-test report finds a case by its test's name. Breaking a freeze rule counts as weakening the tests: the gates stop, naming the file and its planned tests, until the user approves the change (`approve-changes`). With `tests.report` set, two results with the same name for one planned case also fail `red` and `behavior` ("planned case CP1-T01 ran more than once"); differently named results for one case (parametrized tests, subtests) are fine, and each must pass. Accepted limit (the user's decision): this is a structural check, not a proof; a deliberate same-user edit that gets past it (for example code outside a planned test that changes what the test calls) is not caught.
- optional `ui_skip_reason` shown in the viewer when `ui:false`
- `risk`: `low` | `normal` (default) | `high`, which picks the adversarial reviewer set from config `review_depth`. A `high`-risk checkpoint also needs `risk_reason`, a plain sentence naming which users could be harmed and how: `plan-submit` refuses a new plan carrying a `high`-risk checkpoint with an empty or missing `risk_reason`, naming the checkpoint; `plan-extend` applies the same check only to the checkpoints it appends, so a plan approved before this rule existed keeps its own old high-risk checkpoint(s) working untouched
- optional `reviewers`: an explicit list of reviewer ids that overrides `review_depth` for this checkpoint
- on a run built from a spec (section 11): every spec task ref is in some checkpoint's `spec_refs`, every scenario or acceptance-criterion ref has a test case with that `spec_ref` (or is in `spec_refs` of a UI-gated checkpoint), every ref exists in the spec, and anything left out is in the top-level `spec_unmapped` as `{"ref", "reason"}`

Feedback (EXTEND mode) only appends new checkpoints with the next free ids; completed checkpoints are never edited or removed. `plan-extend` and `approve-changes` both call `validate_plan` on the plan before trusting any checkpoint has an id, and both register a hand-appended new checkpoint into `state.json` the same way (or refuse together with the same "Plan invalid" / "Test plans missing for new checkpoints" message) — a checkpoint added to `checkpoints.json` by hand and accepted through `approve-changes` is registered exactly like one `plan-extend` appended, never left to crash later with a `KeyError`.

## 4. tests/CPn.json

```json
{
  "checkpoint": "CP2",
  "strategy": "Service-level tests against the leave module with an in-memory DB",
  "fixtures": ["manager Mia with direct report Eli", "Eli has 10 days balance"],
  "cases": [
    { "id": "CP2-T01", "title": "Manager approves a pending request",
      "given": "Eli has a pending 2-day request", "when": "Mia approves it",
      "then": "status is APPROVED and Eli's balance is 8", "layer": "code", "edge": false },
    { "id": "CP2-T04", "title": "Manager cannot approve someone outside their team",
      "given": "Zoe reports to another manager", "when": "Mia approves Zoe's request",
      "then": "a Forbidden error is returned and nothing changes", "layer": "code", "edge": true },
    { "id": "CP2-T07", "title": "Approve button shows a spinner while saving",
      "layer": "browser", "edge": false,
      "note": "Visual/interaction — checked by the UI gate behaviour reviewer, not in code" }
  ]
}
```

On a run built from a spec, a case carries `"spec_ref": "<scenario ref>"` (or a list) for the scenario or acceptance criterion it proves.

A case also carries an optional `"proves": [1, 3]`: the 1-based line numbers of the plan's top-level `objective.done_means` this case proves. `plan-submit` refuses any number that is not really a done_means line (not 1-based, or past the end of the list), naming the case; `plan-summary` lists any done_means line that no case's `proves` names, as a heads-up, without refusing the plan. `ratchet.py receipt` lists every done_means line next to the case(s) that prove it, or "no test linked" when none does (section 12). A plan with no `proves` fields at all, or no `objective` at all, keeps working: the field is optional, like `spec_ref`.

`layer`: `code` (unit/integration/API/CLI — MUST be automated and tagged with its ID in the test name) or `browser` (only checkable by clicking — handed to the UI gate). `ratchet.py tests-written` and `ratchet.py behavior` fail if any `code` case ID is missing from `tests.files`, and `tests-written` and `red` also fail when, outside Python files, an ID appears only in a comment rather than on its test's opening line (section 3); `red` names an ID that is in no test file at all as not present; with `tests.report` set (section 3), `red` and `behavior` also require each one's own result in the report.

**One flaky failure doesn't cost an attempt.** When `ratchet.py behavior CPn`'s run of `tests.command` fails (exit code, or a planned case failing in the report), and this step's gate (`gates.behavior`) has not yet used its one-time allowance (`flaky_used`, bool, state.json, starts unset), Ratchet re-runs the same command once, immediately, before counting anything. If that re-run passes clean, the gate passes marked `"flaky": true` (`status --json`'s `gates.behavior`, and `rounds[]`/final-review text say so), `flaky_used` is set so this step gets no second chance, and `gates.behavior.attempts` is left exactly as it was before this call — the retry spends nothing. If the re-run fails too, this call still counts as exactly one attempt (never two) and is reported as an ordinary failure, not flaky: a second flaky-shaped failure in the same step, or two failures in a row, is never forgiven. Both the failing and the passing run's own log are kept in `evidence/CPn/` (`behavior-NN.log` and `behavior-NNb.log`), where `NN` is `gates.behavior.runs` (int, state.json, starts unset and increments by one on every call to `ratchet.py behavior CPn`, including a flaky re-run and a later attempt after a genuine failure). Unlike `attempts`, `runs` never decrements when a failure is forgiven as flaky, so it is a count of invocations, not of attempts charged against the step: a later invocation can never reuse, and so overwrite, an earlier invocation's own log file. `flaky_used` likewise stays set once a step has used its one-time allowance, even across later behavior calls for the same step, so a step is never marked flaky more than once. The full regression run at `ratchet.py complete` (`cfg.regression_command`, section 8) gets the same one-time allowance, but tracked for the whole RUN, not per step (`regression_flaky_used`, bool, state.json): once any step's regression run has used it, a later step's regression failure is never retried.

## 6. UI review JSON

Each reviewer writes one file (only that reviewer may write it); `ui_review.py` merges them into `combined.json` (only the script may write it).

```json
{
  "reviewer": "visual",
  "checkpoint": "CP1",
  "verdict": "FAIL",
  "invalid_reason": null,
  "scope": "Sidebar link, page header, empty state only",
  "differences": [
    { "id": "V1", "state": "empty", "severity": "major",
      "location": "page header, top-left, ~24px below nav",
      "description": "Title is ~20px in the app vs ~28px in the reference (about 70% of the size)",
      "expected": "28px semibold per DESIGN.md heading-lg", "actual": "20px regular",
      "fixable_in_code": true, "suggested_fix": "Use <PageHeader size='lg'>" }
  ],
  "notes": "Proportions judged against each screenshot's width."
}
```

- `verdict`: `PASS` | `FAIL` | `INVALID` (screenshots are not the same state/section — orchestrator must recapture)
- `severity`: `blocker` | `major` | `minor` | `nit`
- ratchet.py ignores the self-reported PASS/FAIL and recomputes: any difference with `fixable_in_code: true` blocks (nits too, unless `ui_block_on_nits:false`).

`combined.json` = `{ "checkpoint", "fingerprint", "compared": {"spec_sha256", "scope"}, "reviewers": ["visual","behavior"], "verdict", "invalid_reason", "differences": [...all, each with "reviewer"] }`. `compared` records what the round compared: the hash of `states/CPn.json` (stamped into the capture manifest by `capture.mjs`) and the scope given to the reviewers. `ui-record` only accepts a `combined.json` whose real location (symlinks and `..` resolved) is directly inside the round's own folder, `reviews/CPn/round-NN/`, where NN is one more than the UI rounds recorded so far; a file written anywhere else, copied in from an earlier round's folder, or linked in from outside is refused with a message naming the right folder. After a FAIL round both are frozen: `ui-record` refuses a later round that compared something else until the gate passes, unless the user agreed to a change (`ask ui-respec CPn`, then `ui-respec CPn`). `ui_review.py` (`review` and `combine`) signs `combined.json` the same way as an adversarial review (see Review signing below), with the UI round's own secret in `RATCHET_HOME/review-keys/` and with `<CP>/ui/round-NN` in place of the nonce; `ui-record` refuses a `combined.json` that is unsigned or whose signature does not match, and deletes the secret only after the recorded round is saved. `review` opens the round's secret before any reviewer runs, and `stage` opens it too (outside a Ratchet run, or for a step with no UI gate, `stage` stages without a round). `review` signs each role file it writes (`visual.json`, `behavior.json`, label `<CP>/ui/round-NN/<role>`). `combine` signs only inputs whose origin it can check: role files `review` signed for this round, or `visual.json` / `behavior.json` directly in this round's folder whose writer the guard recorded, `reviewer` matching the file name, each role once (the same writer rules as adversarial reviews, with `ratchet-visual-reviewer` / `ratchet-behavior-reviewer` as the owners). Its `--manifest` (required inside a run) must sit under `reviews/CPn/` and be the one `review` or `stage` last wrote for this round: both stamp the manifest with the current `fingerprint`, `review_scope` and a fresh random `stamp`, keep that stamp as the round's `manifest_stamp`, and sign the manifest (label `<CP>/ui/round-NN/manifest`); a manifest typed, copied or edited by hand, or an older one, is refused. Role files `review` signs carry `manifest_stamp`, and the guard's writer record for `visual.json` / `behavior.json` notes the round's `manifest_stamp` when it was written, so a role file written before the manifest was stamped again is refused. Outside an active Ratchet run (no `.ratchet` folder, or no active run) `review`, `stage` and `combine` still work for an ad-hoc comparison but sign nothing: role files and `combined.json` carry `"unsigned": "<why>"`, and `ui-record` refuses them. A role accepted without confirmation (Codex, Gemini, Copilot, or hooks waived) is listed in `combined.json` as `"unconfirmed": ["<role>: not independently confirmed (<reason>)"]`, covered by the signature, and `ui-record` copies it to the UI gate's `unconfirmed`. Any other input, a step with no open UI gate, or a secret that can't be created makes `review` / `combine` exit non-zero with a plain message and write nothing. A correctly-located `combined.json` is also capped at `MAX_REVIEW_BYTES` (8 MiB): one over the cap on disk, or one that grows past it while being read, is refused outright and never read into memory, naming the limit.

## 7. Adversarial review JSON

```json
{
  "reviewer": "codex-correctness",
  "lens": "correctness",
  "vendor": "openai",
  "checkpoint": "CP2",
  "fingerprint": "<output of ratchet.py fingerprint → id>",
  "round_nonce": "<the nonce printed by ratchet.py reviewers CPn for this round>",
  "files_reviewed": ["src/server/leave/approve.ts", "src/server/leave/types.ts"],
  "verdict": "CHANGES_REQUESTED",
  "findings": [
    { "id": "A1", "severity": "major", "file": "src/server/leave/approve.ts", "line": 42,
      "rule": "standards.md §3 — services never import from app/",
      "kind": "service-imports-app",
      "description": "approve.ts imports a React component type",
      "fix": "Move the DTO type to src/server/leave/types.ts",
      "user_impact": "a manager's approval silently fails because the build pulls in browser-only code on the server" }
  ]
}
```

`reviewer` must be the reviewer id from the config roster, because adv-record matches reviews to the required list by id. `fingerprint` is **required**: reviews of other code are rejected. `round_nonce` is **required** and must match the round opened by `ratchet.py reviewers CPn`, so a review from an earlier round, or one written without launching a reviewer, is rejected. `files_reviewed` lists the files the reviewer actually read; a review with no findings must list at least one of the files this checkpoint changed, or it is rejected. Each review file must sit directly inside the round's own folder, `reviews/CPn/adv-round-NN/` (printed by `ratchet.py reviewers CPn`, and `output_dir` in its `--json`); its real location is checked with symlinks and `..` resolved, so a file written anywhere else, copied in from an earlier round's folder, or linked in from outside is refused. A review file written less than `min_review_seconds` (config, default 20) after its round opened is rejected as too fast to be real. A correctly-located review file is also capped at `MAX_REVIEW_BYTES` (8 MiB): one over the cap on disk, or one that grows past it while being read, is refused outright and never read into memory, naming the limit. Other-provider reviews are written by `external_review.py`, which stamps `reviewer`, `vendor`, `fingerprint`, `round_nonce` and `files_reviewed` itself. **Review signing.** `ratchet.py reviewers CPn`, when it opens a round, creates that round's secret in `RATCHET_HOME/review-keys/<hash>.json`, the hash taken over the project folder, run slug, step, kind, round number and the round's own identity (an adversarial round's `nonce`; for a UI round, the run's `created_at` and the UI gate's `rounds_recorded`, a count `ui-record` raises with every recorded round and an unblock never resets), so a record left by an abandoned run at the same path, or by an earlier round, never speaks for a later one (`{"secret": "<64 hex>", "writers": {"<file name>": {"host", "agent", "at", "confirmed", "other_writer", "manifest_stamp"}}, "manifest_stamp"}`, the two `manifest_stamp` fields for UI rounds only, folder mode 700, file mode 600, changed only through `update_record`; an unreadable one is replaced by a fresh one when the round is opened). It is never printed and never written into the project, and it is deleted only after the state that records the round, or replaces it with a new round, is saved, so a record that fails before its save can simply be run again. When it can't be created, `reviewers` says so plainly: another Ratchet command is using it (try again), or the folder can't be written. `external_review.py` adds `"signature": {"alg": "hmac-sha256", "by": "external_review.py", "value"}`: HMAC-SHA256 with that secret over the review's canonical JSON (every field but `signature`, keys sorted, no spaces, non-ASCII characters escaped), the round nonce and the fingerprint, each on its own line. `external_review.py` checks that the round's secret exists before it runs the reviewer, and replaces any lone surrogate in the reply (a cut-off emoji escape) with U+FFFD before it signs; `adv-record` and `ui-record` do the same to a review after checking it. `adv-record` checks the signature with `hmac.compare_digest`; a signature that doesn't match (an edited file, or one signed for another round or step) is refused naming the file, and a signed review whose round has no secret any more is refused saying so. Only a `signature` shaped like one the scripts write (`alg` `hmac-sha256` and a 64-character lowercase hex `value`) is checked; any other `signature` field is incidental and the review is checked like an unsigned one. A review without a signature counts only for a host sub-agent reviewer (kind `agent`), and only as follows. The guard hook records, in `writers`, every write-tool write into an open round's folder (it does not see shell writes). On Claude Code, which names the acting sub-agent, a write by `ratchet-adversary` is `confirmed` and the review counts. A write by anyone else (the main session, or another sub-agent) is recorded as not confirmed, with `other_writer` naming who, and stays so even if the reviewer writes the file again; that review, and one with no writer record at all (written through the shell, or by hand), is refused as unsigned with the reason, telling reviewers to write with the Write tool. On Codex, Gemini and Copilot, whose hooks don't name the sub-agent, and whenever the user waived the hooks, Ratchet can't tell who wrote the file: an unsigned file in a host reviewer's slot counts whether or not a writer was recorded, even one typed by hand into the round folder with the right nonce and code version. It is marked: its round's `verdicts[].origin` says "not independently confirmed" with the reason in `verdicts[].unconfirmed_because`, and the gate's `unconfirmed` list holds `<reviewer>: not independently confirmed (<reason>)`, which `status` (text and `--json`) and the viewer show. When the guard can't record a writer (its round's record busy or damaged, or an error), it still lets the write through and logs `<time> <host> guard: ReviewWriterNotRecorded: <file>: <detail>` to `.ratchet/hook-errors.log`; a refusal for that file then says so. Anything else is refused as unsigned. This protects against a different process on the same machine that can't read `RATCHET_HOME` (the guard keeps agents out of it), not against the operating system.

A reviewer approves by returning `"findings": []`. Which findings block is set by config `blocking_severities` (by risk), `scope_later_rounds` and `converge_after_round`; findings that don't block are recorded for the final review (`ratchet.py deferred`), never silently dropped. If a finding is wrong, the fixer writes a rebuttal in `fixes.md` and the NEXT adversary round decides whether to withdraw it.

**Later rounds cost less.** Three things make the loop converge instead of costing more with every round:
- **Fewer reviewers after round 1.** `checkpoints.CPn.adv_round.narrowed` (bool, state.json) marks whether the round `reviewers` just opened was narrowed. Round 1 always asks every lens. When the round being replaced was RECORDED (it blocked) and was itself not narrowed, `resolve_reviewers` narrows the next round to only the lens(es) with a still-open BLOCKER or MAJOR finding (`_open_blocking_lenses`; a lens whose only open finding was minor, or that approved outright, is left out). If that narrowed round's fix still leaves a blocker or major open, the round after it goes back to the full set (`narrowed` is false again) instead of narrowing further, so a stuck finding gets every lens looking again, not just the one that already looked.
- **A duplicate slot runs once.** `resolve_reviewers` collapses a slot whose resolved pick is the same company, model and lens (`_dup_key`) as a reviewer an earlier slot in the same round already chose; the slot produces no entry (it never falls back further). `adv-record`'s approval message (`all N reviewer(s)`) counts `rnd["reviewers"]` after this collapse, so it always names the real, distinct number of reviewers, never the configured slot count.
- **A round nobody reviewed is free.** When `reviewers CPn` replaces an open round that was never recorded (the code changed again before `adv-record` ran) AND that round's own folder (`reviews/CPn/adv-round-NN/`) holds no review file at all, the new round's opening does not add to `gates.adversarial.attempts` or `adv_rounds_total` (the increment for opening it is refunded straight back, floored at zero): the replaced round never cost anything. A round where at least one review was written to its folder still counts toward both caps, even though `adv-record` was never run on it.
- **The diff a reviewer sees is prioritized by what changed since the last round it actually reviewed.** `checkpoints.CPn.adv_round.prev_round_tree` carries the previous round's fingerprint forward as the new round's baseline (`null` for round 1). When a round is replaced for free (above), its own `prev_round_tree` is carried forward instead of its fingerprint, since nobody has reviewed that discarded round's code either. `external_review.py`'s `collect_diff` puts every file changed since `prev_round_tree` first, then the rest; when `MAX_DIFF` still has to cut content, the prompt names the specific files left out rather than only a byte count, so a reviewer always sees what changed since the last round it was actually shown first, and knows by name what it didn't see.
- **Minors stop blocking from a configurable round.** Config `converge_after_round` (default 2): from round `converge_after_round + 1` on (round 3 by default), `split_findings` defers every minor finding regardless of scope, instead of only the ones outside `scope_later_rounds`'s changed-file scope. Blocker, major and unknown-severity findings are unaffected: they keep blocking at every round, whatever `converge_after_round` is set to.
- **A reply cut off mid-answer is retried once, and falls back only its own slot.** `external_review.py`'s `_review` tells a reply cut off mid-JSON (an opening `{` or a `"findings"` key with no matching close) apart from a reply that was never JSON at all (a plain error, no `{` anywhere): a cut-off reply is retried once, immediately, before anything is held against the reviewer. If the retry is also cut off, only that reviewer's own id is marked, by writing `<reviewer>.cutoff.json` into the round's own folder (`reviews/CPn/adv-round-NN/`) — never `mark_unavailable`'s `unavailable_ttl_hours` record, so the provider's other reviewers (a different lens, same CLI) keep running and `reviewer-status` still shows this one available. `ratchet.py reviewers CPn`'s same-round branch reads that marker (alongside the usual `reviewer_availability` check) to give just that slot to the next alternative (`resolve_reviewers(..., exclude=<round's cutoff ids>)`), and never re-resolves or discards a slot whose review file already exists in the round's folder. A genuine failure — not installed, signed out, out of quota, or a timeout (never retried: one timeout is enough) — still goes through `mark_unavailable` exactly as before.

`user_impact` (optional per finding, string): who is hurt and how, in normal use. Every reviewer's prompt opens with the plan's objective and asks for this alongside `severity`, so findings stay aimed at the project's real users rather than a case no one would hit. `adv-record` checks it before `split_findings`: a `blocker`, `major`, or unknown-severity finding (any severity not in the known minor set) with no `user_impact` (missing or blank) never blocks, at any round and any risk — it is written to `deferred-findings.json` with `"deferred_because": "no user impact stated"` and shown at the final review and by `ratchet.py deferred`. A `minor` finding is unaffected by this rule either way; it keeps following `blocking_severities` and `scope_later_rounds` as before, whether or not it carries a `user_impact`. A finding that does carry a `user_impact` is judged exactly as before this field existed.

**Marking a deferred finding fixed (`mark-fixed`).** `checkpoints.CPn.deferred` accumulates one entry PER ROUND that recorded it (never rewriting an earlier round's own entry; `adv-record` only drops that round's own prior entries before appending its own), so the same reviewer/id re-raised in round 2 after round 1 first deferred it leaves two raw entries there, one per round. Every reader that shows "what is still left for later" (`cmd_deferred`, `deferred --json`, and `status`'s final-review count) first groups these by `_finding_key` (`"<reviewer>/<id>"`, or the bare id with no reviewer) and keeps only the entry from the LATEST round for each key; a different finding that merely shares a `kind` and `file` (a different reviewer or a different id) is its own key and is never merged into the one above it. `ratchet.py mark-fixed CPn <ref>="<how>"` (`ref` the same bare-id-or-`reviewer/id` form `accept-finding`/`triage` use) adds a `"fixed": {"round": <n>, "how": "<the text given>"}` record directly onto that key's own deferred entry in state (the latest round's own copy), and the grouped readers above exclude any entry carrying one: it then shows under `deferred`'s separate "fixed later in the run" section instead of under "left for later", and no longer counts toward the final-review left-for-later count. It is refused outright, with nothing recorded, unless BOTH hold: (1) the finding's own `file` has changed between the baseline round for this key and the code on disk now (`changed_files` against that baseline round's own recorded `gates.adversarial.rounds[].fingerprint`) — the baseline round is the HIGHEST of every round among this key's own raw deferred entries AND every recorded adversarial round whose own `open-findings.json` (read fresh off disk with `_read_findings_file`, never only this checkpoint's `deferred` list) lists that same key, so a round that re-raises the finding as BLOCKING -- never added to `deferred`, since a blocking finding never is -- also becomes the baseline, and that round itself can never serve as its own proof; and (2) some later recorded round's own fingerprint, compared against the code on disk now, shows that same file unchanged (i.e. a round already reviewed the file in the form it is in now) — the fixed record's `round` is that round's number, the earliest later round for which this holds, not necessarily the globally latest round recorded for the checkpoint. It is also refused when `ref` names a finding that was accepted (`accept-finding`, a separate decision; the message says so and points there) or names no deferred finding of this checkpoint at all.

**Accepting an open finding.** When a round blocks, `evidence/CPn/adversarial/round-NN/open-findings.json` lists the findings still open (blocking). Its ids are not always the bare ids a reviewer wrote: `adv-record` first runs every reviewer's findings through `_dedupe_finding_ids`, so a finding with no `id`, or one that repeats an earlier finding's `id` from the SAME reviewer, is rewritten to a synthetic one (`<id-or-'F'>-dup<n>`; the first of each id is left untouched). Take the ids to accept from this file, never from a reviewer's raw output: a reviewer file with two findings both called "A1" means the second one is really `A1-dup2` by the time it can be accepted. The user, and only the user, can accept named ones instead of spending another round: `ratchet.py ask accept-finding CPn F1,F2` (ids from that file; refused when the round didn't block, when an id is unknown, or when an id was only ever a deferred/minor finding of that round, never blocking, and ALSO refused, before anything is asked, when the code has changed since this round's own fingerprint was captured (refused with "the code changed since this review round; run a new review round first"), excluding `.ratchet/` and any chat transcript recorded since the round opened, the same exclusions `complete` applies to its own gates) stores `"pending": {"action": "accept-finding", "mode": "CPn", "ids": [...], "round", "fingerprint", "asked_at", "session", ...}` (the same shape as every other `ask`, see Controls below) and prints the question naming each finding, with the one reply that accepts them: exactly `accept: <reason>` (case-insensitive on the word `accept`, the reason itself kept verbatim) as the user's own FIRST reply after the question, in the chat that owns the run; no listed-yes phrase, letter or other wording accepts anything here. An id (`F1`) is matched by its bare id unless two reviewers of the same round reported the same id, in which case a bare id is ambiguous and is refused (naming the colliding reviewers); the qualified form `reviewer/id` (e.g. `codex-correctness/A1`) is never ambiguous and always names exactly one finding. `ratchet.py accept-finding CPn` then reads that reply (`_require_pending`, the same owner-chat and transcript rules as every approval), re-checks the code hasn't changed since the round (the same refusal as `ask accept-finding`, in case it changed in between), and, for each accepted id, builds an entry (`"accepted": true, "reason": "<the user's reason>", "accepted_at", "accepted_by": "human", "round"`) for the checkpoint's own `deferred` list. From here the write order is simple and deliberate (no "heal from state" machinery): (a) `.ratchet/learnings.md` gets one line per accepted entry FIRST, keyed by a marker unique to this run, checkpoint, round AND reviewer/id (never just reviewer/id, which repeats across rounds and checkpoints, and bare reviewer/id alone used to collide and silently drop a later, genuinely different acceptance), skipped when that exact marker is already present, so a retry after an earlier crash never duplicates it; (b) the round's own `deferred-findings.json` is written WHOLE (never appended) from the updated list, next; (c) the round's own record is marked (`gates.adversarial.rounds[N].accepted`, found by the round number stamped on that entry, not by its position in the list, so a round `reviewers` opened and then replaced before recording still marks the right one) and state is committed together (`save_state`, standards #12: the one atomic, authoritative write), only after (a) and (b) have succeeded; (d) `accept-finding` rewrites its own round's `open-findings.json` last of all, now only a mirror of what state already recorded. Because (a) and (b) run BEFORE the state commit, a crash before (c) leaves at most a harmless extra learnings.md note or an uncommitted `deferred-findings.json` write: the accept itself never happened (state still shows every id open), so a plain retry (the question is still pending) starts clean and finishes once; a crash can never leave a COMMITTED accept without its own notes, because both are always written first. Accepting an id already accepted earlier in the same round is refused as already closed. State, not `open-findings.json`, is the one authoritative record of what was accepted: the file is only a mirror. Only `ask accept-finding` and `accept-finding`'s own "already accepted" check (`_adv_open_findings`) compute what is open, as the file's contents minus whatever `state.json` already records accepted for that round, so a stale copy left by a crash between (c) and (d) is never mistaken for a reopened finding there, and a retry after such a crash is always refused as already-accepted rather than recording a second acceptance; `plan-summary` and `deferred` never compute this. `status` and `next` do read `open-findings.json` for it, but only read-only, through `_blocked_accept_note` (below), to decide whether to show the accept_note line; neither ever writes evidence or learnings.md from it. `status`, `status --json`, `deferred` and `lanes` are read-only: they never write evidence or learnings.md (no heal runs from them). When no open finding of that round remains, the adversarial gate is marked `passed` for that round's own fingerprint (not a freshly recomputed one, so a chat reply recorded while resolving this never itself reads as a code change) and `complete` accepts it without another round; accepting only some leaves the gate exactly as it was, still blocked on the rest. If the run was `blocked` only because of this checkpoint's own adversarial round limit, OR the run-wide round cap (`next`/`status` name this with their own plain line, never a lettered option, pointing at `ask accept-finding`; running it directly while blocked there works the same way), accepting every open finding resolves it through the same shared `_unblock` helper `human-approve` uses: phase returns to `building` (or the next review phase), the current checkpoint's own failing-gate attempt counters reset, the run-wide round budget resets to 0 when that cap was the cause ("the user chose to continue: the run's budget starts again"), and any stored `choice_allow['unblock']` (from an earlier `ask choice` pick) is consumed so a later, unrelated block can never be unblocked by that same stale pick without a fresh question, so `complete` works without a second question when `next: ratchet.py complete CPn` is actually printed (it is printed only when `complete` would really run now; otherwise the message names the real block or says to run `ratchet.py next`). Any other block reason is left exactly as it was. A later round (opened because the fingerprint changed, i.e. the code changed) follows the normal rules again: nothing accepted here exempts a finding it reintroduces, or any new one. `next_action`'s `accept_note` (carried into `ratchet.py next`'s JSON and `status --json`, and printed as its own line by plain `status`) is the only place this is offered, and `_blocked_accept_note` computes it in a fixed order: it is `null` unless `blocked`, the block is this checkpoint's own round limit or the run-wide cap, and the current checkpoint has a recorded round — and even then, `null` unless that round still has open findings for the current code (a presence check against the round's own open findings, state-filtered, always runs FIRST, before anything else, so neither line below is ever printed about findings that do not exist, for example an approved round or one already fully accepted). Only once that presence check passes does it pick one of two lines, never both: when the code changed since that round, "the last fix changed the code, so these findings need a fresh look; raise the limit (A) for one more round"; otherwise, "you can also accept open findings yourself: the agent asks with `ask accept-finding`, and only your reply `accept: <reason>` closes them." `blocked_options`'s lettered choices never include either of these: `_blocked_accept_note` computes this line separately from `blocked_options`, and nothing about picking a letter can ever produce it.

**Raising a step's round limit.** `blocked_options` (state.json's `blocked_reason`, read against `checkpoints.CPn.gates.adversarial.cap_raised_to`) lists what the user can do at a block: at this checkpoint's own round limit block ("N adversarial rounds used without approval", or "adversarial review still has N finding(s) after R rounds"), the lettered options are, in order: simplify the step, change the step so the review notes no longer apply, stop here and keep what's finished, then — only while `cap_raised_to` is still unset for this checkpoint — raise the limit. At the older, run-wide cap block ("Run-wide adversarial round cap reached"), the order is simplify, stop, raise (that cap's own raise is the pre-existing config-change-plus-`approve-changes` path, untouched by this rule, since it is not scoped to one step). `ratchet.py ask raise-limit CPn` stores `"pending": {"action": "raise-limit", "mode": "CPn", ...}` (the same shape as every other `ask`) and is refused outright, before anything is asked, when `cap_raised_to` is already set for that checkpoint: a step's raise is offered, and spent, at most once, ever. It prints the question with the one reply that raises it: exactly `raise: <reason>` (case-insensitive on the word `raise`), as the user's own FIRST reply after the question, in the chat that owns the run; no other reply, letter or phrase raises anything, and a reply recorded in a different chat is refused the same way an `accept-finding` reply in the wrong chat is. `ratchet.py raise-limit CPn` then reads that reply (`_require_pending`, the same owner-chat and transcript rules as every other approval), sets `checkpoints.CPn.gates.adversarial.cap_raised_to` to one more than the cap currently in force for this step (its own `cap_raised_to` if already set — which `ask raise-limit` already refused, so in practice always `cfg.max_adversarial_rounds` the first and only time this runs), appends the user's reason to `.ratchet/learnings.md`, and, when the block was this checkpoint's own round limit reason, unblocks the run through the same shared `_unblock` helper `human-approve`/`accept-finding` use. From then on, `cmd_reviewers` and `cmd_adv_record` compare this checkpoint's `gates.adversarial.attempts` against `cap_raised_to` (once set) instead of config's `max_adversarial_rounds`, so a later `ratchet.py config --set max_adversarial_rounds=...` can change every OTHER checkpoint's limit, and this one's limit before its raise, but never lifts this checkpoint's own already-raised cap. A reply typed in another chat, or any reply not in the exact `raise: <reason>` form, raises nothing and leaves `cap_raised_to` unset, so the question (and the raise) can still be asked for again later. `_adv_round_cap` (used by `cmd_reviewers`/`cmd_adv_record` to compare against `attempts`) is `cap_raised_to` (or config's `max_adversarial_rounds` while unset) PLUS `gates.adversarial.round_limit_grants` (below): `cap_raised_to` is computed from the CONFIGURED cap alone (`_adv_base_cap`), never from `_adv_round_cap`'s own total, so a raise always adds exactly one round on top of config and a check-in round limit grant always adds exactly one more on top of that, in whichever order they happen, instead of compounding on top of each other.

**Simplify/change at the round limit block: reusing check-in's own simplify record for one more round.** At this checkpoint's own round limit block specifically (never the run-wide cap, and never while a soft check-in — see below — is open: the two never coincide, since `reviewers` refuses a further round while a check-in sits open, so this hard cap is only ever reached after any earlier check-in was resolved), `ratchet.py check-in CPn --decision simplify --why "..."` and `ratchet.py check-in CPn --decision change --why "..."` each grant this step exactly one more review round, reusing check-in's own simplify record (`_adv_block_kind` returning "own") rather than inventing a second mechanism: no user question (the same reasoning as check-in's own simplify — it never lowers the bar, only changes what's reviewed), each refused outright, before anything is recorded, once already used once for this step (`gates.adversarial.round_limit_simplify_used` / `round_limit_change_used`, booleans, each set at most once, ever). A successful call sets its `used` flag, increments `gates.adversarial.round_limit_grants` (int, starts at 0, added to the cap by `_adv_round_cap` above) by one, appends `{"round": <attempts at the time>, "trigger": "round_limit", "decision": "simplify"|"change", "why", "decided_at"}` to `checkpoints.CPn.checkin.decided`, and unblocks the run through the same shared `_unblock` helper `human-approve`/`raise-limit`/`accept-finding` use, with this checkpoint's `adversarial.attempts` preserved exactly as `raise-limit` preserves it (never reset to a fresh budget). `--decision change` with an open check-in instead (the soft trigger, below) is refused, pointing at `--decision simplify` (which already covers narrowing or changing the step there). A lettered "stop" or "change the step" pick, run through the ordinary `ask choice`/`choice`/`human-approve` flow instead of these two dedicated commands, and a bare `human-approve` with no pick at all, never grant a round either way: only `raise-limit` and these two `check-in` decisions ever do.

Each entry in `gates.adversarial.rounds[]` (state.json, one per adversarial round ever RECORDED, i.e. reviewed by `adv-record`, for that checkpoint) carries its own `round` number (the same number used in `evidence/CPn/adversarial/round-NN` and found by `accept-finding` instead of by list position, since a round `reviewers` opens and then replaces before recording is never added here), plus `at` (when `adv-record` wrote the entry), `fingerprint`, `verdicts`, `findings` (count still blocking), `deferred` (count), `raw_findings` (count before dedupe/split), `substitutions`, `blocking_files` and `reviewers` (here, `{"id", "vendor", "model"}` objects, one per reviewer who actually reviewed this round — not the bare id list that lives on `adv_round` below). `opened_at`, `recorded` and `nonce` are not on this entry: they live on `checkpoints.CPn.adv_round`, the round `reviewers` opens and `adv-record` later marks `recorded`, which this `rounds[]` entry is built from. Once any finding of that round is accepted, it also carries `accepted`: a list of `{"id": "<the finding's 'reviewer/id' key, always qualified — never a bare id>", "reason": "<the user's or director's own words>", "at": "<timestamp>", "by": "human" | "director"}`, one entry per accepted finding, appended to (never replacing) whatever that list already held. This `accepted` list lives on the round's own state entry; `open-findings.json` and `deferred-findings.json` (both plain JSON arrays of findings, not of these `accepted` entries) are evidence-folder mirrors of the same decision, never the authoritative copy (see above).

In a director-enrolled lane, a chat `accept: <reason>` reply is never enough (the same rule as every other approval there): `ratchet.py accept-finding CPn --director-token <t> --reason "<their reason>"` is required instead, where the token comes from `director-sign accept-finding` and `--reason` carries the director's own reason (there is no chat reply to read one from, so it is mandatory with a token). The order still matters here as everywhere else: `ratchet.py ask accept-finding CPn <ids>` must run FIRST, by the lane itself, exactly as in a non-enrolled lane (it is where `pending.ids` comes from; `accept-finding --director-token` with nothing pending is refused) — it is just never shown to the user as a chat question to answer. The director signs only after that `ask` (`director-sign accept-finding`), because the token is bound to `awaiting_since`, which `ask` moves; signing before the `ask`, or running `ask` again after signing, both leave the token stale and need a fresh signature. The resulting entry carries `"accepted_by": "director"` in place of `"human"`.

**Triage: fix or rebut before the next round.** Once a round is recorded blocking with one or more open (blocking) findings, `ratchet.py reviewers CPn` refuses to open the next round until every one of them has a decision — even a single remaining finding needs its own fix-or-rebut call; there is no exemption for a lone finding. `ratchet.py triage CPn <ref>=fix:<reason> ...` records any number of decisions in one call, `<ref>` being a finding's key from `open-findings.json` (a bare id, or `reviewer/id` when a bare id is ambiguous, resolved the same way `accept-finding` resolves a ref — an unambiguous bare id matches directly, a bare id shared by two reviewers' findings is refused naming the colliding reviewers). Only `fix` and `rebut` are accepted, each needing a one-line reason after the `:`; `accept`, `defer`, `waive` and `skip` are refused, pointing at the accept-finding flow (CP3) instead, because the orchestrator can never defer or accept a finding through triage — only the user's own reply does that. Decisions are written to `evidence/CPn/adversarial/round-NN/triage.json` (`{"<ref>": {"decision": "fix"|"rebut", "reason", "at"}}`, one entry per ref, a later call may change one) and, from the `fix` ones only, `fix-list.json` (the same finding objects as `open-findings.json`, each with its own `triage_reason`) — the fixer is handed `fix-list.json`, never `open-findings.json` directly, once triage has run. The next round's reviewers see every `rebut` decision from the PREVIOUS round as one of the round's own review rules (`review_rules`, so both a `host-*` sub-agent's brief and `external_review.py`'s prompt carry it): "withdraw this finding if the rebuttal holds up, or re-raise it with a stronger user_impact if it doesn't."

**Check-in: pausing on the objective when reviews drag.** `checkpoints.CPn.checkin` (state.json): `{"round_count_fired": bool, "new_kind_fired": bool, "new_kind_repeats": <int>, "open": {"round", "trigger": "round_count"|"new_kind_repeat", "opened_at"} | null, "decided": [{"round", "trigger": "round_count"|"new_kind_repeat"|"round_limit", "decision": "simplify"|"change"|"stop", "why" (simplify/change only), "decided_at"}]}`. Right after a round is recorded still blocking, `adv-record` opens a check-in (once per trigger per step) when either: this is the `checkin_round`'th (config, default 2) round in a row to block, or this is the SECOND round where a blocking finding's `kind` was never seen before in this step, in a file an EARLIER round already had a blocking finding in (the first such round only counts toward the total; it does not open one on its own). While one is open, `reviewers CPn` refuses to open another round, naming `ratchet.py check-in CPn` to resolve it first; `complete CPn` is already refused too, because the gate the check-in paused is still not passed. `ratchet.py check-in CPn` with no `--decision` prints (or, with `--json`, returns) the objective's goal and users, the gate's latest recorded round's own still-open (not accepted) findings (the same current view `reviewers` and the fixer already use), each one's `user_impact`, how many rounds this step has used, the finding kinds grouped by the file they're in, and the three lettered options (simplify, accept, stop); it changes nothing. Before picking `--decision simplify` or `--decision stop`, the orchestrator must spawn a fresh strong-model reviewer (a sub-agent with no history in this round) with the objective, this brief's open findings and the round history, and have it recommend simplify, accept or stop; the orchestrator never decides a check-in from its own reasoning alone. `--decision simplify --why "..."` is then recorded with that reviewer's reasoning — no user question, since lowering the bar is not what this does; it only narrows or changes the step. `--decision accept` is always refused, pointing at `ask accept-finding` / `accept-finding` (CP3), so a cooperative agent can never wave its own findings through a check-in. `--decision stop` moves the run into the existing blocked/ask flow (`_set_blocked`) for the user to decide how to wrap up, the same as any other block. `--decision change` is refused here (while a check-in is actually open): it only ever applies at the step's own round limit block, with no check-in open (see above); the message points at `--decision simplify` instead. `plan-summary` lists every `decided` entry (simplify's or change's reasoning, or stop) next to the findings the user accepted; plain `status` never does, since a past decision must not make it look like one is open again — only a currently open check-in gets its own line there. Accepting the last open finding of a round through `accept-finding` (CP3) also clears an open check-in for that step: once nothing is left open, there is nothing left for the check-in to pause on.

`gates.adversarial.round_limit_grants` (int, default 0), `round_limit_simplify_used` and `round_limit_change_used` (bools, default unset/false) are a SEPARATE mechanism from the `checkin` record above: they track the step's own round limit block's reuse of check-in's simplify record (see "Simplify/change at the round limit block" above), not the soft `checkin_round`/`new_kind_repeat` triggers. The two never fire in the same state (the soft check-in is always resolved before the hard cap can be reached), but their `decided`/`used` bookkeeping lives in different fields because the soft trigger's `decided` entries never consume a round, while a `"trigger": "round_limit"` entry always does.

`human_review`: `end` (default — you review once all checkpoints pass), `each` (review every checkpoint), `none` (fully autonomous after plan approval; gates stay just as strict). Other keys and defaults: see `DEFAULT_CONFIG` in `scripts/ratchet.py`.

**Providers.** Each entry in `providers` is an agent CLI that can review: a `preset` (`claude`, `codex`, `gemini`, `copilot`, `cursor`, `opencode`) or its own `command`, plus an optional `model` and `company`. The company is whose model it runs; when not given it is worked out from the model name (claude/opus/sonnet → anthropic, gpt/codex → openai, gemini → google, grok → xai, glm → zhipu, qwen, deepseek, kimi, llama, mistral) or from a single-company preset. A provider whose company is unknown, or the same as the host's, is not used as an independent reviewer. `for_risk` limits it to some risk levels (for a smaller model). Each provider gives three reviewers: `<id>-correctness`, `<id>-standards`, `<id>-both`. `ratchet.py providers --discover` finds installed tools, tests them and adds what works; `--add` registers one (it is tested first); `--check` re-tests; `--remove` drops one. Test results are kept in `.ratchet/provider-status.json`. `providers` is not one of the rules locked at plan approval: adding a working provider mid-run only changes who is available.

**Review slots.** Each `review_depth` entry is a list of slots. `any-<lens>` means: every provider's `<id>-<lens>` in order (a company not yet reviewing this round preferred), then `host-alt-<lens>` (the host's company on a different model, from `host_models.<company>.alternates`; unavailable when the host has no alternates), then `host-<lens>`. A slot can also be a reviewer id or a list of ids as alternatives; a slot of only command reviewers falls back to `host-alt-*`, then `host-*`, same lens first. Before relying on a provider not tested in the last `probe_ttl_minutes`, `ratchet.py reviewers` sends it a test request; one that fails is skipped for `unavailable_ttl_hours`. `blocking_severities`: which severities block, by risk (`"all"`, or a list; unknown severities always block). `scope_later_rounds`: from round 2 on, minor findings outside the code changed since the previous round are recorded instead of blocking. `converge_after_round` (default 2): from round `converge_after_round + 1` on (round 3 by default), a minor finding never blocks, whatever its scope; blocker and major findings always block. `checkin_round` (default 2): after this many blocking rounds in a row, `ratchet.py reviewers CPn` pauses for a check-in before opening another round (see "Check-in" in section 7). Recorded findings: `ratchet.py deferred`. A project whose `review_depth` is still the pre-1.5 default is moved to the new default automatically. `host_provider`: `auto` detects the running agent CLI from its environment (Claude Code, Codex, Gemini CLI, Copilot CLI); set it explicitly (or `RATCHET_HOST_PROVIDER`) for anything else. `ratchet.py reviewers CPn --json` shows the resolved list with `fallback_for`, reasons, models and the round's `review_rules`. `ratchet.py reviewer-status [--reset ID]` shows or clears availability. Command placeholders: `{prompt_file}` `{prompt}` `{out_file}` `{root}` `{model}`; `"stdin": true` pipes the prompt.

**Automatic checks and guardrail steps.** Every adversarial finding may carry a `kind` (a kebab-case label for the type of mistake); only this explicit label counts. A kind found in two places (distinct checkpoint + file) is a repeat (`ratchet.py repeats`). After the user picks a guardrail option (`ask choice --guardrail "A=<kind>"`, then `choice`, at the same checkpoint) or the director signs `director-sign guardrail --kind <kind>`, `ratchet.py guardrail` inserts a checkpoint right after the current one with a `guardrail` object (`kind`, `check_command` with a `{target}` placeholder, `target`, `bad_example`, `why`) and a ready test plan. It refuses a kind that hasn't repeated or that already has a check. Before that checkpoint can complete, Ratchet runs the check on `bad_example` (must fail) and on `target` (must pass), and neither run may change a file. Ratchet also rebuilds every reviewed code version where a blocking finding of that kind was recorded and acted on (the flagged file changed in the next version; a disproved finding doesn't count), using `git archive` of that version with links skipped, the step's own files laid over it and installed dependencies linked in, and runs the check there: it must fail on each. Every case a check was proven on is kept on its `checks` entry (`cases`) and re-run when it is strengthened, so no past case can be dropped; a case that can't be rebuilt fails the proof instead of being skipped, and a check that changes the installed dependencies fails it too. For a high-risk kind (`guardrail.high_risk`: found on a high-risk checkpoint or rated a blocker), the step is high risk, needs ≥3 files in `<variants_dir>/bad` (each must fail) and ≥2 in `<variants_dir>/good` (each must pass), written by `ratchet-variant-writer` before `tests-written`. A failed proof sends the step back to `behavior` (bounded by `max_behavior_attempts`). Then the check (with `{target}` filled in, plus `template`, `target`, `bad_example`, `test_command`, `test_files`, `high_risk`, `variants_dir`) is added to `checks` and recorded in `learnings.md`. When a later review finds a blocker or major finding of a covered kind, Ratchet adds a step with `guardrail.strengthen: true` right after the current one, automatically; it replaces that kind's check once proven against every past case plus the missed one. Every behavior gate runs each `checks` command after the tests; a failing check, or one that changes files, fails the gate. Minor findings of a covered kind are recorded instead of blocking; blocker and major findings always block. `checks` is locked at plan approval like the other rules (removing or editing a check needs the user's yes); a completed guardrail updates the lock itself.

**Models per role.** `role_models` gives each sub-agent role a tier (`strong`, `standard`, `light`) or a model name; `host_models.<company>` maps the tiers to model names for that host (`inherit` = the session's own model). A host with no entry runs every role on the session's model. `ratchet.py models` prints the table the orchestrator uses when it spawns sub-agents.

`approver`: `human` (chat message after the pause), `director` (signed token only), `either`. A lane enrolled with `director-enroll` is forced to `director`, whatever this key says.

**Chat approvals answer a question Ratchet printed.** Every chat approval needs a question registered first: `ratchet.py ask <action>` (`approve-plan`, `human-approve`, `cancel`, `set-review <mode>`, `approve-changes`, `claim`, `ui-respec <cp>`, `hooks-waive`, `choice`, `accept-finding <cp> <ids>`, `raise-limit <cp>`) stores `"pending": {"action", "mode", "asked_at", "prev_awaiting", "session", "phase"}` in `state.json` (`phase` only for `approve-plan` and `human-approve`: their answer counts only at the pause they were asked at; `choice` adds its options) and prints `ASK THE USER: …` with the replies that count, then a `NEXT:` line telling the agent to show it as the only question in its message (Ratchet can't see what the agent showed, so a yes to another question in the same message would still count; that the question was shown alone is not checked by the engine, an accepted limit by the user's decision). `session` is the chat whose reply answers it: the run's `owner_session`, and for `claim` the chat that ran `ask claim` (from the guard hook's note for that exact call, see below), so a reply in any other chat, including one the user typed in later, never answers it or moves the run. Only with no usable note for that call (an agent CLI whose guard hook doesn't run, or a call the guard couldn't read, such as one inside `bash -c`) does `claim` fall back to the chat the user typed in last. **Which chat owns a run:** `init` sets `owner_session` to the chat that ran it. The guard hook sees the chat (session id) of every shell call, so when the command really runs `ratchet.py init` or `ratchet.py ask` (as `python3 …/ratchet.py`, `…/ratchet.py` or `$RATCHET`) it notes that chat in the per-user `engine-call-sessions.json` (`{"<resolved project folder>|init" or "...|ask": [{"session", "argv", "at"}, …]}`, in `RATCHET_HOME`, written by the guard only; `argv` is the call's arguments after `ratchet.py`). The guard reads the command as shell words: a mention of ratchet.py inside quotes (an echo, a commit message, a grep pattern), in a comment or after a quoted `;`/`&&` is not a call, and a command with a heredoc or here-string, a command substitution (`` `…` `` / `$(…)`), bash `$'…'` quoting, or an argument the shell would still expand (`$VAR`) gets no note. `init` and `ask` each take a note only when its `argv` equals their own arguments exactly and it is under 60 seconds old (`ENGINE_NOTE_SECONDS`); the matching note is removed (used once), and stale or malformed notes are dropped. When notes from more than one chat match the same call, none is used. A note that doesn't match is ignored and the rules below apply. With no `init` note, `init` falls back to the chat of the last message in `human_log.jsonl`. When there is still no owner (the first run in a repo starts before the prompt hook can log anything), the next of these sets it, whichever comes first: an `ask` with a note makes the chat that ran it the owner (history `owner_recorded`, `via: "ask"`), or the first chat the prompt hook records for the run becomes the owner: the hook only appends that chat to the run's `prompt-chats.jsonl` (it never writes `state.json`), and the next command that changes the run makes it the owner under its own lock (`owner_recorded`, `via: "prompt"`; only a record matching a message in `human_log.jsonl` counts, and each is used once, tracked by `prompt_chats_seen` in `state.json`). A question asked with no owner and no note (an agent CLI whose guard hook doesn't run) is stored with no `session`; the first chat the user then types in owns the run and answers it. `ask claim` with no owner is refused (there is nothing to take over; plain `resume` works). Reply matching never falls back to every chat: a question's replies come only from its `session` (or the owner), and while neither is known only a message that carries no chat id at all counts (an agent CLI that sends none, where Ratchet can't tell chats apart). After that the owner changes only through `resume --claim` (`approve-plan` never changes it). Only the user's FIRST reply in `human_log.jsonl` after `asked_at` from that chat answers it; a message from another chat neither answers nor closes the question and never changes `owner_session` (only `resume --claim` moves a run). Except for `hooks-waive` (its own exact phrases), `choice` (a letter) and `accept-finding` (its own exact reply, `accept: <reason>`, see section 7) and `raise-limit` (its own exact reply, `raise: <reason>`, above), that reply approves only when it is one of `yes`, `yes, go ahead`, `go ahead` or `approved` (case, commas, extra spaces and a trailing `.` or `!` ignored; nothing else attached). Any other first reply approves nothing and closes the question (`pending` is removed, `"spent_question": {"action", "asked_at", "session"}` remembers it and history gets `question_not_approved`; `awaiting_since` stays at the question, so `feedback` can still record that reply), and the agent asks again. A reply typed before the question, or while a different question is pending, never counts. **One question at a time:** `ask approve-plan` / `ask human-approve` are refused while a different question still waits for its first reply (answer it or `ask withdraw` first). Any other `ask` over such a question replaces it but prints `NOT ASKED: …` and stores `"overtook"` / `"overtook_mode"` (the replaced question) on the new `pending`; a question marked that way approves nothing and is closed when its command runs, so the agent asks it again on its own. Asking over a question that already had its first reply starts clean. Two kinds of waiting question are never replaced, and `ask` refuses (nothing is stored or logged) instead: a question still waiting for its first reply in another chat (for example the run chat's plan question when another chat runs `ask claim`, or the other way round; the agent tries again after it is answered there, or runs `ask withdraw` if the user says that chat is gone), and a `hooks-waive` question that has no reply yet or whose first reply was the waiver phrase (`hooks-waive` reads its answer from that question, so replacing it would hide that reply; the agent runs `hooks-waive` or `ask withdraw` first). A `hooks-waive` question whose first reply was anything else was answered no, so it can be replaced like any answered question. Every replaced question is logged as `question_overtaken` (`action`, `mode`, `by`, `answered`), and `ask withdraw` logs `question_withdrawn`. `plan-submit` clears a pending `approve-plan` question (the plan changed) and prints a `NEXT:` line saying to run `ask approve-plan`; `feedback` clears a pending `human-approve` question. When a `human-approve` question was asked at this pause (still pending, or spent with `spent_question.asked_at` equal to `awaiting_since`), `feedback` is bound to the first reply after that question in its chat, the same reply that answered it, not a later message; otherwise it takes the latest message from the run's chat since `awaiting_since`. A run that was already waiting before this rule has no `pending` entry, so its approval is refused until the agent runs `ask approve-plan` (or `ask human-approve`) and the user answers. A director token (`--director-token`) needs no question and no chat reply, and so does a confirmed `RATCHET_HUMAN_OVERRIDE` (section 10). **One command at a time:** every command that changes a run (`STATE_LOCKED_CMDS`: `init`, `plan-submit`, `approve-plan`, `tests-written`, `red`, `implemented`, `behavior`, `ui-record`, `adv-record`, `complete`, `human-approve`, `feedback`, `plan-extend`, `pause`, `resume`, `ask`, `accept-state`, `hooks-waive`, `cancel`, `set-review`, `choice`, `ui-respec`, `accept-finding`, `raise-limit`, `approve-changes`, `guardrail`, `reviewers`, `repeats --offered`, `spec import`, `spec keep`, `wait`, `check-in` and `triage`) holds one exclusive lock file, `.ratchet/state.lock`, for its whole run: from before its first read of `state.json` to after its last write, its test runs, checks, regression suite and provider probes included. Ratchet serialises; it never merges two commands' changes. The lock file is created with `O_CREAT|O_EXCL` and holds the command's process id, a random token and the command's name; it is removed when the command ends. A second command started meanwhile waits for a short one (at most `STATE_LOCK_WAIT_SECONDS`, 30) and then reads the state the first one wrote, so a double submit can't spend one answer twice: the second copy finds the question already spent and refuses. Behind a long one (`LONG_LOCKED_CMDS`: `red`, `behavior`, `complete`, `reviewers`) it waits only `STATE_LOCK_BUSY_WAIT_SECONDS` (2), then refuses with `Ratchet is busy running <command>; try again when it finishes` and changes nothing. So an approval command (a `cancel` or `set-review` the user said yes to) run while tests run is refused as busy; the user's reply is already recorded, so the agent runs the same command again once the long one finishes, and it then works on that reply. Two `behavior` runs of the same checkpoint can't both count: the second is refused as busy. Every other failure to create the lock (a Ratchet folder it can't write, a folder or a link where the lock goes) is retried the same way, with a pause between tries, and then refused with a plain message that names the lock file; nothing is changed. A live command touches its lock file every `STATE_LOCK_REFRESH_SECONDS` (30) while it runs. A lock file not touched for longer than the longest test run plus a margin (`test_timeout_sec` from the project's config, at least the default 900, plus `STATE_LOCK_STALE_MARGIN_SECONDS`, 300) is left over from a crashed command and is removed, so a long, live test run is never taken for a crash. The lock file is only ever removed (that stale case, or a command removing its own lock) while holding a second `O_CREAT|O_EXCL` file, `.ratchet/state.lock.break`, so two waiters can't both clear one stale lock and none can remove a newer live one; a `.break` file older than 30 seconds was left by a process that died while holding it (it is held for a few system calls) and is removed, but never by path: a waiter first renames it to a name of its own and removes it only when it is the very file it judged stale (same inode and modification time), and otherwise puts it back at once; a holder checks that its `.break` file is still in place before removing anything under it, so two waiters behind one stale `.break` file can't both hold it. `state.lock` and the per-user locks below share this one breaker protocol (only a regular file is ever judged stale or removed; a folder or a link in its place is left alone), so they behave the same. `init`, the first command in a project, creates the `.ratchet/` folder before it takes the lock, so two first `init`s at once are serialised too: one starts the run, and the other then finds that run active and refuses (`Run '<slug>' is still active`). **The hash record and its lock:** after each write Ratchet keeps a SHA-256 of each file it owns (`state.json`, `human_log.jsonl`) in the per-user `file-hashes.json` in `RATCHET_HOME` (`{"<resolved file path>": "<sha256 hex>"}`, replaced in one rename); a later read that finds a different hash refuses (the file was changed outside ratchet.py). Every read-modify-write of that record, every append to a recorded file together with its new hash (`append_recorded`: the prompt hook's message, an override's audit line), and every check of a file against its hash holds a second, per-user lock file, `file-hashes.lock` in `RATCHET_HOME` (created with `O_CREAT|O_EXCL`, holding its process's own random token, held for milliseconds, removed on release only while it still holds that token). It is separate from `state.lock` so the prompt hook, which never takes `state.lock`, can append while a long command runs: two writers never drop each other's hash, and a check never sees a recorded file between its append and its new hash. It is best effort: a caller waits for it at most 5 seconds and then goes on without it, a lock file older than 30 seconds is left from a process that died and is removed, and when the per-user folder can't be written the caller goes on without it. Like `state.lock`, this lock file is only removed (that stale case, or a release) while holding a second `O_CREAT|O_EXCL` file, `file-hashes.lock.break`, and judged again under it, so two processes clearing one stale lock can't both proceed and none removes a newer live lock; a `.break` file older than 30 seconds was left by a process that died while holding it and is removed. The record is replaced through a temp file named with the process id and a random token, in one rename. A `file-hashes.json` that can't be read (not valid JSON, not a JSON object) vouches for nothing: every check against it refuses with a plain message naming it (the prompt hook does not record the message, says so to the agent and never crashes; the stop hook counts no typed message), a write leaves it as it is (it never starts a fresh record, which would drop every other file's hash) and says so on stderr, and only `accept-state`, confirmed by a person at their own terminal, replaces it with a new record of that project's files. **The engine-call notes and their lock:** every read-modify-write of the per-user `engine-call-sessions.json` (the guard hook noting an `init` / `ask` / `wait` call, and `init` / `ask` / `wait` using a note up) holds its own per-user lock file, `engine-call-sessions.lock` in `RATCHET_HOME`, built the same way as `file-hashes.lock` (created with `O_CREAT|O_EXCL`, holding its process's own token, held for milliseconds, removed on release, one older than 30 seconds cleared as left by a process that died, every removal done while holding `engine-call-sessions.lock.break`), so two guard hooks noting calls at once never drop each other's note and two commands never use the same note. A caller waits for it at most 2 seconds. When it can't be had, nothing is recorded: the guard notes nothing (the call itself still runs) and `init` / `ask` use no note and leave the notes as they are, so the owner rules that apply without a note take over. The notes are replaced through a temp file named with the process id and a random token, in one rename. A notes file that can't be read (not valid JSON, say after a crash mid-write) holds no note: the guard says so on stderr and replaces it with the call it is noting, and `init` / `ask` say so on stderr and use no note (the rules without a note apply); nothing exits or crashes over it. Likewise an unreadable `director-folders.json` names no director folder: the director check treats it as empty, and a director session's guard says so on stderr and replaces it. **Every shared record and its lock:** a record more than one process can update at once is only ever changed through one read-modify-write, `update_record`, which holds a lock for that file from its read to its write, so two writers never drop each other's entry (two `init`s in two projects at once both stay in `active-runs.json`, two `director-enroll`s for two lanes at once both stay in `enrolled.json`). These are every record in `RATCHET_HOME` (`file-hashes.json` and `engine-call-sessions.json` under the locks above; `active-runs.json`, `enrolled.json`, `director-folders.json` and `stop-errors.json` each under its own lock file next to it, `active-runs.lock`, `enrolled.lock`, `director-folders.lock`, `stop-errors.lock`) and, in `.ratchet/`, `hook-heartbeat.json`, `provider-status.json` and `unavailable-reviewers.json` (`hook-heartbeat.lock`, `provider-status.lock`, `unavailable-reviewers.lock`). Each of these lock files is built like `file-hashes.lock` (created with `O_CREAT|O_EXCL`, holding its process's own token, held for milliseconds, removed on release, one older than 30 seconds cleared as left by a process that died, every removal done while holding its `.break` file). A writer waits for it at most 5 seconds (a hook writing `hook-heartbeat.json`, 1 second). When it can't be had, nothing is written over the record, and what happens instead depends on the file: `director-enroll` refuses with a plain message naming the lock and changes nothing (no `director.json` either), so the director runs it again; `reviewer-status --reset`/`--mark` and `providers --add` (checked or `--no-check`) refuse the same way, with a plain message naming the lock, and change nothing, so the user runs them again; each of these refusals ends with the user's own whole command to run again (this Python, this `ratchet.py` and every argument given, `--preset`, `--command`, `--model`, `--company`, `--reason` and the rest, quoted for the shell), so running it as written works; a checked `providers --add` takes both `provider-status.lock` and `unavailable-reviewers.lock` before it writes either record, so a busy lock on either one leaves `provider-status.json`, `unavailable-reviewers.json` and `config.json` exactly as they were (and an add refused because its test request failed records nothing either); a run that starts, is reopened (`plan-extend`), is approved at the end (`human-approve`), completes, is cancelled or resumes says on stderr that it was not registered in (or removed from) `active-runs.json` (`pause` and then `resume` registers it again); a director session's guard reports `director-folders.json` as a record it could not save (see `hook-env.json` below); a stop hook counts one more refused stop without saving it (fail closed); a hook skips that heartbeat (liveness only); and a best-effort provider probe (run from `reviewers`, `providers --discover` or `providers --check`) only says on stderr that its result was not saved. Each file keeps its own rule for a damaged record (section 10). `hook-env.json` is not changed this way: it is rebuilt from the per-run records in `.ratchet/hook-env/`, never from its own content (below). A test reads `ratchet.py` and fails if any other function writes one of these records, or if a helper writes a path it was handed. The prompt hook never takes the lock and never writes `state.json`, so it never waits behind a long command and every message is recorded at once: it appends the message to `human_log.jsonl` (with its hash, under a lock of a few milliseconds around the hash record only, `file-hashes.lock`, described above) and, while no chat owns the run, the chat to the run's `prompt-chats.jsonl`; commands read both under their own lock. The stop hook only reads `state.json` (it is replaced in one rename, so a read never sees half a write). While a command holds the lock it does not let the agent stop silently: it says `Ratchet is busy running <command>`, with the same limited fail-closed count as an unreadable `state.json`. While a live wait applies (see "Waiting on background work" in section 10) it lets the owner chat stop and adds no line. It keeps its count of refused stops in the run's own `stop-blocks.jsonl` (one line per refused stop, `{"at", "phase"}`, or a reset `{"at", "reset": true}` when a stop is allowed); the count restarts at a progress event or `resumed` in the history, a message the user typed, or a reset line. It writes `state.json` only after one try at the lock, never waiting: to block the run once the count passes `max_stop_blocks`, and to end a hooks waiver once the enforcement hooks have fired since it was given (see section 10). If a command holds the lock at that moment, it skips the write. With `RATCHET_HUMAN_OVERRIDE=1`, a locked command asks for the code before it takes the lock, so nothing waits on the person typing it. `complete` holds the lock from its first read, so nothing can fail on the lock after its checkpoint commit. If it still fails after the commit (a crash, a full disk), running it again finds that commit at `HEAD` (same message, same reviewed tree) and records it instead of making a second one; a fingerprint difference only inside `.ratchet/` (the shared files that commit added) does not count as a code change. Likewise, a file that is the agent CLI's own chat transcript (its `transcript_path`, as recorded on a human reply) of a reply recorded since a gate passed is not a code change either, for every gate: `complete` ignores a difference there, so a CLI that keeps its transcript inside the project does not make its own gates stale just by being used. Accepting every open finding of an adversarial round (section 7) stamps that gate's `passed_at` with the round's own `opened_at`, not the time of the acceptance, so `complete` correctly looks for a transcript change (never a code change) from when the round actually opened.

## 10. Hooks

`ratchet.py hook <stop|prompt|guard> --host auto|claude|codex|gemini|copilot` is the single entry point every agent CLI calls. Written by `install-hooks` (or the plugin's `hooks/hooks.json`):

| host | config file (project / user) | stop | prompt | guard |
|---|---|---|---|---|
| claude | `.claude/settings.json` / `~/.claude/settings.json` | Stop | UserPromptSubmit | PreToolUse |
| codex | `.codex/hooks.json` / `~/.codex/hooks.json` | Stop | UserPromptSubmit | PreToolUse |
| gemini | `.gemini/settings.json` / `~/.gemini/settings.json` | AfterAgent | BeforeAgent | BeforeTool |
| copilot | `.github/hooks/ratchet.json` / `~/.copilot/hooks/ratchet.json` | agentStop | userPromptSubmitted | preToolUse |

**Plain-language output (user-facing; never paste JSON at the user).** `ratchet.py status` (no flag) prints plain text: first line `Step N of M done: <title>` (or `All M steps are done.` / `No plan yet.`), the phase in words, what is happening now, a re-run note when a passed check went out of date, and, when blocked, the reason in quotes plus 2-3 lines `A) ...`, `B) ...`, `C) ...`. `ratchet.py plan-summary` prints, per step: title, first done-when line, `UI review: yes|no`, `Risk:` and `Reviewed by:`, plus a hooks-skipped note when waived; paste it at the plan approval stop. `next` gains `options: [{letter, text}]` (blocked phase only, same choices as the text status) and the warning/doctor text is addressed to the agent. viewer-data.json `next` gains `label` (plain sentence for the current step); `hooks.waived` drives the viewer's hooks-skipped banner. `status --json` and `lanes --json` gain `blocked_reason_plain` (the block reason as a plain sentence; unknown reasons pass through unchanged, null when not blocked; `blocked_reason` stays the raw text), viewer-data.json `state` gains the same `blocked_reason_plain`, and `next` in the blocked phase gains `reason_plain` next to the raw reason in `action`. `status --json` also carries `next_action`'s `accept_note` (null except at an adversarial round limit block whose current checkpoint's last recorded round still has open findings for the current code; see "Accepting an open finding" in section 7): the agent prints it, as its own plain line, next to the lettered options, never as one of them. `status --json` also carries `objective` (the plan's own object, or the `NO_OBJECTIVE_NOTE` string for a plan with none). At `awaiting_final_review`, plain `status` opens with it (the goal, who it's for, then every `done_means` line printed as `check: <line>`, with no met or not-met claim, since finishing the checkpoints never by itself proves a line is met) before anything else, followed by the findings accepted along the way and anything left for later, so the final review is reported against the objective with that context; a plan with no objective gets the same plain note instead. A check-in open for the current checkpoint (section 7) adds its own one-line note, naming `ratchet.py check-in CPn`; a past check-in decision is never shown by plain `status` (only `plan-summary`, next to the findings the user accepted), so `status` never looks like one is open again once it's been answered.

**Waiting on background work.** `ratchet.py wait --for "<what>" [--minutes N] [--session <id>]` stores `"wait": {"reason", "set_at", "until", "session", "minutes"}` in `state.json` under the state lock (history `wait_set`). `minutes` is kept between 1 and `WAIT_MAX_MINUTES` (120), default `WAIT_DEFAULT_MINUTES` (30); `reason` is the `--for` text, spaces collapsed, at most 300 characters. Only the run's owner chat may set it: the chat is the one the guard hook noted for this exact call (as for `init` and `ask`), else the chat the user typed in last (the session of the last `human_log.jsonl` message, as for `ask claim`). `--session` is only a cross-check, never proof on its own (`owner_session` is plain text any local process can read): a `--session` that differs from that chat, no chat Ratchet can tell, a chat that is not `owner_session`, a run no chat owns yet, or a run that is blocked, paused, done or cancelled is refused with a plain message and nothing is stored. A wait applies (`live_wait`) only while the phase is not blocked, paused, done or cancelled, `session` is still `owner_session`, `set_at` is not in the future, `until` is still ahead and at most `WAIT_MAX_MINUTES` after `set_at`, and no `PROGRESS_EVENTS` entry or `paused` / `resumed` / `cancelled` event was logged after `set_at`. Any of those events also removes it (history `wait_cleared`, `by` the event). While it applies, the stop hook lets the owner chat stop with a one-line note and adds nothing to `stop-blocks.jsonl`, so the stops never count toward `max_stop_blocks`; once it has ended, stopping is refused and counted as before. `status --json` and `next` carry `"wait": {"reason", "set_at", "until", "session"}` while it applies and `null` otherwise; plain `status` prints `Waiting on: <reason> (until <time> UTC).`

**Turns the agent CLI sends on its own.** The prompt hook records nothing for a prompt where one of `HOST_TURN_MARKERS` starts any line of it, after any leading wrapper tags (`HOST_TURN_WRAPPER_TAGS`: `<system-reminder>` or `</system-reminder>`) and any leading whitespace (Unicode and zero-width included) are set aside on that line alone. Every line of the prompt is checked, in one linear pass; there is no fixed line count, block count or blank-line cap, so no amount of ordinary preamble text ahead of the marker line changes the result. The markers: `HOST_TURN_MARKER_RE` matches `<agent-message from="...">` at the start of a line (the real bytes the hook receives for a sub-agent's hand-back; the attribution value isn't fixed, matched by the opening tag alone), and `HOST_TURN_MARKERS` holds `Another Claude session sent a message:` (Claude Code's on-screen rendering of that same hand-back, kept too so an older run or a differently-rendering host still matches), `[SYSTEM NOTIFICATION - NOT USER INPUT]` and `<task-notification>` (a background task's notice). No `human_log.jsonl` line and no `prompt-chats.jsonl` line is written, so the turn answers or closes no waiting `ask` question, counts toward no approval and does not restart the stop hook's count; the hook tells the agent so. Only line starts are checked (exact, case-sensitive): a message that mentions a marker mid-line is recorded as usual. A genuine reply with a marker at the start of one of its lines is dropped too, on purpose (the safe side), and the user sends it again.

**Reviewer prompts too large for one argument.** A reviewer command that takes the prompt as a command-line argument (`{prompt}`; the `copilot`, `cursor` and `opencode` presets) is checked before it starts: when one argument would exceed the system's single-argument limit (Linux: 32 pages, 128 KiB with 4 KiB pages) or the arguments and environment together would exceed `SC_ARG_MAX` (Windows: a 32,767-character command line), less an 8 KiB margin, `external_review.py` does not start it, marks it (and every reviewer using the same CLI) unavailable through `mark_unavailable` with that reason, and exits 3, writing no review file. An `E2BIG` from the system when starting it is handled the same way, and any other refusal to start (`OSError`) also marks it unavailable and exits 3. A provider whose `command` reads `{prompt_file}` or uses `"stdin": true` is not limited this way. The `ratchet-<reviewer>-` temp folder holding the prompt and the CLI's reply is removed when the review ends, pass or fail (kept only with `--dry-run`).

Runtime files: `.ratchet/hook-heartbeat.json` (last time each hook fired and via which host; read by `doctor`, `next`, and `status --json` as `hooks_warning` and `hooks`) and `.ratchet/hook-errors.log` (internal errors; hooks fail open; one line per crash, `<iso time> <host> <event>: <ExceptionType>: <message>`; read by `status`, `next` and `doctor` as `hook_errors`), and `.ratchet/hook-crashes/` (a folder of empty marker files named `<host>.<event>.<crash|clean>.<microseconds since 1970>.<unique suffix>`, written only by `run_hook`: a crash creates a `crash` marker; a clean run of that same hook on that same host creates a `clean` marker, stamped with the time that run started, only when it resolves a crash recorded before it began. A crash is unresolved while no `clean` marker of that hook and host is newer than its newest `crash` marker. Each run only creates its own marker with an exclusive create and then deletes markers it supersedes (that hook's older crash markers; for a clean run, also its older clean markers), so no file is ever read, changed and written back, and concurrent hooks cannot erase each other's records on any OS. It does not age out, so a crash older than the 24-hour `hook_errors` window still keeps `enforcing` false until that hook runs cleanly. Other file names are ignored; a missing folder means no crash was recorded. Fail safe: when a crash marker cannot be saved, `run_hook` appends `<iso time> <host> <event>` to `.ratchet/hook-crashes-unsaved.log`, and readers count that line as a `crash` marker at that time (never deleted; a newer `clean` marker resolves it, and a clean run that cannot save its marker resolves nothing). When `hook-crashes/` exists but cannot be listed (not a folder, no permission), or `hook-crashes-unsaved.log` exists but cannot be read, every hook counts as broken (`enforcing` and `prompt_hook` false) and `hooks_warning`, plain `status` and `doctor` say the crash records cannot be read. Fail closed on writes too: a hook counts as working only while Ratchet can save its crash state. Readers prove it with a real write (they create and delete a `.write-probe.*` file in `hook-crashes/`, or in `.ratchet/` before that folder exists); while that fails, every hook counts as broken. Crash state is only ever written as per-run exclusive-create marker files or appended lines; no crash-state path reads, changes and rewrites a shared file, so concurrent hooks cannot erase each other's crashes. `hook-heartbeat.json` is rewritten whole by each hook (to a temp file renamed into place, so no reader ever sees it half-written), under its own lock, `hook-heartbeat.lock` (section 8, "Every shared record and its lock"), so concurrent hooks keep each other's entries; it holds liveness only, so a beat skipped because that lock could not be had within a second can only make a hook look less healthy until its next run. When a crash can be saved in neither `hook-crashes/` nor `hook-crashes-unsaved.log`, `run_hook` prints a plain, non-blocking message to the host; while writes are refused, `hooks_warning`, plain `status` and `doctor` say the crash records cannot be saved. Known limit: such a crash leaves no lasting record (at most a `hook-errors.log` line, which counts until that hook runs cleanly again, for at most 24 hours), so once writes work again it no longer counts; hooks count as broken only while writes are refused). Known limit: when `hook-crashes/` is not a real folder (for example a broken symlink) and every fallback write (`hook-crashes-unsaved.log` and `hook-errors.log`) also fails at that moment, that crash may go unrecorded entirely; this is an accepted limit, not a bug.

**`.ratchet/hook-env.json`** (written only by `run_hook`, before it decides anything; the guard refuses agent writes to it): `{"home": "<resolved RATCHET_HOME>", "key_file": "<resolved director key file>", "guard_role": "director" | "builder", "at": "<iso>", "host": "<host>"}`. A hook runs with the agent CLI's own environment, not with a shell the agent controls, so this is the per-user folder (where the integrity hashes, enrollments and director key live) and the key file Ratchet trusts for the project. Ratchet does not check who called its hook command, though: a script deliberately written to cheat, running as the same OS user, can run `ratchet.py hook guard` itself with made-up input and environment and so forge this record (and `director-folders.json`). That is an accepted limit (see the known limit under "Variables a builder session may read but never set"): these records stop an agent from stumbling past a gate or taking an easy shortcut, not a deliberate same-user forgery. `guard_role` is written by the guard hook only (it runs right before every command any session runs): `director` when the agent CLI that last ran a command here was started with `RATCHET_ROLE=director`, `builder` for any other session; absent until a guard has run here. No hook reads this file, changes it and writes it back, so concurrent hooks never drop each other's newer values: each hook run first saves its own record in `.ratchet/hook-env/`, a file named `hook-env.json.<guard|env>.<start time in microseconds>.<director|builder|->.<pid>-<random>` (the role only for a guard run) holding `{"home", "key_file", "at", "host"}`, renamed into place whole; it removes the records its own supersedes (a guard run every older record, any other run older non-guard records). Then it makes `hook-env.json` agree with the records, rewriting it in one rename only when `home`, `key_file` or `guard_role` differ, and checks again after each rewrite: `home` and `key_file` come from the newest record, `guard_role` from the newest guard record (newest by when the hook run started; when a director and a builder guard record started in the same microsecond, the builder's counts as the newer one, so a tie never favours the director), so a hook that started first but finished last cannot restore an older role or folder. The director check reads the role from the newest guard record directly whenever `hook-env.json` exists (falling back to the file's `guard_role` when there are no records); a folder of records that can't be listed counts as an unreadable record. A hook that can't save its record, or can't get `hook-env.json` to agree, counts as a failed write (below). Every other `ratchet.py` command (and every integrity check of `state.json` or `human_log.jsonl`) refuses with a plain message when its own `RATCHET_HOME` or `RATCHET_DIRECTOR_KEY_FILE` resolves to something else, instead of silently using a folder that holds no integrity record or a key of an agent's own making. The director commands (`director-key`, `director-enroll`, `director-sign`) also need the hooks to agree on the role, because `RATCHET_ROLE=director` in a process's environment proves nothing on its own (a builder could set it inside a script the guard never sees). They run only when the session's own folder (the working directory, not `--root`) is a Ratchet project whose `guard_role` is `director`, or a folder with no `.ratchet/` that a director session's guard recorded in the per-user `director-folders.json` (`{"<resolved folder>": "<iso first seen>"}`, written by the guard only). Otherwise, when the own folder's record, or failing that the target project's, shows `builder` (or cannot be read), they refuse with a plain message. A missing record is never read as permission: when neither place has a director record and Ratchet's hooks are in use, the commands refuse and say to restart the director's agent CLI so its hooks record the role. "In use" means installed for any agent CLI (user scope, or the own folder's or the lane's project config; any CLI, not only the detected one, because host detection reads variables a script can set), or delivered without that config (a plugin) and seen enforcing: a guard or stop hook has run in the own folder's project or the lane, or a hook failure there is still unresolved. The one exception is a setup where Ratchet's hooks are not in use at all: then nothing records or enforces anything, `RATCHET_ROLE=director` is taken at its word, and the command says so on stderr. So the director's agent CLI needs Ratchet's hooks and its own folder, and reaches lanes with `--root <lane>`. A hook that cannot save this record (or `director-folders.json`) does not continue silently: it records the failure like a hook crash (a marker in `hook-crashes/`, or the `hook-crashes-unsaved.log` fallback, plus a `HookRecordError` line in `hook-errors.log`), so the hook counts as broken until a later run saves the record, and it says so in its output; its decision about the command itself still stands. For the folder check, a missing file means no hook has run here yet, and nothing is compared, unless the hooks are in use and a hook may have failed to save it (an unresolved hook crash, or crash state Ratchet can't read or save): then every command refuses with a plain message until a hook writes it again. An existing record is not trusted either while a hook failure in that project is unresolved (a crash, or a record a hook could not save: a failed write leaves the old record, which may still name a director) or while Ratchet can't read or save its crash state. Then the folder check refuses every command, and the director commands refuse when this holds for the session's own folder or the target project, until that hook runs cleanly. `status`, `next`, `doctor`, `view` and `install-hooks` only read or repair hooks, so they still run in every one of these cases and say on stderr what is wrong. `accept-state`, the repair Ratchet names for a file or hash record it won't trust, also still runs while a hook failure is unresolved (it needs a person to type back the terminal code, and it is still refused while the record is missing, unreadable or names another folder). The reads exit 1 when the record is missing, unreadable or names another folder. A record without `home` or `key_file`, or an unreadable one, is refused with a message to delete it (the next hook run writes it again). To move the folder on purpose, restart the agent CLI with the new `RATCHET_HOME`, so its hooks record it.

**Damaged records.** Every read of one of Ratchet's own records goes through one reader that never exits or raises (`_read_record`), and every rewrite through one atomic writer (`_write_record`: a temp file named with the process id and a random token, flushed to disk, renamed into place in one step, removed on failure); append-only records (`human_log.jsonl`, the run's `.jsonl` files, `hook-errors.log`, `hook-crashes-unsaved.log`) are only appended to, whole lines at a time, through one appender. The records are `.ratchet/active.json`, the run's `state.json`, `human_log.jsonl`, `prompt-chats.jsonl`, `stop-blocks.jsonl`, `hook-heartbeat.json`, `hook-env.json` and `hook-env/`, `director.json`, `provider-status.json`, `unavailable-reviewers.json` and `viewer.json`, and in `RATCHET_HOME` `file-hashes.json`, `engine-call-sessions.json`, `director-folders.json`, `active-runs.json`, `stop-errors.json` and `enrolled.json`. A record may start with a UTF-8 byte-order mark, which is ignored (it is not damage). A record that is missing, can't be read, is not valid JSON or is not a JSON object reads as "nothing recorded", and Ratchet says so on stderr in one line naming the file, the cause and what it did instead. A record that grants trust grants nothing then: a damaged `file-hashes.json` vouches for no file, a damaged `director-folders.json` names no director folder, a damaged hook record confirms no folder or role, a damaged line of `human_log.jsonl` is no message. A record that holds a restriction keeps it: a damaged `director.json` still enrolls the lane (chat replies approve nothing; `director-enroll` writes it again, which enrolls the lane once more). The per-user `active-runs.json` and `enrolled.json` hold restrictions for other projects and lanes too, so a damaged one is never written over (a write would keep only the writer's entry and silently drop the others): `director-enroll` refuses and changes nothing, `init` and the other commands that register a run leave the file as it is, and stderr and `doctor` name the file and how to repair it (restore it or fix the JSON by hand; or move it aside, after which each project's run is registered again when it next starts, and the director enrolls every lane again). Meanwhile a damaged `enrolled.json` keeps restricting: while a director key exists on this machine, a project with no `director.json` of its own counts as enrolled (chat replies approve nothing; a director token still does). A damaged `active-runs.json` names no run: a deleted Ratchet folder is not noticed until it is repaired. A damaged `active.json` names the run this project registered in `active-runs.json`, when that run's folder is here, and `accept-state` writes it again; damaged per-user counts and caches (`stop-errors.json`, `engine-call-sessions.json`, `hook-heartbeat.json`, the provider files) are replaced by their next write. No hook crashes on a damaged record and no run is left stuck by one: the hooks answer as above, and the repair Ratchet names, `accept-state`, still runs while a hook failure is unresolved (it is refused only while the hook record is missing, damaged or names another per-user folder, which the next hook run fixes). A damaged `state.json` can't be accepted as a baseline: `accept-state` refuses, before it asks for the code, and says to restore it, or to start the feature over with `init --force` (a person at their own terminal); `init --force` treats the damaged run as still active. The stop hook logs each stop it could not check this way to `hook-errors.log` (`StateUnreadable`) and fails closed up to its limit, but writes no crash marker, so it never locks out the commands that repair the run. Files that a person or an agent writes (`config.json`, `checkpoints.json`, `tests/CPn.json`, `reference/`, an agent CLI's own settings) are not Ratchet's records: a damaged one stops the command with a plain message naming it, because only its author can fix it. A test reads `ratchet.py` and fails if any other function reads or writes JSON files, or opens a file for writing, outside the reader, the writer, the appender and a short list of such files.

**Variables a builder session may read but never set.** `RATCHET_HUMAN_OVERRIDE`, `RATCHET_ROLE`, `RATCHET_HOME` and `RATCHET_DIRECTOR_KEY_FILE`. Besides a literal `VAR=`, the guard refuses shell commands that set one through `export`, `declare`/`typeset`/`local`/`readonly`, `setenv` or fish `set -x`, a dict or keyword entry (`os.environ[...] = `, `env={...}`, `dict(os.environ, VAR=...)`), `putenv`-style calls, or indirectly (the name kept in another variable or built from pieces, then used by `eval`, `env -S`, `printf -v`, `${!v}`, sourcing a file, or an `os.environ` write). Plain reads (`$VAR`, `printenv VAR`, `grep VAR` in docs, `os.environ.get`) stay allowed. This is best-effort: a script written to a file first and run later is not seen by the guard, which is why the engine also distrusts each of these values itself: `RATCHET_HOME` and `RATCHET_DIRECTOR_KEY_FILE` must match what the hooks recorded (the folder check above), `RATCHET_ROLE=director` counts only where the guard recorded a director session (`guard_role` and `director-folders.json` above), and `RATCHET_HUMAN_OVERRIDE` needs the terminal code below. Known limit: a script that changes into the director's own folder before running a director command passes the role check, and a script running as the same OS user can edit Ratchet's protected files, read the director key file directly, or forge Ratchet's hook records (`hook-env.json`, `director-folders.json`, the crash markers) by running Ratchet's own hook command with made-up input; no check inside Ratchet can stop that. This is an accepted limit (the user's decision): Ratchet's protections stop an agent from stumbling past a gate or taking an easy shortcut, not a deliberate same-user forgery. The guard blocks the direct routes (writes under `.ratchet/`, any command naming the key file or the per-user folder), and keeping lanes and the director in separate folders keeps the role check meaningful. The guard also refuses a shell command that really runs Ratchet's own hook command (`ratchet.py hook ...`, directly, through python, a wrapper such as `env` or `timeout`, an unknown `$PROGRAM`, `bash -c` or `eval`): only the agent CLI calls hooks. It reads the command as shell words, so text that only mentions a hook (a grep pattern, an echo, a commit message, a comment) is not refused; a command it can't read that way (a command substitution, a heredoc, `$'...'`) is refused whenever it mentions a hook at all.

**`RATCHET_HUMAN_OVERRIDE=1`** is for a person at their own terminal: it never approves anything on its own. The command (`human-approve`, `approve-plan` and the other approvals, `accept-state`, `init --force` over an active run, `choice` without transcript checks) opens the real terminal (`/dev/tty`; `CONIN$`/`CONOUT$` on Windows), prints a six-digit code there and reads it back, in the same process. No terminal (an agent's shell tool runs on pipes), a wrong code, end of input or no answer within 5 minutes (on every OS; on Windows the console is read on a separate thread that is given up after that time) means refused with a plain message, and nothing is recorded. A confirmed override appends `{"at", "by": "human", "override": true, "action", "via"}` to `human_log.jsonl`; such lines are audit records only and never count as a chat reply. The line is written before anything else changes: when it can't be written (the log or `.ratchet/` not writable, a full disk), the command refuses with a plain message and nothing is approved, accepted as a baseline, replaced or recorded as a choice, so an override is never used without its audit line (the line is written by the override check itself, so no command can use the override without it). Known limit: an agent that can start its own pseudo-terminal (pty) and read the code from it could still answer; the guard refusing commands that set the variable covers the usual route, and the record shows every use.

**`hooks` object** (in `status --json`, in `next`, and as the only key of `doctor --json`; read-only, computed for the agent CLI running the command):

| key | type | meaning |
|---|---|---|
| `host` | string | `claude`, `codex`, `gemini`, `copilot` or `unknown` (from `host_provider` / environment) |
| `installed` | bool | a project or user hook config for `host` contains Ratchet hooks |
| `heartbeat_seen` | bool | the heartbeat has an entry from `host` (any host if `host` is `unknown`) |
| `fresh` | bool | such an entry has an `at` timestamp within the last 24 hours and not more than 5 minutes in the future |
| `enforcing` | bool | the guard or stop heartbeat from `host` is fresh, and neither of those hooks broke on its last run. A recent `hook_errors` entry for that event and host, logged at or after its heartbeat (or with no heartbeat for that event), means it crashed, even when the heartbeat is fresh; so does an unresolved crash in `hook-crashes/`, whatever its age. Crashes are judged per (host, event): only a heartbeat or clean run from the host that crashed clears that crash, and with `host` `unknown` any host's unresolved guard or stop crash keeps this false. The next clean run of that hook on that host makes it count again |
| `prompt_hook` | bool | the prompt heartbeat from `host` is fresh and the prompt hook did not break on its last run (it only records the user's replies; it enforces nothing) |
| `missing` | bool | `not installed and not enforcing` |
| `waived` | bool | (`status --json`, `next`, viewer-data `hooks`, plain `status`; not `doctor`) the user chose to build without hooks (`ask hooks-waive`, then `hooks-waive` after their reply, which must be one of a fixed allow-list of full phrases, `HOOKS_WAIVE_PHRASES` in ratchet.py, after lowercasing and dropping punctuation and a trailing \"please\": \"yes go ahead without hooks\", \"yes skip the hooks\", \"yes build without hooks\", \"go ahead without hooks\", \"skip the hooks\", \"proceed without hooks\"; anything else is refused and clears the question; stored in state.json as `hooks_waived {at, by, prompt}`, with a `hooks_waived` history event). True only while no enforcement hook is installed or seen firing: the guard and stop hooks decide, not the prompt hook (which is how the yes is recorded) and not `missing`. Once they are installed or fire, the next state save removes `hooks_waived` (history event `hooks_waive_cleared`; the stop hook makes that save itself when it fires, after one try at the state lock, and otherwise the next command does), so it cannot resurface later without new consent. `hooks-waive` refuses to record anything while they are active. Never blocks anything |

`hooks_warning` (string or null) is null when `enforcing`. Otherwise it tells the agent that a safety hook broke on its last run (run `doctor`, fix the cause, tell the user), that the hooks are installed but silent (restart the CLI), or that none fired yet (offer to run `install-hooks`, ask the user first).

**`hook_errors`** (list, in `status --json` and `next`; `[]` when there are none): hook crashes from `hook-errors.log` in the last 24 hours (and not more than 5 minutes in the future), from the same `host` as the `hooks` object (every host when it is `unknown`), newest first, at most 3. Each entry is `{event, host, at, message}`: `event` is `guard`, `stop` or `prompt`, `at` is the ISO time the crash was logged, and `message` is the logged `ExceptionType: message`, cut to 300 characters (for the agent; never pasted at the user). There is nothing to dismiss: entries age out after 24 hours. Plain `status` turns them into two plain lines (which check failed, how long ago, whether it has run cleanly since, and to ask the agent to run the doctor check), never the raw error text; `doctor` lists them with the raw text. A corrupt or unreadable log, or any line not in the format above, counts as no error. Every other hook that is still unresolved for `host` (in `hook-crashes/` whatever its age, or in the log with no clean run since) gets its own plain line in `status`, naming that hook and its own crash time and consequence, so a newer resolved error never stands in for an older unresolved one (when the list is empty, these are the only lines, followed by asking the agent to run the doctor check); `doctor` lists those crashes.

A corrupt or odd `hook-heartbeat.json` or `config.json` counts as empty here; `doctor` never raises for it.

## 11. Building from a spec tool (OpenSpec, Spec Kit, BMAD)

`ratchet.py spec detect [--json]` lists open items: OpenSpec changes (`openspec/changes/<id>/`, not `archive/`), Spec Kit features (`specs/<NNN-name>/` with `.specify/`; the current one from `SPECIFY_FEATURE_DIRECTORY`, `.specify/feature.json` or `SPECIFY_FEATURE`), BMAD stories (v4: `devStoryLocation` in `bmad-core/core-config.yaml`, default `docs/stories/{epic}.{story}.*.md`; v6: `_bmad-output/implementation-artifacts/{epic}-{story}-*.md` with `sprint-status.yaml`), skipping finished ones.

`ratchet.py spec import <openspec|speckit|bmad|auto> <id…> [--force]` (while planning) writes `reference/spec-source.json` (`{"items": [{"tool", "id", "path"}], "imported_at"}`), a draft `checkpoints.json` and `tests/CPn.json` (unless a plan exists; `--force` replaces it), and adds the tool's standards files to config `standards` (OpenSpec `openspec/config.yaml` / `project.md`, Spec Kit `.specify/memory/constitution.md`, BMAD `docs/architecture/coding-standards.md` or `docs/architecture.md`). `auto` picks the only open item (or the only one matching the ids given).

Refs (stable ids the plan points at):

| Tool | Scenario / criterion (needs a test) | Requirement | Task (needs a step) |
|---|---|---|---|
| OpenSpec | `<change>#req:<capability>/<requirement-slug>/sc:<scenario-slug>` (each `#### Scenario:` under ADDED/MODIFIED) | `<change>#req:<cap>/<slug>` | `<change>#task:1.1` |
| Spec Kit | `<feature>#US1/AS2` (user story acceptance scenarios); `<feature>#FR-001` (a functional requirement is tested itself) | `<feature>#US1` | `<feature>#T012` |
| BMAD | `<story>#AC2` | same | `<story>#task:1` (subtasks `#task:1.2` follow their task) |

Draft plan: one checkpoint per OpenSpec task group (each requirement goes with the group that talks about the same things), per Spec Kit user story (setup tasks in the first, FRs in the last), per BMAD story. Each checkpoint gets `spec_refs` and a `spec` block (`source`, `requirements` with their scenarios) that reviewers see. The draft has no test command, so the planner must refine it before `plan-submit`.

Locking: the spec's requirements, scenarios and task list (not task ticks or status) are part of the plan approval; changing them mid-build stops the run like any other locked file.

Write-back: when a checkpoint completes, Ratchet ticks its `spec_refs` tasks (`- [ ]` → `- [x]`; a BMAD task ticks its subtasks) and commits those files with the checkpoint. When the last checkpoint touching a BMAD story completes, the story's status becomes `Done` (v4) / `done` (v6, also in `sprint-status.yaml`) and a `### Ratchet verification` note (steps, commits, the test proving each acceptance criterion) goes under `## QA Results`. When the run is approved (or finishes in `none` mode), each OpenSpec change whose tasks are all ticked is archived with `openspec archive <id> -y` and committed on its own; without the CLI the change stays open and Ratchet says so. Config `spec_archive: false` turns archiving off.

No spec tool: when a run is approved in a project where `spec detect` finds nothing and config `spec_keep` is unset, `human-approve` (or the last `complete` in `none` mode) prints an `Offer:` line, and the agent asks the user once. `ratchet.py spec keep on|off` records the answer in config `spec_keep`. With it on, every approved run writes `openspec/specs/<run slug>/spec.md` in OpenSpec's format (a `### Requirement:` per completed step with `The system SHALL…` and its done-when list, a `#### Scenario:` per planned test with GIVEN/WHEN/THEN and a `<!-- proven by test CPn-Tnn in <file>, commit <id> -->` note; guardrail steps are left out) and commits it with the config on its own. Answering `on` after a finished run records that run straight away.

`ratchet.py spec status [--json]`: per scenario, its tests, steps and state (`not planned`, `planned`, `proven` once every step covering it is done, `left out: <reason>`), and which tasks are ticked. `viewer-data.json` has the same under `spec`.

## 12. `ratchet.py receipt`

One honest proof receipt to paste into the pull request, run at the final review (see the orchestrator's Phase C). Plain markdown by default; `--json` prints the same facts as data, for anything that wants to read them instead of the agent pasting the markdown. Never posts anywhere and never reads cost or token figures: neither appears in either form.

**Sections (markdown).** Per step: its title, a short commit or `no commit recorded` when `complete` never made or found one, and a plain duration (`"4h 17m"`) or, for a step still mid-build, `not finished (time so far: <duration>)`; under it, its own adversarial review rounds and reviewers. The whole run's own line: a plain duration from `created_at` to the run-level `approved` history event, or, before that event exists, `run not finished (time so far: <duration>)`. Every duration is wall-clock, including any time spent waiting on you, and the receipt says so. Then the findings you accepted (`ratchet.py ask accept-finding` / `accept-finding`, reused from `_accepted_findings_lines`), findings fixed later in the run (CP1's `mark-fixed`, `_fixed_later`), and findings left for later (`left_for_later`), the same grouping `ratchet.py deferred` uses, so the two commands always agree. Every finding printed in these three sections is identified by `_finding_key(f)` (`reviewer/id`, or the bare id when no reviewer is recorded), the same qualified reference `ratchet.py deferred` prints: two reviewers routinely pick the same bare id within one checkpoint, so the checkpoint alone never disambiguates them.

**Commit.** A step's own `commit` field (the one `complete` records) when it has one. When `complete` ran with `commit_per_checkpoint` on but made no commit of its own because the code was already committed some other way before it ran (directly, by the user or agent: the accepted same-user limit), the receipt still names the real commit instead of a false "no commit recorded", by an exact rule, never a date guess: it looks for the one commit, if any, whose own git tree is exactly the tree Ratchet recorded as reviewed for that step — the step's passed adversarial gate's own `fingerprint`, or else its last adversarial round's own `fingerprint` when the gate never passed. A step with `commit_per_checkpoint` off, or where no commit's tree matches what was actually reviewed, still says `no commit recorded`.

**Done-means proof.** Every line of the plan's top-level `objective.done_means`, next to the test case(s) whose own `"proves"` (section 4) names that line: each case's `id`, `title` and `file`, and whether it passed: `"checked by the UI gate"` for a `browser`-layer case (never run by `ratchet.py behavior`). Otherwise the checkpoint's own latest per-case test report in evidence decides it, if that report has any entry naming this case: `"passed"` only when every entry whose name matches this case's id passed, so one failed, errored or skipped entry among several (a parameterized test, or repeated runs) still shows `"failed"`. With no such report, or no entry in it for this case, a supported exit-code-only step (`tests.report` none or missing) still has a recorded result at the step level — the checkpoint's own `gates.behavior` status, checked by exit code only rather than per case. With neither a per-case report nor a recorded behavior-gate status (never run), the case reads `"no result recorded yet"`. A done_means line no case's `proves` names reads plainly `"no test linked"`; no test id is ever invented. A plan with no `objective.done_means` at all (approved before either existed) prints a plain note instead of this section; a plan whose cases carry no `"proves"` fields at all still prints every line as `"no test linked"`, plus one more plain note that this plan's tests were never linked.

**Reviewers.** Built per round from `gates.adversarial.rounds[]`'s own `reviewers` ({"id", "vendor", "model"}, the final set for that round, including any mid-round swap) and `substitutions` ({"used", "instead_of", "why"}). Any reviewer whose roster entry is `"kind": "agent"` (a host sub-agent, the host's own company) is always marked as the host's own company standing in. Its reason: when that round's `substitutions` names it as the `used` reviewer, the `why` text for the reviewer(s) it `instead_of` replaced; when the round carries a `substitutions` key but no entry names this reviewer, or carries no `substitutions` key at all (a round recorded before this field existed), `reason not recorded`, never invented, never left blank. A reviewer whose own roster entry is not `"kind": "agent"` (an outside provider) carries no fallback marking or reason. `--json`'s `reason` is a single string or `null` (never present for a non-host reviewer).

**`--json` shape:**
```json
{
  "run": {"elapsed_seconds": 22200, "finished": true},
  "steps": [
    {"id": "CP1", "title": "Step 1", "commit": "abc1234", "finished": true, "elapsed_seconds": 15420,
     "reviewers": [{"round": 1, "id": "host-alt-standards", "host_fallback": true,
                    "replaced": ["codex-standards"], "reason": "out of credits"}]}
  ],
  "accepted": [{"checkpoint": "CP1", "id": "B1", "reviewer": "codex-standards", "severity": "blocker",
                "description": "unsafe write", "reason": "low risk, tracked separately", "accepted_by": "human"}],
  "left_for_later": [{"checkpoint": "CP1", "id": "S2", "reviewer": "codex-standards", "description": "README is stale",
                       "deferred_because": "deferred as minor, not blocking"}],
  "fixed_later": [{"checkpoint": "CP1", "id": "S1", "reviewer": "codex-standards", "description": "missing a guard note",
                    "round": 2, "how": "added the blocked-state guard, confirmed by the later clean round"}],
  "done_means": {
    "lines": [
      {"text": "A manager can approve or reject a request with a reason, from the Approvals page",
       "cases": [{"id": "CP1-T01", "title": "Manager approves a pending request",
                   "file": "src/server/leave/__tests__/approvals.cp1.test.ts", "status": "passed"}]},
      {"text": "The employee sees the decision and the reason", "cases": []}
    ],
    "any_proves": true
  }
}
```
`done_means` is `null` when the plan has no `objective.done_means` at all (section 3's older-plan case); an empty `cases` list on a line means "no test linked", and `any_proves: false` means not one case in the whole plan carries a `"proves"` field (an old test plan). `steps`, `accepted`, `left_for_later` and `fixed_later` carry the same facts the markdown shows, in the same order the plan's own `checkpoints` list gives (not the order checkpoints finished). `accepted`/`left_for_later`/`fixed_later` carry the finding's own bare `id` PLUS its own `reviewer` (`null` when the finding was never tagged with one): the checkpoint alone never disambiguates two reviewers who independently picked the same bare id within one checkpoint, which is normal (their shared prompt gives every reviewer the identical example id), so `id` and `reviewer` together are this shape's own identity, matching the qualified `reviewer/id` form (`_finding_key`) the markdown prints. `run.finished` and a step's own `finished` are `true` only once the matching timestamp (the run's `approved` event; the step's `completed_at`) is on record; while false, the paired `elapsed_seconds` is time so far, not a final total.

## 13. CI export

`ratchet.py ci-export [--stdout]` writes a GitHub Actions workflow, `.github/workflows/ratchet.yml`, that keeps the mechanical checks a run relied on running on every push and pull request: config `regression_command` first, then every `checks[].command` (section 8, in saved order), then, only when there is no `regression_command`, a completed checkpoint's own `tests.command` across every run under `.ratchet/runs/`. Exact duplicate commands collapse to their first occurrence. The AI review gates (adversarial, UI, human review) are never part of this: the workflow's header says so and why (CI machines have neither the agent CLIs nor the credentials those gates need).

Ownership is decided only by the file's first line, a fixed marker comment. A file at that path without the marker (hand-written, or written by another tool) is never touched: `ci-export` refuses, names the path and suggests `--stdout` so the agent can print the workflow and show it to the developer instead. With the marker already there, running `ci-export` again updates the file in place when the commands changed, and says it is already up to date, byte for byte, when they did not. `--stdout` prints the same bytes to stdout and writes nothing, whether or not a file already exists at that path.

`ci-export` never starts an app, a database or anything needing secrets; a command that looks like it needs one (config `app.start_command` or `app.url` set) gets a comment in the workflow instead of a guess. Setup steps (checkout, then Python and/or Node, picked from the project's own files) come before the commands; nothing here is platform-specific to GitHub Actions in how commands are gathered, so another CI platform can reuse the same list later.

At the end of a run, right when it finishes (the final `human-approve`, or `complete` itself when `human_review` is `none`), Ratchet prints one line telling the agent it can run `ratchet.py ci-export` to keep these checks running in CI, and asking it to mention that to the developer in plain words. This opens no question (`pending` stays empty) and never repeats on a later `status` or `next` read; it is also silent when there is nothing to export, or when `.github/workflows/ratchet.yml` already matches what `ci-export` would write.
