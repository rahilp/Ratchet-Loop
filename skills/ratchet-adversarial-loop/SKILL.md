description: Runs the Ratchet adversarial code-review gate — independent reviewers (another company's model through any registered agent CLI whenever one is available and working, otherwise the host's company on a different model, otherwise the host's own sub-agents) assume the checkpoint's code is wrong and hunt for violations of the written standards and for correctness/security bugs; a separate fixer fixes every blocking finding; tests (and UI review, if visible code changed) re-run; every reviewer re-reviews the new code; repeat until no blocking findings remain. Risk decides how many reviewers look and, on low-risk steps, that only blocker and major findings block. Use at Gate 3 of the Ratchet loop, or whenever the user wants a hostile, multi-vendor review-and-fix loop on a change rather than a one-shot code review.

# Ratchet Adversarial Loop (Gate 3)

At this point the feature works and looks right. This gate checks whether the code underneath is any good. It only works if there's a **written standard** to enforce. A reviewer without a standard just gives opinions; a reviewer with one gives findings.

```bash
RUN=.ratchet/runs/<slug>
ADV="python3 <this skill's base directory>/scripts/external_review.py"
```

## Standard to enforce
Sources come from config `standards`, in order: `.ratchet/standards.md` (drafted by ratchet-app-scout, then edited by the human), `CONTRIBUTING.md`, `ARCHITECTURE.md`, lint configs, `DESIGN.md` §8 for UI code, and `.ratchet/learnings.md`. If `.ratchet/standards.md` is missing, spawn `ratchet-app-scout` in standards-only mode first.

## Realistic-use bar
Every reviewer's prompt opens with the plan's objective: who this project's users are, what they want, what done means, and what is out of scope. Judge every finding against that objective, not against some other project's users; findings stay aimed at the users and goal it names. A finding must describe real harm to those users in realistic use of this project, with a concrete scenario; severity follows real user harm — blocker or major only when users of this project would actually be hurt in normal use. What's out of scope comes from the objective's `out_of_scope`, and it differs by project: deliberate same-user evasion of Ratchet's own checks (split or encoded names, planted option-shaped files, comment or quoting tricks) is an accepted limit, out of scope for Ratchet's own plans and at most minor, but a public-facing project's plan can and should treat malicious users as in scope. Every finding needs `user_impact` (who is hurt and how, in normal use) to go with its severity; a blocker, major or unknown-severity finding with no `user_impact` is recorded for the final review instead of blocking, at any round and any risk (`ratchet.py deferred`). A run whose plan carries no objective (approved before this existed) still reviews normally, falling back to the project's own `standards.md` for who the users are and what's out of scope, with a plain note that none was stated.

## Who reviews: a different company first, at every risk level
Each checkpoint has a `risk` (`low` / `normal` / `high`, set by the planner). Risk only decides **how many** reviewers look: config `review_depth` gives each risk a list of review slots (defaults: low 1, normal 2, high 4). **Who** fills a slot is the same at every risk level:

1. **Another company's model**, if one is available and capable: any agent CLI registered under config `providers` (Codex, Gemini, Claude, Copilot, Cursor, OpenCode or your own command). A company not yet reviewing this round is preferred.
2. Otherwise **your own company on a different model** (`host-alt-*`): a `ratchet-adversary` sub-agent you spawn with a model other than yours (config `host_models.alternates`, e.g. Sonnet when you are Opus).
3. Otherwise **you, on your own model** (`host-*`).

**The host** is whichever model runs this loop (auto-detected, or `host_provider` in config). A provider counts as available only if its tool is installed, its company is known and differs from the host's, it is allowed for this risk (`for_risk`), and it answered a small **test request** recently: `ratchet.py reviewers` sends one before relying on a provider it hasn't checked in the last `probe_ttl_minutes`, so a tool that is signed out or out of quota hands its slot on at once. A provider that fails mid-review is marked unavailable for `unavailable_ttl_hours` (default 6) together with every reviewer using the same tool. **A missing or failing provider never stalls the loop.** (For a high-risk checkpoint with nothing but the host available, the count of distinct reviewers can be smaller than the slots.) `ratchet.py providers` shows the picture, `providers --discover` finds and tests installed tools, picking and testing one flat-rate other-company model itself for a tool that runs several companies' models (listing any per-use or unknown-cost one instead, for the agent to ask the developer about first), `providers --add` registers one (with `--model` for tools that run several companies' models). Every substitution is logged in the run history, and the plan, the viewer and `reviewers` name who reviews each round.

`$RATCHET reviewers CPn` resolves the slots for this round. It prints who must review, which alternative each one replaced and why, the model for each `host-*` sub-agent, the round's review rules, the fingerprint, each reviewer's output path, and the command or sub-agent to launch. **Always start the round with it, and re-run it if a reviewer exits with code 3** (unavailable): the slot will have moved to the next alternative.

**Duplicate slots run once.** When two slots would resolve to the same company, model and lens (the same reviewer under a different id), the second one collapses: it runs once, and `adv-record`'s approval message shows the real number of reviewers it needed — "all 1 reviewer(s)", not the two configured slots — so the loop's own bookkeeping never counts one review twice.

## What blocks
- **Severity bar by risk** (config `blocking_severities`). On a **low-risk** checkpoint only blocker and major findings block; minor ones are recorded for later (`ratchet.py deferred`) and shown to the user at the final review. Normal and high risk: every finding blocks.
- **Later rounds look at what changed** (config `scope_later_rounds`). From round 2 on, a minor finding only blocks if it is in code changed since the previous round; blocker and major findings block anywhere. This keeps each round from turning into a fresh review of everything.
- **Minor findings stop blocking from a configurable round** (config `converge_after_round`, default 2, meaning round 3 on). From round `converge_after_round + 1` on, a minor finding never blocks any more, whatever its scope; it's recorded for later instead. Blocker and major findings always block, at every round. This is what makes reviews converge instead of turning into an endless hunt for ever-smaller nits.
- Severities other than the known minor ones (minor, nit, nitpick, trivial, low, info, suggestion, style) always block, so a made-up severity can't slip past. A finding with no file, or a file Ratchet can't place, counts as in scope.
- A file that had a blocking finding last round stays in scope, so a finding the fixer didn't fix is judged in full again.
- Adding or changing a provider that runs its own command (not a preset), or changing `host_models` / `role_models`, after plan approval needs the user's yes (`ask approve-changes`), like any other rule. `approve-changes` also validates and registers any checkpoint hand-appended to `checkpoints.json`, the same way `plan-extend` does for feedback-appended ones.
- Pass the round's review rules (printed by `reviewers`) to every `host-*` reviewer you spawn; `external_review.py` adds them to other providers' prompts itself.

## The loop (round k = 1, 2, …)

1. **Plan the round.** `$RATCHET reviewers CPn`. It stamps the fingerprint and lists the reviewers. A review of older code is rejected later. A round replaced before any review was written is free: it doesn't count toward either round cap (the code changed again before anyone reviewed it). A round where at least one review was written still counts, even if `adv-record` was never run on it.
2. **Launch every listed reviewer in parallel.** Each one starts with a fresh context.
   - `kind: agent` (`host-*`) → spawn a `ratchet-adversary` sub-agent with the model `reviewers` names (for `host-alt-*`: one of the alternates that is NOT your own model), its `lens`, its **reviewer id**, the fingerprint, the round's review rules and its output path. Don't give it the implementer's reasoning, the test results, or earlier rounds' findings.
   - `kind: command` → run `$ADV --reviewer <id> --cp CPn --out <path>` (add `--fixes <fixes.md>` from round 2 on). The script gives the other provider's CLI the adversary instructions, the standards, the learnings and the full diff inline, runs it read-only, and writes normalized findings JSON stamped with the fingerprint. When the diff is too large to include whole, files changed since the last round a reviewer actually reviewed come first, and the prompt names by file anything still left out. **A reply cut off mid-answer is retried once**, automatically, before anything counts against the reviewer — the script tells a cut-off (an incomplete JSON object) apart from a genuine failure and reruns the same CLI call itself; nothing to do here but wait for it. If the retry is cut off too, only **that reviewer's own slot** falls back this round (its provider is not sidelined for hours, unlike a real quota/auth/timeout failure, and any review another slot already finished in the round is left untouched). **Exit code 3** means that provider (or, for a persistent cut-off, just this one reviewer) is unavailable for this round and has been marked so (also when its CLI takes the prompt as a command-line argument and this round's prompt is too large for one: it is not started, and a provider `command` that reads `{prompt_file}` or stdin avoids that). Re-run `$RATCHET reviewers CPn` and launch whichever reviewer now fills that slot (possibly a `host-*` sub-agent).
   - From round 2 on, every reviewer gets `fixes.md` so it can withdraw a finding the fixer disproved with evidence. Otherwise each round is a fresh, hostile look.
3. **Record.** `$RATCHET adv-record CPn --reviews <all output files>`. A review from another provider counts only when `external_review.py` signed it for this round (it signs with a per-round secret Ratchet keeps outside the project); one typed, copied or edited by hand is refused as unsigned. Never write or touch a review file yourself. A host ratchet-adversary sub-agent's review is not signed, and the sub-agent must write it with the Write tool, not through the shell. On Claude Code the guard confirms that the sub-agent wrote it, and a file written any other way (by the main session, through the shell, or by hand) is refused as unsigned. On Codex, Gemini and Copilot, or with the hooks waived, Ratchet can't tell who wrote it: any file in the round folder with the right nonce and code version counts, even one typed by hand, and `status` and the viewer show it as "not independently confirmed".
   - It refuses if any required reviewer is missing, or if any review is of a different fingerprint.
   - It refuses any review that is not directly inside this round's own folder, `$RUN/reviews/CPn/adv-round-NN/` (`reviewers` prints it). Links and `..` paths are resolved first, and a file from an earlier round's folder doesn't count. If a reviewer wrote somewhere else, launch it again with its output in that folder.
   - No required reviewer has a blocking finding (see "What blocks") → **approved**, and `next` says `complete`. Minor findings that didn't block are kept in `deferred-findings.json` for the final review.
   - Otherwise ratchet.py writes `evidence/CPn/adversarial/round-NN/open-findings.json`, with each finding tagged by reviewer. (NN = the current round, zero-padded: 01, 02, ...)
4. **Triage.** However many findings are still open, decide fix or rebut for every one of them FIRST, tied to the objective: `$RATCHET triage CPn <ref>=fix:"<reason>"` or `<ref>=rebut:"<reason>"` (`<ref>` from `open-findings.json`, same id rules as accept-finding; any number in one call). `fix`, `rebut` only — never `accept`, `defer` or `waive` here; that needs the user's own reply (`ask accept-finding`). `$RATCHET reviewers CPn` refuses to open the next round until every one has a decision, a single remaining finding included.
5. **Fix.** Spawn `ratchet-fixer` with the `fix-list.json` step 4 just wrote, never `open-findings.json` directly. It makes the **smallest change that resolves each finding**, adding no new mechanism or file unless the finding itself needs it; when a proper fix would need a redesign instead, it stops and says so rather than improvising one, which opens a check-in (below). It fixes **every** finding it was handed, from every vendor, or writes an evidence-backed rebuttal in `$RUN/reviews/CPn/adv-round-NN/fixes.md`, touching nothing unrelated. The orchestrator may instead offer the user `$RATCHET ask accept-finding CPn <ids>` for the ones they'd rather accept as a known limit than fix (see the orchestrator skill); only the user's own `accept: <reason>` reply records that, never the fixer or the orchestrator on its own.
6. **Re-prove.** `$RATCHET behavior CPn`. If it fails, send the log to `ratchet-fixer`, since the fix broke it. (A failure that passes clean on one immediate automatic re-run is marked flaky and passes without spending an attempt, once per step; a second one is a real failure like any other.) If the fixer touched UI files, re-run the `ratchet-ui-compare` gate.
7. Go to step 1 with the next round (NN+1). Round 1 always asks every lens. From round 2 on, only a lens with an open blocker or major finding is re-run; a lens that approved last round sits this one out. If the fix still leaves a blocker or major open, the round after THAT one brings back the full set again, rather than narrowing further — a stuck finding gets every lens looking, not just the one that's been staring at it. A round whose own file carried a `rebut` decision tells its reviewer so (in the round's review rules), and it either withdraws the finding or re-raises it with a stronger `user_impact`.

The loop ends only when **all** required reviewers (that round's narrowed or full set) approve the **same, current** code. `ratchet.py complete` re-checks this.

## Quota guards
- `max_adversarial_rounds` (per checkpoint) and `max_adversarial_rounds_run` (whole run) both **block and escalate** to the human or director. They never lower the bar. At a step's own round limit, the options Ratchet offers lead with simplify, then change the step, then stop; accepting the open findings is offered separately, as its own plain line, never one of these lettered picks. Raising the limit comes last, and only once per step, ever, with the user's own reason: `$RATCHET ask raise-limit CPn`, then only their exact `raise: <reason>` reply in the run's owning chat raises it by one round, appends that reason to `.ratchet/learnings.md`, and records this step's own cap; a later `config --set max_adversarial_rounds=...` never lifts that recorded cap, and the step is never offered a second raise. Blocking is the right outcome when review quota is scarce: the director decides whether to raise the cap, lower a checkpoint's risk, or split the checkpoint.
- Don't spend high-risk depth on skeletons: a checkpoint's risk is set in the plan, and the human sees it at plan approval.

## Check-in: when reviews drag
Right after a round is recorded still blocking, Ratchet itself (not you) decides whether reviews have been dragging: either this is the `checkin_round`'th round in a row to block (config, default 2), or this is the second round where a blocking finding's `kind` was never seen before in this step shows up in a file an earlier round already flagged. Either way it opens a check-in (once per trigger per step) and refuses the next `$RATCHET reviewers CPn` until it's answered. Run `$RATCHET check-in CPn` (no flag): it prints the objective's goal and users, every still-open blocking finding from the gate's latest recorded round (minus anything already accepted) with its `user_impact`, how many rounds this step has used, the kinds grouped by file, and three options. Before picking one, spawn a fresh strong-model reviewer (a sub-agent with no history in this round, never you continuing your own reasoning) with the objective, this brief's open findings and the round history, and have it recommend simplify, accept or stop; you never decide a check-in from your own reasoning alone. Tied to its recommendation:
- **Simplify** (A): narrow or change the step so the review notes stop applying. Record it with the strong-model reviewer's reasoning (no user question, this doesn't lower the bar): `$RATCHET check-in CPn --decision simplify --why "<its reasoning>"`.
- **Accept** (B): you cannot do this, whatever the reviewer recommends. Say so, and offer the user `$RATCHET ask accept-finding CPn <ids>` instead (above); only their own `accept: <reason>` reply closes a finding. `check-in --decision accept` is refused outright.
- **Stop** (C), or the strong-model reviewer isn't sure: `$RATCHET check-in CPn --decision stop` moves the run into the normal blocked/ask flow; put the quoted findings and lettered options to the user the same way as any other block.

## Guardrails
- Findings are never waived by the orchestrator. The human or director decides at a block, and that decision usually becomes a line in `standards.md` or `learnings.md`. The user, and only the user, can also accept named open findings of a blocked round directly, with their own reason, through `$RATCHET ask accept-finding CPn <ids>` then `$RATCHET accept-finding CPn` once they reply `accept: <reason>` (a bare id shared by two reviewers' findings is refused as ambiguous; say `reviewer/id` instead); that is recorded in `learnings.md`, the step's deferred findings and the round's own record, same as any other block decision, and it never applies to a later round's findings once the code changes. In a director-enrolled lane a chat reply never accepts a finding: `director-sign accept-finding` must sign it instead, the same as every other approval there.
- When the same `kind` of finding turns up in a second place (another file or checkpoint), `adv-record` prints `REPEAT:`. Offer the user a guardrail straight away (see "When the same mistake repeats" in the orchestrator skill): an automatic check, built as its own step, that then runs with the tests so that mistake fails in seconds instead of costing review rounds. For a kind a check in config `checks` already covers, minor findings are noted instead of fixed; blocker and major ones still block, and also mean the check let a case through: Ratchet adds a step to strengthen it automatically (`STRENGTHEN:`), and you tell the user in one line.
- Adversaries don't fix, and fixers don't review. Keeping the roles separate is what makes the loop adversarial.
- Each reviewer writes its own review file. Never write, copy or edit one yourself, even to transcribe what a reviewer said. Where the host names the acting sub-agent on each tool call (Claude Code does; Codex, Gemini CLI and Copilot CLI currently don't, so there it is on you), the guard blocks anyone but a `ratchet-adversary` sub-agent from writing `adv-round-NN/*.json`. If a reviewer didn't write its file, launch it again.
