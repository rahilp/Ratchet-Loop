# Standards for the Ratchet Loop plugin

1. The engine is a single stdlib-only Python 3.8+ script; add no third-party imports. Example: skills/ratchet-orchestrator/scripts/ratchet.py (`from __future__ import annotations`).
2. Gate state changes only through `ratchet.py` subcommands (`cmd_*`), never by hand-editing state.json, evidence or the human log. Example: cmd_behavior in ratchet.py.
3. Gates verify evidence themselves (run tests, recompute verdicts); never trust an agent's claim of PASS. Example: cmd_behavior, cmd_ui_record, cmd_adv_record.
4. Every gate pass is stamped with the code fingerprint and goes stale when code changes. Example: cmd_fingerprint.
5. Human approval is accepted only from a real user message recorded by the UserPromptSubmit hook; no agent message, env var or flag may impersonate it. Example: cmd_human_approve.
6. The PreToolUse hook must block hand-edits to protected state, nested agent sessions and director key access. Example: hooks/hooks.json and the `hook` handler in ratchet.py.
7. Stay provider-neutral: no code path or doc may assume Claude is the host; use `host_provider` and the reviewer-selection logic. Example: cmd_reviewers in ratchet.py.
8. Every hook payload dialect (Claude, Codex, Gemini, Copilot) must be handled with a test in tests/test_hooks.py.
9. A new provider or host is added by extending the adapter tables, not by branching in gate logic.
10. When no other-provider reviewer is available, fall back to host sub-agents and log the substitution; never stall or lower the bar. Example: cmd_reviewer_status.
11. Errors exit through `die(msg, code)` with an actionable message; no bare tracebacks for user errors. Example: `die` in ratchet.py.
12. Persist state via `save_state` on the run object, not ad-hoc json writes. Example: `save_state` in ratchet.py.
13. Subprocess calls use argument lists (no shell=True with interpolated input) and explicit timeouts for external CLIs. Example: skills/ratchet-adversarial-loop/scripts/external_review.py.
14. Secrets (viewer token, director key) never appear in process lists, logs or served files. Example: "token not visible in the process list" in tests/test_viewer.py.
15. The viewer serves only whitelisted run artifacts; tests must assert what is NOT served. Example: tests/test_viewer.py.
16. Viewer/dashboard HTML is a single self-contained file with no external network dependencies. Example: skills/ratchet-orchestrator/assets/viewer.html.
17. Background servers must be stoppable (`--stop`) and leave no process behind; tests verify this.
18. Skills are markdown with YAML frontmatter (`name`, `description` with trigger phrases); the name matches the folder. Example: skills/ratchet-tdd-planner/SKILL.md.
19. Agents are markdown in agents/ with frontmatter `name`, `description`, `tools`; name is `ratchet-<role>`. Example: agents/ratchet-fixer.md.
20. Agents state a bounded return format (e.g. "Return ≤10 lines") and stay in their role; reviewers do not fix, fixers do not review.
21. Data file shapes are defined once in skills/ratchet-orchestrator/references/schemas.md; change the schema doc together with the code that reads/writes it.
22. Tests are never weakened, skipped or deleted; planned test IDs (`[CPn-X01]`) must remain present.
23. Tests are runnable scripts (`python3 tests/test_x.py`) using a `check(name, cond)` helper, exit non-zero on failure, and build a throwaway project in a temp dir. Example: tests/test_hooks.py.
24. Tests must not touch the real .ratchet/ of the repo; use tempfile projects and clean up spawned servers.
25. Behavior changes to ratchet.py need a test in tests/ in the same change.
26. README.md and the plugin manifests (.claude-plugin/plugin.json, .codex-plugin/plugin.json) stay in sync with what the skills and agents actually do.
27. UI reviewers are isolated (screenshots, a11y trees, DESIGN.md only); never pass code, CLAUDE.md or chat to them. Example: skills/ratchet-ui-compare/scripts/ui_review.py.
28. Never commit .ratchet/ run state or __pycache__.
29. Realistic-use bar for every review finding. Ratchet's users are developers running it on their own projects with a cooperative coding agent that may cut corners (skip a test, mark its own work, hand-edit a gate to get unstuck), not an attacker. A finding must describe something a well-meaning agent or a normal developer setup would plausibly hit, with a concrete scenario. Severity follows real user harm: blocker or major only when a user would be hurt in normal use. Commands or files built to evade a check on purpose (split or encoded names, planted option-shaped file names, comment or quoting tricks, loader variables) are out of scope under the accepted deliberate same-user forgery limit; at most note them as minor. The guard is an early friendly warning; the state tamper check is the backstop.
30. Converting a slow integration suite: in-process engine calls instead of per-call subprocesses. A test suite that drives the engine (skills/ratchet-orchestrator/scripts/ratchet.py) by shelling out to a fresh `python3 ratchet.py ...` subprocess for every single command pays that interpreter-startup-plus-module-compile cost (the engine is one large stdlib script, tens of thousands of lines) again and again, once per call, which is what made tests/test_trust_cp5_e.py, tests/test_trust_cp5_d.py and tests/test_quota_shared.py each take on the order of 15 minutes. The fix used across those three conversions is: import the engine module exactly once per test process with `importlib.util.spec_from_file_location` / `module_from_spec` / `exec_module`, memoize that loaded module object (for example with `functools.lru_cache`, see tests/trust_helpers.py's `cp5y_load_engine()`), and have every call in the suite reuse that same module object instead of launching a new interpreter. Each "call" then becomes a direct invocation of the module's own CLI entry point (its `main([...])` function) inside a small context manager (see tests/trust_helpers.py's `InProcessCall`) that: changes the working directory to the test's temp project, swaps `os.environ` for the call's own env dict, and redirects `sys.stdout`/`sys.stderr` (and `sys.stdin` when a case needs piped input) to `io.StringIO()` so the captured text and exit code look exactly like a `subprocess.CompletedProcess`'s `stdout`/`stderr`/`returncode` to the rest of the test. Because `main()` exits through `SystemExit` rather than `return`, the context manager must catch `SystemExit` itself and read its `.code` as the returncode, while still letting other `BaseException` subclasses (`KeyboardInterrupt`, and any future non-Exception misuse) propagate past the call site the same way a real subprocess dying to Ctrl-C would stop the whole suite rather than just fail one command. Two more things this pattern must get right or it silently corrupts later calls in the same process: (1) the engine keeps module-level globals that one command call can leave set (`_IN_HOOK`, `_OVERRIDE_CONFIRMED`, `_CHAIN_REBUILD`, etc.); the context manager must reset each to its known default both before AND after the call, because a command that raises partway through can leave one set and the next call might not go through the same context manager at all; (2) anything that calls real wall-clock `time.sleep` inside a retry or lock-wait loop (for example a per-record file lock) must have that wait capped for the test process (see `DEFAULT_LOCK_WAIT_CAP`), since no test asserts a minimum wait, only an upper bound or a refusal, so shortening the wait never weakens what the test proves. This technique only applies to cases whose assertion is about the engine's own command logic; a case whose real point is a genuine subprocess boundary (cross-process file-lock contention, a real pty/interactive run, an actual CLI exit code from a separate process) must keep a real subprocess and is out of scope for this conversion. The next slow integration suite in this project should be converted the same way: load the engine module once per process, reuse it for every call, and wrap each call in an in-process context manager with this same reset-globals/lock-wait-cap/SystemExit-capture contract, rather than inventing a new mechanism.
