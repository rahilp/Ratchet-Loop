# Ratchet learnings

Every Ratchet agent reads this file before starting work. Entries come from human reviews and repeated gate failures.

- (2026-09-29, gate:adversarial) Adversary reviewers must write their findings JSON file themselves with the Write tool (even when approving); returning text only stalls the round.
- (2026-09-29, gate:adversarial) Do not gate user-consent on keyword heuristics; use an exact-phrase allow-list printed in the question.
- (2026-10-04, human) Accepted limit (user decision, CP1 of the trust-holes run): Ratchet does not promise to record a hook crash when the crash-record folder is not a real folder (for example a broken symlink) and every fallback write also fails at that moment. This is documented in schemas.md; reviewers should not block on that case.
- (2026-10-04, human) Accepted limit (user decision, CP4 of the trust-holes run): Ratchet's protections stop an agent from stumbling past a gate or taking an easy shortcut, but a deliberate same-user script can still forge Ratchet's records, for example by calling Ratchet's own hook command directly with forged input. The README states this plainly. Reviewers should not block on deliberate same-user forgery of hook calls or hook records; they should still block on easy or accidental bypasses.
- (2026-10-04, gate:adversarial) When a step changes how Ratchet behaves (what counts as a reply, which commands need a question, what a hook does), update every place the docs describe it in the same step: README, every SKILL.md that mentions it, and schemas.md. Grep for the command or rule name before finishing.
- (2026-10-04, human) Accepted limit (user decision, CP5 of the trust-holes run): Ratchet's engine cannot check that the approval question was shown to the user alone in the agent's message. The skill instructions require asking it alone, at the end of its own message, and the docs say plainly that the engine cannot verify this. Reviewers should not block on the engine not verifying what the agent displayed.
- (2026-10-04, human) Known limits and set-aside items (user decision, CP5 round 6 of the trust-holes run): (1) the hook-call guard does not recognise every wrapper form that takes an option value (env -u X, sudo -u me, timeout -s KILL 10, uv run, python3 -m) or a hook call inside a heredoc body; this falls under the accepted same-user-forgery limit. (2) When the prompt or stop hook cannot take the state lock, the message it shows may be generic rather than naming the exact cause. (3) The lock's busy message may misreport a stale lock it just cleared. These are recorded for later and should not block reviews. Still must be fixed: long engine commands must not overwrite an approval made while they ran, and the README must say a reply can go unrecorded and needs resending.
- (2026-10-04, human) Design decision (user, CP5 round 7 of the trust-holes run): concurrency in the engine is handled by serialising, not merging. Every Ratchet command that changes a run holds the state lock for its whole duration, including test runs. The prompt hook does not write run state (it keeps its own records), and an approval that arrives while another command holds the lock is refused with a plain 'busy, send it again'. Prefer this simple rule over merge logic.
- (2026-10-05, human) Product requirement (user, Oct 5 2026): review loops must converge cheaply. In the trust-holes run the review limits had to be raised several times (CP1, CP5 twice, run budget 30 to 50); developers will not burn tokens on reviews that keep finding narrower edge cases. The cost-levers run must make reviews converge (for example: minors stop blocking after round 2, fewer reviewers after round 1, incremental diffs, small fix rounds, earlier accept-a-limit prompts, budget shown up front).
- (2026-10-05, human) Decision (user, CP6 round 2 of the trust-holes run): (1) A plan step without a tests.report setting keeps exit-code checking; this is acceptable because plan-summary, status and next show it plainly as 'checked by exit code only'. Reviewers should not block on this. (2) Test-weakening detection after the red run is structural, not heuristic: a planned test's body may not change and no later definition may reuse its name (AST for Python, test-block boundaries for other languages). A deliberate same-user edit that gets past this is an accepted, documented limit; reviewers should not hunt for more line-pattern bypasses.

- (2026-10-19, gate:adversarial) tests/test_trust_cp5_d.py and tests/test_trust_cp5_e.py are genuinely slow (close to or over 900s) when run in isolation (not under load -- reproduced identically on the pre-modularization baseline commit), because they spawn dozens of fresh python3 subprocess invocations of the 21,000+ line ratchet.py. - (2026-10-19, gate:adversarial) Correction to the earlier test_trust_cp5_d/e slowness learning: raising ratchet.py config's test_timeout_sec does NOT fix a checkpoint test that nests a full run of one of these heavy files inside itself via subprocess.run -- that config only bounds ratchet.py's OWN outer invocation of a checkpoint's tests.command. tests/run_all.py has its own separate default (DEFAULT_TIMEOUT=900s) applied per suite, used whenever tests.command does not pass --timeout explicitly, and that is the real governing limit for a single suite's wall-clock budget, nested subprocess calls included. The actual fix: add --timeout <N> to the checkpoint's own tests.command in checkpoints.json (done for CP2: '... --timeout 2700'). A future checkpoint (CP3/CP5) that nests these same heavy files in its own test file needs the same --timeout bump in its own tests.command, not a project-wide config change.
- (2026-10-19, gate:adversarial) ratchet.py's own _run_cmd and _run_check_in build subprocess env as CI="1", FORCE_COLOR="0" to disable argparse color leaking into captured test/check output, but on Python 3.14 this doesn't work: CPython's _colorize.can_colorize() treats FORCE_COLOR as presence-based, so "0" still forces color ON, not off. This can intermittently colorize any output this engine captures and compares exactly, independent of any checkpoint's own change. Director decision (confirmed): out of lane M's scope (behavior-preserving modularization only); queued as its own fix for a tranche-2/follow-up lane. The working fix (verified in this run's own test files): use PYTHON_COLORS="0" (checked first in can_colorize(), reliably forces color off) and/or NO_COLOR="1", not FORCE_COLOR="0" alone.
- (2026-10-19, gate:adversarial) A checkpoint's own 'the complete local suite passes after this checkpoint' planned case (this run's done-means #5, e.g. CP2-T13/CP3-T13/CP5-T12/CP6-T20/CP7-T15/CP8-T17) must never hard-fail the whole suite's exit code just because .ratchet/runs/<run>/evidence/CPn/regression.log doesn't exist yet -- that log is written only by `ratchet.py complete CPn`, which can only run AFTER `behavior CPn` (which runs this same test file) has already passed, so requiring it to exist at behavior-gate time is a real, unrecoverable deadlock (hit and fixed in CP2-T13). Correct pattern (matching CP1-T10's working design): missing log -> pass (nothing to check yet, not a failure, since ratchet.py complete already structurally refuses to mark a checkpoint done if its own regression run fails -- that's done-means #5's real enforcement mechanism); log exists and parses with 0 failed -> pass; log exists but shows >0 failed or is malformed -> fail (this remains a real, meaningful check). Future checkpoints' test-writers (CP3, CP5, CP6, CP7, CP8 all carry the same risky given/when/then wording in their already-written test plans) must implement their own analogous case this way, not by requiring the not-yet-written log to exist.
- (2026-10-19, gate:adversarial) Correction/addition to the earlier CP2 timeout learnings: a checkpoint's test file that nests a BARE subprocess.run(...) call to one of the heavy pre-existing trust files (test_trust_cp5_d.py/_e.py/test_quota_shared.py) needs its OWN explicit timeout raised too (e.g. timeout=3600), separate from and in addition to run_all.py's own --timeout flag on the outer tests.command in checkpoints.json -- the outer --timeout only bounds run_all.py's per-suite watchdog around the WHOLE file, never a bare subprocess.run call made from inside that file's own Python code, which has its own independent timeout= argument. Missing this (as CP2-T12 did at first, hardcoded timeout=600) crashes with TimeoutExpired under real load even after the outer timeout is fixed. Future checkpoints that nest these heavy files (CP3, CP5, CP6, CP7, CP8 per the earlier learning) must raise BOTH timeouts, not just the outer one.
- (2026-10-20, gate:adversarial) Director steer for CP3..CP9 (applies starting CP3, confirmed): (1) Never nest a full subprocess re-run of the heavy pre-existing suites (test_trust_cp5_d.py/_e.py, test_quota_shared.py, ~990s each) inside a checkpoint's own test file -- the full suite ratchet.py complete already runs them once project-wide; nesting them again inside the per-checkpoint file doubles total time for no benefit. (2) Front-load every lesson below into each checkpoint's test-writer brief UP FRONT (not discovered after a failed run): any subprocess comparing --help/argparse output needs env NO_COLOR=1, PYTHON_COLORS=0 (Python 3.14 argparse color leak; FORCE_COLOR=0 alone does NOT work, it's presence-based); checkpoints.json's own tests.command needs --timeout 2700 on its run_all.py invocation AND any bare nested subprocess.run elsewhere in the test file needs its own timeout>=3600 (these are two separate, independent timeouts); a new tests/test_modularize_cpN.py file must be added to README.md's alphabetical Reference command list (CP6-T05's own check) in the SAME checkpoint that creates it; any source-inspection test checking 'where is function X defined' must be re-pointed to also check the new module file, not just ratchet.py. - (2026-10-20, gate:adversarial) Critical addition to the regression.log pattern (CP2-T13 and its analogues for CP3/5/6/7/8/9): a checkpoint's own file is ALSO run as one of the small related-tests pre-check files (tests/run_all.py {files}, capped by related_tests_max, currently 8) that ratchet.py complete runs BEFORE its own real regression_command (tests/run_all.py with no args, ~115 suites). If that checkpoint's 'full suite passes' case blindly reads evidence/CPn/regression.log whenever it exists, it will read a STALE log from an earlier complete attempt (possibly one that failed for unrelated reasons, e.g. machine contention from another lane) during THIS pre-check, fail the pre-check, and block complete from ever reaching the point where it would overwrite that log with a fresh result -- a self-poisoning loop, not a one-time deadlock. Fix (applied in CP2-T13): before inspecting the log, check tests/run_all.py's own RATCHET_RUN_ALL_SUITES env var (comma-separated list of every suite in THIS run_all.py invocation); only treat the log as meaningful when that list's length is large (>= half the on-disk tests/test_*.py count, a self-adjusting threshold) -- i.e. this really is the full regression_command run, not the related-tests pre-check or a standalone direct invocation. When absent or small, skip straight to the same 'nothing to check yet' pass the missing-log case already uses. Every future checkpoint's own 'full suite passes' case must apply this same suite-count gate, not just check log existence.
- (2026-10-20, gate:adversarial) Refinement to the related-tests self-poisoning fix: don't gate a checkpoint's regression.log trust on a fixed ratio of the total test-file count (e.g. half of ~115) -- that breaks if .ratchet/config.json's related_tests_max is ever raised at or above that ratio, since the pre-check's own suite count could then cross into the 'large/trust it' bucket while still being the pre-check. Instead read the project's ACTUAL configured related_tests_max value directly from .ratchet/config.json (plain json.loads, never import ratchet.py itself) and treat the current RATCHET_RUN_ALL_SUITES count as the pre-check/standalone case whenever it is <= that value, trusting the log only when it exceeds it -- this is exact and correct for any value the config is ever set to, since the pre-check can never pick more files than its own configured cap allows.
- (2026-10-20, gate:adversarial) Final resolution for the regression.log pattern (CP2-T13 and analogues for CP3/5/6/7/8/9): abandoned entirely after 2 blocked review rounds of trying to patch a count-based context heuristic. The real, unfixable flaw: evidence/CPn/regression.log is written only AFTER ratchet.py complete's regression_command finishes, so a test case reading that path from WITHIN any invocation of this same checkpoint's own test file (including when it runs as one of the small 'related tests' files complete runs ahead of the real regression_command) can never distinguish a stale log left by an earlier, unrelated attempt from a fresh result of the run currently reading it -- no suite-count/env-var heuristic can close this, because the file structurally cannot reflect the run that is reading it. Correct, final design: the checkpoint's own 'full suite passes' case does NOT read regression.log at all by default; it passes trivially, documenting that done-means #5 is already structurally enforced by ratchet.py complete itself (which refuses to mark a checkpoint done when its own regression run fails) -- no separate re-verification is needed or even possible from inside a related-tests pre-check. Keep an opt-in env-var-gated path (e.g. RATCHET_CPn_T##_FULL_SUITE=1) that genuinely runs tests/run_all.py inline for a human/agent who wants to pay for it directly; that path can really fail. Every future checkpoint's own case must use this simpler design from the start, not attempt to read complete's own evidence file.
