# Ratchet learnings

Every Ratchet agent reads this file before starting work. Entries come from human reviews and repeated gate failures.

- (2026-09-29, gate:adversarial) Adversary reviewers must write their findings JSON file themselves with the Write tool (even when approving); returning text only stalls the round.
- (2026-09-29, gate:adversarial) Do not gate user-consent on keyword heuristics; use an exact-phrase allow-list printed in the question.
- (2026-10-04, human) Accepted limit (user decision, CP1 of the trust-holes run): Ratchet does not promise to record a hook crash when the crash-record folder is not a real folder (for example a broken symlink) and every fallback write also fails at that moment. This is documented in schemas.md; reviewers should not block on that case.
- (2026-10-04, human) Accepted limit (user decision, CP4 of the trust-holes run): Ratchet's protections stop an agent from stumbling past a gate or taking an easy shortcut, but a deliberate same-user script can still forge Ratchet's records, for example by calling Ratchet's own hook command directly with forged input. The README states this plainly. Reviewers should not block on deliberate same-user forgery of hook calls or hook records; they should still block on easy or accidental bypasses.
- (2026-10-04, gate:adversarial) When a step changes how Ratchet behaves (what counts as a reply, which commands need a question, what a hook does), update every place the docs describe it in the same step: README, every SKILL.md that mentions it, and schemas.md. Grep for the command or rule name before finishing.
- (2026-10-04, human) Accepted limit (user decision, CP5 of the trust-holes run): Ratchet's engine cannot check that the approval question was shown to the user alone in the agent's message. The skill instructions require asking it alone, at the end of its own message, and the docs say plainly that the engine cannot verify this. Reviewers should not block on the engine not verifying what the agent displayed.
- (2026-10-04, human) Known limits and set-aside items (user decision, CP5 round 6 of the trust-holes run): (1) the hook-call guard does not recognise every wrapper form that takes an option value (env -u X, sudo -u me, timeout -s KILL 10, uv run, python3 -m) or a hook call inside a heredoc body; this falls under the accepted same-user-forgery limit. (2) When the prompt or stop hook cannot take the state lock, the message it shows may be generic rather than naming the exact cause. (3) The lock's busy message may misreport a stale lock it just cleared. These are recorded for later and should not block reviews. Still must be fixed: long engine commands must not overwrite an approval made while they ran, and the README must say a reply can go unrecorded and needs resending.
- (2026-10-04, human) Design decision (user, CP5 round 7 of the trust-holes run): concurrency in the engine is handled by serialising, not merging. Every Ratchet command that changes a run holds the state lock for its whole duration, including test runs. The prompt hook does not write run state (it keeps its own records), and an approval that arrives while another command holds the lock is refused with a plain 'busy, send it again'. Prefer this simple rule over merge logic.
- (2026-10-05, human) Product requirement (user, Oct 5 2026): review loops must converge cheaply. In the trust-holes run the review limits had to be raised several times (CP1, CP5 twice, run budget 30 to 50); developers will not burn tokens on reviews that keep finding narrower edge cases. The cost-levers run must make reviews converge (for example: minors stop blocking after round 2, fewer reviewers after round 1, incremental diffs, small fix rounds, earlier accept-a-limit prompts, budget shown up front).
