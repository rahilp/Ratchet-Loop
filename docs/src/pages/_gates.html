Four gates. Always in this order.

The gates run in a fixed order, and a step can't move on until each one passes. Gates 1 to 3 run on every checkpoint. Gate 4 is you, at the end. A step with no screen change, like an API change, skips gate 2.

Gate 1Waiting

Tests

Has to be true
Tests are written before the code. At least one fails on an assertion. Then all of them pass.
How it's enforced
Ratchet runs the tests and reads each planned test's result. A test that crashed, was skipped or didn't run counts as missing. Deleting a test is refused.
  • Planned tests are frozen after their first failing run. Changing one needs your OK.
  • A test that passes before the code exists is rejected.
Gate 2Waiting

Looks right

Has to be true
The screen matches the prototype, or the old screen when rebuilding one, in the same state.
How it's enforced
Both are opened in a browser, put in the same state and screenshotted after the same actions. Two reviewers list every difference. Any difference that can be fixed in code blocks the checkpoint.
  • One reviewer checks the look. The other checks behaviour: clicks, typing and errors.
  • Reviewers see only the screenshots and the design file. They never see the code or the chat.
  • If the two screenshots show different states, the comparison is redone.
Gate 3Waiting

Review

Has to be true
No reviewer has a blocking finding on the current code.
How it's enforced
Review rounds repeat until that is true. A review counts only if Ratchet's review script signed it for that round, or the agent's own reviewer wrote it.
  • Each finding must say which users are harmed, and how.
  • From round 3, minor findings stop blocking. They are listed for you at the end.
Gate 4Waiting

You

Has to be true
You try the feature and approve it.
How it's enforced
Only a message you typed counts. Messages your CLI sends by itself, such as a background task finishing, are ignored.
  • "ok", 👍 or "yes, but…" are not approvals. Test a reply.
