Checkpoint-and-gate building

Ratchet Loop: make your AI coding agent prove its work

Your agent says it works. Ratchet makes it show you.

You describe a feature in a sentence. Your agent breaks it into small steps and builds them one at a time. Each step has to pass four checks before the next one can start. You don't type any commands.

01The problem

AI agents are fast. They're also sure of themselves when they're wrong.

Ask a coding agent for a feature and it will usually say it's done. Sometimes it is. Sometimes the tests were written after the code, so they only check what the code already does. Sometimes the button is the wrong colour, or an edge case was never tried. You find out later, after more work has been built on top.

Ratchet Loop doesn't make the agent smarter. It changes what counts as done. The agent can't say a step works. It has to show it, and Ratchet checks the evidence itself.

Agent on its ownWith Ratchet Loop
Size of each changeThe whole feature at onceSmall steps, one commit each
When tests are writtenAfter the code, if at allBefore the code, and at least one must fail first

Can it skip a checkYes, if it decides toNo. Hooks block it, and only you can lower the bar

02The idea

Done means code plus proof.

A step only counts once both are there. The proof comes from four gates, and the agent doesn't get to mark its own gates.

05The four gates

Four gates. In order. No skipping.

The first three run on every step. The last one is you, at the end. Work with nothing to look at, like an API change or a refactor, skips gate 2.

Gate 1Waiting

Tests

Has to be true
Tests are written before the code. At least one fails on an assertion. Then all of them pass.
How it's enforced
Ratchet runs the tests itself and reads each planned test's own result. A test that crashed, was skipped or never ran doesn't count. None may be deleted.
  • Planned tests are frozen after their first failing run. Changing one needs your OK.
  • A test that already passes before the code exists isn't testing anything.
Gate 2Waiting

Looks right

Has to be true
The screen matches the design, or the old screen if you're rebuilding one, in the same state.
How it's enforced
Both are opened in a browser, put in the same state, clicked through the same actions and screenshotted. Two reviewers list every difference. Any difference that can be fixed in code blocks the step.
  • One reviewer checks how it looks. The other checks how it behaves: clicks, typing, errors.
  • They only see screenshots and the design file, never the code or the chat.
  • If the two screenshots aren't showing the same thing, the comparison is thrown out and redone.
Gate 3Waiting

Review

Has to be true
Reviewers try to break the code and find nothing serious.
How it's enforced
Rounds keep going until no reviewer has a blocking finding on the current code. A review only counts if it was signed for that exact round, or written by the agent's own reviewer.
  • Every finding must say who is harmed and how, judged against the plan's objective.
  • Small nitpicks stop blocking after two rounds and are listed for you at the end.
Gate 4Waiting

You

Has to be true
You try it and say yes.
How it's enforced
Only a real message from you counts. Messages your CLI sends on its own, like a background task finishing, are never taken as your reply.
  • A thumbs-up, an "ok" or a yes with a "but" on the end doesn't count. Try it in section 10.

06Safeguards

Why the agent can't cheat. It can only fix the problem.

Ratchet installs hooks into your CLI. Hooks run on every action the agent takes, so the rules hold even when the agent would rather skip them.

R1

Ratchet checks, it doesn't take anyone's word

The agent doesn't get to say "tests pass". Ratchet runs them. Reviewers don't get to say "approved". Ratchet works out the verdict from what they found.

R2

Tests come first

A test that passes before the feature exists is rejected, because it isn't testing anything.

R3

Tests can't disappear

Every planned test has to still be there each time the tests run.

R4

Any change resets the gates

Every gate result is tied to the exact code it checked. Change the code afterwards and the gates run again.

R5

Same state, or it doesn't count

If two screenshots being compared aren't showing the same thing, the comparison is thrown out and redone.

R6

Screen reviewers are kept apart

They work in a folder that holds only the screenshots and the design file. They never see your code, your agent's instructions or the chat.

R7

Records are protected

A hook blocks anyone from editing Ratchet's records by hand. In Claude Code, only the right reviewer can write each review.

R8

No quitting early

Another hook stops the agent from ending its turn until a gate is passed, unless it's waiting for you, stuck, or paused.

What each CLI enforces today

The four CLIs don't all give hooks the same view. Ratchet is honest about the gaps.

On every CLI, a review from another AI tool counts only when Ratchet's own review script signed it for that round. A review that was typed, copied or edited by hand is refused.

07Who reviews

A second opinion from somebody else.

The model running your agent could be Claude, GPT, Gemini or a Copilot model. Ratchet doesn't mind which. What matters is that the reviewer is someone different, because a second company tends to catch what the first one misses.

Who gets asked, in order

  1. 1

    Another company

    Any AI tool installed and signed in on your machine that works.

  2. 2

    Another model

    Same company, different model. Sonnet reviewing work done by Opus, for example.

  3. 3

    The same model

    Only if nothing else is available.

How many look, by risk

Low

1 reviewer. Only serious findings block.

Normal

2 reviewers. The default.

High

4 reviewers. The plan must say which users could be harmed, and how.

Later rounds cost less

Round 1 asks every reviewer. After that, only the reviewers with an open serious finding are asked back. A small fix after approval gets one reviewer, unless the step is high risk.

One flaky failure is free

If the tests fail once and pass on an immediate re-run, the step is marked flaky and no attempt is spent. A second time counts as a real failure.

Tools that are down are skipped

A tool that's signed out is skipped for six hours. One that's out of credits waits for the reset time it gave. Its slot goes to another working tool.

Long reviews get a check-in

If a step blocks twice in a row, a fresh reviewer looks at the goal and the history and suggests simplifying the step, or asking you.

{{ICON_ASK}}Try it

Does this count as a yes?

When Ratchet needs your approval, only a clear yes moves it forward. Type a reply and see what Ratchet would make of it.

  • Counts: yes yes, go ahead go ahead approved
  • Capitals and a full stop or exclamation mark at the end don't matter.
  • Nothing else can be attached. "ok", "sure", 👍 or "yes but…" don't count.
  • Only your first reply after the question counts, and a yes only answers that one question.

Accept a finding yourself

accept: your reason

If a review blocks on something you've decided isn't worth another round, you can accept it once, with your own reason. It's written down in the step's record and in .ratchet/learnings.md. If the code changes later, normal review rules apply again.

Give a step one more round

raise: your reason

When a step hits its review limit, raising it is always the last option offered, and only once per step. Your reason is written down so later rounds and agents see it too.

The proof receipt

When you approve the finished feature, the agent pastes one honest receipt into its last message, ready for your pull request.

  • Each step's title, commit and how long it took
  • Who reviewed each step, and how many rounds it took
  • Findings you accepted, with your reason
  • Small issues left for later
  • Time is wall-clock, including time waiting on you. Never cost or tokens.

12Specs and CI

Fits the way your team already works.

If your team writes specs

OpenSpec, GitHub Spec Kit, BMAD

Ratchet builds from the spec you've written instead of making up its own plan. Every scenario gets a test that has to pass, every task is assigned to a step, and if anything is left out, the plan tells you why. As steps pass, Ratchet ticks off the matching tasks in your spec files.

Use Ratchet to build the add-dark-mode change. Use Ratchet to build story 1.3.

No spec tool? The plan you approve is the spec. After your first feature, the agent asks once if you'd like a simple record of what's been built.

Keep the checks running in CI

"Ask your agent to set up CI."

Ratchet writes a GitHub Actions workflow that runs your test command and every automatic check saved during your runs, on every push and pull request.

The AI review gates don't run in CI, because CI machines don't have the agent tools and sign-ins those gates need. If a hand-written workflow already exists, Ratchet never replaces it.

13Install

Install once. Then just ask.

You install Ratchet once per computer, not once per project. After that it's there in every project you open. The hooks do nothing in projects where you're not using Ratchet.

  1. 01Ask your agent to install it

    {{INSTALL_PROMPT}}

    Open your agent in any folder and paste this. It asks before it changes anything. Part of setup is adding hooks to your CLI, which is what stops the agent skipping a gate.

  2. 02Restart your CLI, then say

    Set up Ratchet and continue

    Hooks only load when the CLI starts. The agent checks they work, tells you Ratchet is ready, and asks what you'd like to build.

  3. 03Build something

    Use Ratchet to build this feature: describe it in a sentence or two.

    Open your agent in your project folder. A real one: "managers can approve or reject their team's leave requests, with a reason."

What you need

Your project in a git repository, and Python 3.8 or newer. If you're building screens, Ratchet also uses Node 18+ and Playwright for screenshots, and offers to set them up.

Only for one project?

Ask your agent to "install Ratchet Loop for this project only". If you use more than one CLI, ask each one to install Ratchet for itself.

Codex, Gemini or Copilot

Claude Code finds Ratchet's skills on its own. For the others, the installer keeps one shared copy, and the agent can link it into your CLI's skills folder for you.
